## 1. 原始目标与验收口径

最初要求是在 `main` 上补齐 LS2K1000LA 所需能力，第一阶段至少包含：

1. 两个 CPU 都能启动并进入正常调度；
2. UART、IRQ 控制器、AHCI、GMAC、RTC、reboot/poweroff 等板级资源根据设备树加载，
   不能在生产驱动中固定板卡地址；
3. GMAC 从轮询收发改成中断驱动；
4. AHCI 增加中断完成队列和可睡眠等待；
5. 能运行 cagent 和 buildstorm；
6. 无板阶段先完成静态检查，有板阶段再用真实串口、磁盘和网络完成验收。

参考口径在过程中发生过一次明确调整：前期允许参考 TGOSKits 观察同板固件和外设现象，
后续明确要求**正确性以 Linux 实现为准**。当前代码和静态检查因此主要对照 Linux 的
LoongArch 上下文切换、`libahci`/`libata` 和 `stmmac` 生命周期；TGOSKits 不再作为寄存器
语义和并发正确性的依据。

## 5. 真机调试时间线

### 5.1 2026-08-07：AHCI 探测错误地睡眠，触发调度器断言

最早一批 MOSS 真机日志已经能看到：

- CPU0 启动；
- DTB 报告 2 个 CPU 节点；
- GMAC0 从 DTB 探测成功；
- AHCI 进入探测，但控制器的 `ports` 一度为 `0x0`；
- AHCI 初始化中的等待进入了调度器阻塞路径，最终在
  `vendor/axtask/src/run_queue.rs:473` 触发 `assertion failed: !curr.is_idle()`。

该现象在
[2026-08-07 运行日志](../../hardware-ls2k1000la-20260807-runtime.log) 的
L1012-L1047、L1959 附近等多轮启动中重复出现。这说明初始化/idle 上下文不能使用普通
任务的睡眠等待。

随后做了以下调整：

- 平台 AHCI probe 强制使用轮询；
- 根分区识别完成后才开启运行时可睡眠等待；
- AHCI 的 `current_can_block()` 拒绝 init/idle 上下文进入 wait queue；通用 `block_on`
  则让 idle 保持轮询而不进入 run queue，普通 bootstrap 上下文与 idle 的规则并不相同；
- wait queue 在 listener 注册后再次检查条件，避免 lost wakeup。

这解决了已知断言路径，但没有解决完整启动。

### 5.2 AHCI `PI=0`：补充设备树端口掩码和 HBA reset 保存/恢复

LS2K1000LA 在 HBA reset 后会出现 `HOST_PORTS_IMPL/PI` 变为 0 的现象，导致唯一 SATA
端口消失。按 Linux `libahci_platform` 的思路，后续改为：

- reset 前保存 CAP/PI；
- reset 后恢复端口掩码；
- 允许 DT 的 `ports-implemented` 属性向低层传递；
- 当前真机 DT 临时写入 `ports-implemented = <0x1>`。

最新日志已经打印 `platform_ports=Some(1)`，因此“当前仍然只是 PI 缺失”不是足够的
解释。但这些修改是当前未提交工作区的一部分。

### 5.3 AHCI 初始化顺序和恢复状态机重构

为对齐 Linux 行为，又先后做了：

- DMA 元数据分配与 MMIO 激活拆分；
- 端口撤销按 `clear ST -> wait CR -> clear FRE -> wait FR` 顺序执行；
- FIS receive、命令引擎和 COMRESET 顺序重构；
- 增加链路 debounce、COMRESET retry、错误冻结和延迟恢复；
- 恢复路径在可能睡眠前释放命令发布自旋锁；
- 致命 IRQ 在确认 PxIS 以前先发布 `recovery_needed`，避免清状态后误报成功；
- 用多版带阶段标志的镜像定位：`MOSS_AHCI_STAGE_2E9E_BEGIN`、
  `MOSS_AHCI_SETUP_STAGE_BEGIN`、`MOSS_AHCI_LINUX_ORDER_BEGIN`。

### 5.5 SMP/IPI 与 LoongArch 上下文修改

针对上述 panic 及独立静态审查意见，工作区又修改了：

- secondary CPU 的 early/per-CPU 初始化顺序；
- 启动 IPI action 与运行时 IPI action 分离；
- IPI handler 先确认硬件状态，再解码 action 并分发；
- IPI 状态增加独立状态机测试；
- 任务上下文增加 `CSR.PRMD` 保存/恢复；
- 启动时一次性设置 `CSR.CRMD`，并设置初始 `CSR.PRMD`。

Linux 的 LoongArch `switch.S` 本身会保存和恢复 PRMD，因此“增加 PRMD 保存”目前没有
证据表明是错误。但这些低层修改与 AHCI 重构叠加在同一批镜像中，扩大了回归面，也使
后续卡死难以直接归因。

Primary CPU 0 started
device tree contains no usable RAM; using platform firmware memory ranges
MOSS_DTB cpu_nodes=2 memory_regions=2 memory_bytes=0x80000000

LS2K1000 GMAC0 from DTB ... irq=Some(28)

此后等待几十秒仍没有下一条 `COMRESET release starts`。当前能严格确认的范围是：

1. 已经向 PxSCTL 写入 COMRESET；
2. 日志中的回读值为 `0x301`；
3. 已经完成该条日志输出；
4. 没有到达下一条“释放 COMRESET”的日志。

当前源码在两条日志之间应只进行一次 1 ms 的 `Poll` 等待。对当前二进制的反汇编也确认
传入的是 `WaitMode::Poll`，不是错误进入 Event/睡眠等待；等待循环使用 `rdtime.d` 读取
单调时间。

更重要的是，对“走得最远”的旧镜像和当前镜像做原始二进制反汇编比较后，COMRESET
写入、日志调用和 1 ms 轮询等待的指令序列实质等价。旧镜像在板上通过过这段。因此，
目前没有依据把根因简单归结为“1 ms 延时函数写错”。

### 5.7 当前 AHCI 阻塞的完整代码地图

本节按**当前工作区源码**整理，不把“曾经有关”“以后会执行”和“当前已经执行”混在一起。
代码地图的目的不是复制整个仓库，而是列出当前阻塞所经过的全部生产路径、能够打断它的
外部路径，以及成功返回后才会进入的下游路径。

先给出当前最短的直接调用链：

```text
axruntime::rust_main
  -> axdriver::init_drivers
    -> AllDevices::probe
      -> Ls2kAhciDriver::probe_global
        -> RawAhci::prepare_with_port_map
          -> simple_ahci::AhciDriver::prepare_with_port_map
            -> AhciPort::try_new
              -> AhciPort::recover_if_needed(WaitMode::Poll)
                -> AhciPort::hard_reset(WaitMode::Poll, deadline_ms)
                  -> PxSCTL.write(0x301)
                  -> INFO: "COMRESET asserted"                 [已经返回]
                  -> delay_ms::<AhciHalImpl>(WaitMode::Poll, 1) [当前边界]
                  -> INFO: "COMRESET release starts"           [未到达]
```

因此对“现在是不是 AHCI 初始化出问题”的精确回答是：**是，启动当前同步阻塞在 AHCI
端口 0 的第一次初始化恢复/COMRESET 内；但还不能写成“AHCI 设备 IRQ 初始化失败”。**
AHCI 自己的 IRQ 注册要等 `prepare_with_port_map()` 成功返回后才执行，当前根本没有走到；
此时已经启用并可能介入的是全局 timer IRQ、trap return 和调度抢占路径。

#### 5.7.5 当前两条日志之间到底有什么代码

关键实现是 `vendor/simple-ahci/src/ahci.rs` L604-L622：

```rust
let sctl = (self.port.SCTL().read() & SCTL_SPD_MASK)
    | SCTL_IPM_ACTIVE
    | SCTL_DET_COMRESET;
self.port.SCTL().write(sctl);
info!("AHCI port {} COMRESET asserted: ... SCTL={:#x}",
      self.index, self.port.SCTL().read());
delay_ms::<H>(wait_mode, 1);
info!("AHCI port {} COMRESET release starts: ...", self.index);

let Some(det) = self.resume_link(wait_mode, deadline_ms) else {
    return HardResetResult::Failed;
};
```

等待策略在 `vendor/simple-ahci/src/hal.rs` L73-L102：

```rust
if mode == WaitMode::Event && H::can_sleep() {
    H::wait_for_event(timeout, condition)
} else {
    wait_until_timeout::<H>(condition, timeout)
}

pub(crate) fn delay_ms<H: Hal>(mode: WaitMode, milliseconds: u64) {
    let _ = wait_for_event_or_spin::<H, _>(mode, milliseconds, || false);
}
```

当前调用明确传入 `Poll`，所以条件 `mode == Event` 为假，不会调用
`AhciHalImpl::wait_for_event()`，也不会进入 `WaitQueue::wait_timeout_until()` 或
`axtask::block_on()`。实际循环只做：

```text
start = H::current_ms()
loop:
    condition() == false
    now = H::current_ms()
    if now - start >= 1: return
    spin_loop()
```

`H::current_ms()` 在 `vendor/axdriver/src/ls2k1000.rs` L91-L93，将
`axhal::time::monotonic_time_nanos()` 除以 1,000,000；下层路径为：

```text
vendor/axhal/src/time.rs L3-L8
  -> vendor/axplat-loongarch64-ls2k1000/src/time.rs L120-L135
    -> loongArch64::time::Time::read()
      -> vendor/loongArch64/src/time.rs L6-L17: rdtime.d
```

最新串口日志严格证明第一条 `info!` 已经完整返回；它不能证明下一次 `rdtime.d` 已经执行，
也不能区分“循环不退出”“循环中被 IRQ 打断后没有返回”“循环已经返回但第二条日志前/内
失去执行流”。因此下一次实验必须用内存 heartbeat，而不是继续只靠两条 UART 文本夹逼。

#### 5.7.7 旧断言为什么触发，以及它现在是不是直接路径

旧日志中的断言位于 `vendor/axtask/src/run_queue.rs` L470-L491：

```rust
let curr = &self.current_task;
assert!(curr.is_running());
assert!(!curr.is_idle());
...
curr.set_state(TaskState::Blocked);
self.inner.resched();
```

这个断言表达的是调度器不变量：“idle task 不能被标成 Blocked 后从可运行集合中移走”。
**断言本身是合理的，旧错误在于上游把 idle/init 探测上下文送进了可睡眠等待。** 删除或
放宽断言只会把明确 panic 变成更难定位的无可运行任务/错误切换，并不是修复。

相关防线分布为：

| 源码 | 关键位置 | 当前语义 |
| --- | --- | --- |
| `vendor/axtask/src/block_context.rs` | L1-L17 | AHCI 等普通 wait queue 只允许非 init、非 idle 任务阻塞；通用 `block_on` 只禁止 idle park |
| `vendor/axtask/src/api.rs` | L88-L97 | `current_can_block()` 向驱动暴露上述普通任务判定 |
| `vendor/axtask/src/future/mod.rs` | L50-L97 | idle 遇到 Pending 时继续 poll；可 park 的任务才进入 run queue |
| `vendor/axtask/src/wait_queue.rs` | L89-L120 | 注册 listener 后重查条件，最后通过 `block_on` 等待 timeout/event |
| `vendor/axtask/src/run_queue.rs` | L463-L491 | 最终阻塞入口保留 `!curr.is_idle()` 断言 |
| `vendor/axdriver/src/ls2k1000.rs` | L99-L108 | AHCI Event wait 用 `current_can_block()` 判定并接入全局 AHCI wait queue |

旧失败的路径是：

```text
AHCI delay/recovery(Event)
  -> wait_for_event_or_spin(Event)
  -> AhciHalImpl::wait_for_event
  -> WaitQueue::wait_timeout_until
  -> axtask::block_on
  -> blocked_resched
  -> assert!(!curr.is_idle())
```

当前最新停点的路径是 `delay/recovery(Poll) -> wait_until_timeout -> rdtime.d`，不经过上述
Event/wait queue/blocked_resched 链。因此不能再用旧断言解释当前 COMRESET 后的停点；
断言修复应保留，但本轮首先要查 Poll 窗口本身和能够打断它的全局 IRQ 路径。

#### 5.7.8 MMIO、barrier、DMA 和日志的代码依赖

| 类别 | 源码 | 当前能确认的事实 | 尚不能下的结论 |
| --- | --- | --- | --- |
| MMIO 布局 | `vendor/simple-ahci/src/mmio.rs` L8-L16、L533-L578 | ports 起点为 host+0x100，每个 `PortRegisters` 0x80；PxSCTL 是结构中的 u32 字段 | 结构定义本身不证明具体 SoC 写后时序正确 |

属于初始 reset 环境的一部分；但最新直接停点发生在一个只读取时间的 1 ms 循环中，尚无
证据能把 cache coherency 写成第一根因。MMIO barrier、DMA mapping、日志时序都应分别做
单变量实验，不能一次一起改。

#### 5.8.1 watchdog 的硬件事实和职责边界

本轮静默没有进入 panic handler，所以只做 panic→reboot 不能恢复这一类故障。实际
`board.dtb` 给出了以下硬件资源：

```dts
watchdog@1ff6c030 {
    compatible = "loongson,ls2x-wdt";
    reg = <0x0 0x1fe27030 0x0 0xc>;
    clocks = <0x5 0xc>;
    clock-names = "wdt-clk";
    status = "okay";
};
```

Gitee 上 `open-loongarch/linux-5.10` 的 LS2K1000 厂商驱动和头文件进一步确认：

- `RST_CTR = 0x00`、`WD_CR = 0x04`、`WD_TIMER = 0x08`；
- start 向 `RST_CTR` 写 `1 << 1`，ping 向 `WD_CR` 写 `1`；
- timeout count 为 `wdt_clk_hz * timeout_seconds`；
- `CLK_WDT` 是 `CLK_APB`；本板 U-Boot 多次实测 `Bus @ 125 MHz`，Linux 也反复打印
  `ls2x-wdt 1fe27030.watchdog: Loongson2 Watchdog driver registered`；
- 因此 30 秒对应 `3_750_000_000` counts，仍在 `u32` 范围内；理论整数秒上限为 34 秒。

参考代码：

- `drivers/watchdog/loongson2_wdt.c`：start/ping/stop/set_timeout 和 DT compatible；
- `arch/loongarch/include/asm/mach-loongson64/loongson-2k.h`：三个寄存器偏移；
- `arch/loongarch/boot/dts/loongson/loongson2k1000.dtsi`：节点、MMIO 和 `CLK_WDT`；
- `include/dt-bindings/clock/loongson2k1000-clock.h`：`CLK_WDT = CLK_APB`。

硬件 watchdog 能解决“静默卡死后实验永远停住、必须人工按 reset”的恢复问题，但不会
修复 AHCI、SMP 或 fork/exec/wait 的根因。喂狗也不能简单绑定到 timer IRQ：如果调度或
用户进程已经卡死，而 timer IRQ 仍能运行，无条件喂狗会把真正的卡死永久掩盖。

为避免再次混变量，实施顺序固定为：

1. 先用现有单核镜像完成 SMP on/off A/B；
2. 再单独实现 LS2K1000 start/ping/stop，首个 watchdog 镜像只做“启动后故意停止喂狗”；
3. 真机验收约 30 秒后硬件自动复位；
4. 复位闭环通过后，再增加依赖测试前进量的 heartbeat，前进量超时即停止喂狗；
5. panic→reboot 处理快速失败，watchdog 处理无 panic 的死锁/活锁，两者职责分开。

### 5.9 2026-08-08：收敛 AHCI，并实现硬件 watchdog 闭环

本轮不再继续扩大 AHCI、SMP、调度器和文件系统的改动面，只实现两个可独立验收的变化：

1. 把 AHCI 同步恢复限制为一次 5 秒 COMRESET；
2. 增加与 panic→reboot 独立的硬件 watchdog，负责从无 panic 的静默卡死中回到 U-Boot。

#### 5.9.1 为什么原来的 35 秒在这里不合理

原代码的 `RESET_TIMEOUTS_MS = [10_000, 10_000, 35_000, 5_000]` 来自 Linux libata EH
的 reset timeout 表。35 秒不是 LS2K1000 AHCI 控制器要求的固定等待时间，也不是本板 SATA
盘的实测需求。Linux 把这组重试放在独立 error-handling worker 中执行，普通 I/O 提交者不会
在原调用栈中同步承担整组最长约 60 秒的等待；MOSS 没有 libata EH worker，却把同一调度表
放进同步 probe/recovery 调用栈，因此会长期占住启动或 I/O 任务，而且一次失败没有增加新的
诊断信息。

现在 `vendor/simple-ahci/src/ahci.rs` 只保留：

```rust
const RESET_TIMEOUT_MS: u64 = 5_000;
```

`recover_if_needed()` 只调用一次 `hard_reset(wait_mode, deadline_ms)`。成功就恢复命令引擎；
失败或 offline 就保留 `recovery_needed`，通过已有的 `OFFLINE_RETRY_MS = 60_000` 在后续 I/O
重新尝试。这样 5 秒是当前调用的明确上界，60 秒是下一次尝试的门控间隔，二者职责不再混合。

#### 5.9.2 watchdog 的完整代码边界

与 watchdog 直接相关的代码如下：

- `vendor/axplat-loongarch64-ls2k1000/src/fdt.rs`：按
  `compatible = "loongson,ls2x-wdt"` 解析 MMIO，并校验 12-byte 寄存器窗口、`wdt-clk`
  和 APB watchdog clock selector 12；生产代码不固定写入本板 MMIO 地址；
- `vendor/axplat-loongarch64-ls2k1000/src/watchdog.rs`：实现 `start/ping/stop`，寄存器偏移
  分别为 `RST_CTR=0`、`WD_CR=4`、`WD_TIMER=8`，以 125 MHz APB clock 计算 timeout count；
- `vendor/axplat-loongarch64-ls2k1000/src/init.rs`：DT 解析完成后先停止 warm boot 可能遗留
  的 watchdog；平台 IRQ 和 per-CPU timer 就绪后启动 watchdog，因此 AHCI driver probe 已在
  watchdog 保护范围内；
- `vendor/axplat-loongarch64-ls2k1000/src/power.rs`、`vendor/axplat/src/power.rs` 和
  `vendor/axhal/src/lib.rs`：向内核提供 `axhal::watchdog::{start,ping,stop}`；其他平台默认
  为不可用/no-op，不改变现有 poweroff/reset 行为；
- `kernel/src/watchdog.rs`：建立独立 monitor task，每 5 秒检查一次前进量；最后前进时间在
  20 秒以内才喂狗，超过 20 秒停止喂狗并只在状态转换时打印一次错误；
- `kernel/src/syscall/mod.rs`：只有可识别的 syscall 进入时才刷新前进量，无效 syscall 不算；
- `kernel/src/entry.rs`：调度器就绪后尽早启动 monitor；init 正常退出、unmount 和 flush
  分阶段刷新前进量，受控 poweroff 前停止 watchdog；
- `vendor/axruntime/src/lang_items.rs`：panic 仍立即调用 `system_reset()`；watchdog 是没有
  panic 或 reset syscon 路径失效时的后备；
- 根 `Cargo.toml` 和平台 `Cargo.toml`：`watchdog-smoke` 使用 10 秒 timeout，并故意让
  `ping()` no-op，用于证明复位完全由硬件完成；
- 根 `Makefile`：`kernel-la-2k1000-watchdog-smoke`、`kernel-la-2k1000-smp1` 提供可重复
  的 smoke 和单核构建；
- `tests/fixtures/ls2k1000la.dts` 与 `scripts/check_ls2k1000_static.sh`：验证 DT watchdog
  合同，并禁止 AHCI 恢复重新引入 35 秒或多次同步 reset。

生产策略是 30 秒硬件 timeout。最后 syscall 后，monitor 最多继续喂约 20 秒，随后硬件从
最后一次 ping 再计 30 秒，所以预期自动复位窗口约为 45--50 秒。若 monitor task 自己无法
调度、整个 CPU 卡死或 IRQ 路径失效，硬件会在最后一次 ping 后约 30 秒直接复位。

这个策略是当前板级调试策略，不是通用服务器健康判据：一个合法的、超过约 50 秒完全不进入
syscall 的纯计算或长睡眠进程也可能触发复位。当前目标是自动捕获已经复现的
`waitpid/fork/exec` 静默停滞；根因修复后应把前进量改成更具体的测试阶段 heartbeat，或调大
策略阈值。

应只对 `hard_reset()` 的 COMRESET write 之后到 `delay_ms(Poll, 1)` 返回之间做单变量定位。

没有机会启动；其 20 秒 stale 转换日志和约 45--50 秒 reset 路径仍待一轮 AHCI 成功启动后验收。

单核 A/B 也已上板，但没有进入 AHCI。日志 L2185 确认 `smp = 1`，L2216 随即在
`axtask::init_scheduler()` 触发既有断言：

```text

```

把调度器修补和 AHCI 时序改动放进同一镜像。

## 7. 已经排除或明显降级的解释

下面这些说法与现有证据不符，不能继续当成当前根因：

- **板卡或 SATA 盘已经坏了。** U-Boot 和同一日志中的 Linux 都能识别
  `Kingchuxing 32GB`，Linux 能挂载该盘；MOSS 的中间镜像也识别过它。
- **当前只是 AHCI `PI=0`。** 最新日志已经显示 `platform_ports=Some(1)`，并实际访问
  了端口 0 的 PxSCTL。
- **COMRESET 没有写进去。** 最新日志回读 `SCTL=0x301`。
- **错误进入了可睡眠 Event wait。** 当前镜像反汇编显示该调用使用 Poll。
- **1 ms 的 `rdtime.d` 循环必然写错。** 旧的走远镜像具有实质等价的循环，并在板上
  通过过；它仍可能受到中断或上下文影响，但循环本身不能据此定罪。
- **宿主机测例通过就代表驱动完成。** 测例不覆盖真实 MMIO、cache coherency、DMA、
  LIOINTC 和设备时序。

## 8. 尚未证实的根因方向

当前只能保留以下假设，不能把其中任何一项写成结论：

1. 1 ms 轮询期间到来的 timer/device IRQ 在 trap return、PRMD 或调度路径上丢失了执行流；
2. AHCI 重构后，FIS receive/命令引擎启动到 COMRESET 之间的稳定时间不足；旧版大量 INFO
   日志无意间提供了额外延时；
3. 端口或 HBA 在 warm boot/reset 后存在尚未正确处理的控制器状态；
4. MMIO/cache/barrier 语义在某条新路径上不完整；
5. 当前 AHCI 改动和同期 SMP/IPI/上下文改动发生交叉回归。

Linux 会先建立端口和错误处理状态，再由异步 error-handling 流程处理初始 reset；当前
MOSS 在同步 probe 中完成这些动作。生命周期差异可能重要，但还没有单变量实验证明它是
本次卡死原因。

## 9. 调试过程本身存在的问题

本轮长期没有收敛，不只是硬件难调，执行方式也有明显问题：

1. **改动面不断扩大。** AHCI、GMAC、调度器、wait queue、SMP/IPI、CSR 上下文、FDT
   和内存同时变化，使一次板测失败无法对应到唯一变量。
2. **没有为每个上板镜像冻结对应源码提交。** 目前保留了二进制和日志，但“最远镜像”
   没有一个可直接检出的临时提交，增加了复现和二分难度。
3. **调试日志改变了设备时序。** 最远镜像有大量逐阶段 INFO；精简日志后又卡住，说明
   日志不能当成无副作用观测手段。
4. **静态测试覆盖被高估。** 状态机测例能防纯逻辑回归，但没有 MMIO/DMA/IRQ 集成层；
   通过 74 个测例并不表示 AHCI 或 GMAC 已经上板完成。
5. **多次 reset 没有对应新的、可证伪的假设。** 这造成重复上电但信息增量很低，还让
   Linux 多次报告 ext4/JBD2 非正常关机和元数据不一致风险。
6. **阶段性走远曾被当成接近完成。** 实际上只要没有稳定进入用户态、跑完应用和压力
   验收，就仍应标记为失败。
7. **参考实现边界前期不够严格。** TGOSKits 只能辅助观察板级现象；正确性最终必须按
   Linux 和硬件规范核对。

## 10. Linux 与 MOSS 当前表现的对比

同一块板和磁盘上，Linux 日志显示：

- SATA link 以 3.0 Gbps 建立；
- 识别同一块 32 GB SATA 盘；
- 发现 `sda1`、`sda3`；
- 能挂载根文件系统并进入系统服务。

因此硬件链路有稳定工作的参照。Linux 同时报告过 ext4 bitmap/bg descriptor 不一致、
JBD2 dirty metadata 和 journal 非正常关闭；这些首先是根文件系统一致性风险，现阶段没有
证据证明由 MOSS AHCI 数据写坏导致，但反复硬 reset 会加重风险，后续测试前应先在 Linux
下只读检查或备份数据。

MOSS 的差距是：AHCI 初始化和错误处理仍在同步启动路径中，SMP/IPI 生命周期也没有经受
稳定启动验证，GMAC 只完成 probe。它离 Linux 的可靠性不是一两个日志告警的差距，而是
关键生命周期尚未闭环。

6. AHCI 能稳定越过 COMRESET 后，再验收 syscall monitor 的 20 秒 stale 转换与 45--50 秒

## 14. 17:15 后的收敛结果（覆盖前面的历史“当前状态”）

前面第 5.9、8、11、12 节保留的是当时的实验记录，其中“仍卡在 COMRESET”和“20 秒无
syscall 后停止喂狗”已经被后续证据推翻。本节是本文截至目前的有效状态。

### 14.1 不是一个 AHCI bug，而是三个依次暴露的问题

最终因果链如下：

1. **启动阶段假卡在 AHCI。** timer IRQ 在驱动同步初始化期间抢占 primary bootstrap task。
   该 task 使用固件启动栈，不具备普通调度任务的生命周期；从 IRQ return 路径切走后会触发
   `Arc::strong_count(&prev_task) > 1` 等不变量或丢失执行流。COMRESET 只是当时正好执行的代码。
2. **修复 bootstrap 抢占后，secondary/GC 仍可能异常。** 固定工具链
   `nightly-2025-05-20` 在 LoongArch release 构建中移动较大的 `TaskInner` 返回值时，A/B
   诊断观察到 `need_resched`、`is_idle` 等字段在最终 `Arc` 中与构造值不一致。代码形状变化
   会改变表现，因此不能靠添加日志或拆表达式作为修复。
3. **真正进入用户态后才暴露 AHCI 运行期完成丢失。** 旧日志
   [AHCI/SMP 综合日志](../../hardware-ls2k1000la-20260808-ahci-irqmask-board.log) L37307 和 L37443
   的 timeout 同时满足 `PxCI=0`、`PxIS.DHR=1`、TFD 无 BSY/DRQ/ERR。这严格说明磁盘/HBA
   已完成命令，而软件完成队列没有得到发布；随后 L37359/L37496 是 ext4 error 5，L37498
   是 bash 的 SIGBUS。它不是磁盘仍忙，也不是应该继续等待 35 秒。

所以，原断言本身对正常 `switch_to()` 是合理的：当前 task 的局部 `Arc` 即将转移/释放时，
调度器或其他所有者必须仍持有强引用，否则上下文切换途中就可能析构 task。错误做法是删掉
断言继续跑；本轮保留 L678 的断言，修复让不满足其前提的 bootstrap/idle 上下文不再进入
这条普通任务切换路径。

### 14.2 最终调度器相关代码

屏蔽 AHCI 外部 IRQ、保持 PxCI 可读”的 fault-injection，确认该告警出现且读盘仍成功。

run queue 和上下文切换仍健康。真正的内核硬锁使 monitor 无法运行，最后一次 ping 后约 30 秒
硬件会自动复位；用户态逻辑死锁但调度器仍健康不属于这个硬件 watchdog 能可靠判定的范围。

64 个 inode cache shard 和 16 个 lookup lock shard 已全部撤销；当前代码和静态检查均拒绝
`INODE_METADATA_CACHE_SHARDS`、`LOOKUP_LOCK_SHARDS`。

### 16.1 DWMAC 不是“能 link up 就正确”：描述符步长必须与 ATDS 一致

板上 `DMA_HW_FEATURE=0x1b0d2fbf` 明确表明 DWMAC 3.70a 支持 enhanced descriptor。旧实现
在描述符字段中使用 enhanced ring end 位，却仍按 16-byte descriptor 分配和递增 DMA ring，
同时 CSR0.ATDS 为 0。硬件按 8-word enhanced descriptor 访问时会越过软件分配的 4-word
元素边界，能够破坏相邻内存；PHY link up 和偶尔收发成功不能排除这种 DMA 越界。

当前改动位于：

| 文件 | 当前职责 |
|---|---|
| `vendor/axdriver_net/src/dwmac_ls2k1000.rs` | TX/RX ring 使用 32-byte enhanced descriptor；启动时校验 HW feature，设置 CSR0.ATDS，并打印实际寄存器回读 |
| `vendor/axdriver_net/src/dwmac_ls2k1000_state.rs` | 纯状态函数构造 BUS_MODE，包含 ATDS/PBL/FB/MB/AAL 等受控位；测试 enhanced stride 和 RX FCS 长度处理 |

[原始 Event 路径真机日志](../../hardware-ls2k1000la-20260808-dwmac-atds32-original-event-smp1.log)
L1045-L1046 已确认 `descriptor_size=32`、`BUS_MODE=0x01900880`、`ATDS=true`；L1306-L1317
随后建立了 10 条本地 TCP 连接。这证明修复真实进入硬件，但不代表后面的软件并发问题消失。
`dwmac_ls2k1000_state.rs` 的 23 个宿主机测例全部通过。

### 16.2 第一处后续故障：`event-listener` 内部指针被观察为 `0x1`

同一日志 L1318-L1319 在 17.8 秒出现 PLV0 写 page fault：PC
`0xffffff809820457c`、`fault_vaddr=0x148`。符号化落到 `event_listener::Inner::insert`，现场的
`Event::inner` 指针值为 `0x1`。panic handler 随即在 L1362 调用 DT syscon reset，U-Boot 在
L1371 重新出现。因此这不是 AHCI 初始化、DWMAC ring stride 或“断言一定错误”，而是进入
`axsync::RawMutex` 的 heap-backed listener 慢路径时读到了损坏/无效的 Event 内部状态。

现阶段的收敛改动在 `vendor/axsync/src/mutex.rs`：只有 LoongArch 在有竞争且短自旋失败后
执行 `yield_now()`，让持锁者继续运行，不进入已实测崩溃的 `event-listener` 慢路径；其他架构
保持原实现。它是隔离内存生命周期问题的临时 containment，不是对 `event-listener` 根因的
最终证明，也没有扩展成新的锁分片结构。

### 16.3 第二处后续故障：raw `spin::RwLock` upgrade 在单核形成活锁

[mutex-yield 真机日志](../../hardware-ls2k1000la-20260808-dwmac-atds32-mutex-yield-smp1.log)
已经越过 17.8 秒 page fault，但随后反复停在 PC `0xffffff8098260440`。L477、L498 在 46 秒和
96 秒采样到完全相同的 PC，符号化为 `DirEntry::grow_cached_len_if_present()` 中
`spin::RwLockUpgradableGuard::upgrade()` 的 LL/SC 循环。L472 同时说明 watchdog monitor 和
timer 仍能运行，最后 syscall 为 64；这是一条“调度器活着、业务线程在内核锁里活锁”的直接
证据。

原 `INODE_METADATA_CACHE_TRANSACTION` 的普通 metadata 操作持 read guard，长度提交/失效路径
取得 upgradeable guard 后原地自旋升级。在单核上，如果 read guard 的持有者已经被换下，
升级者持续占 CPU 就使持有者无法恢复并释放 read guard。断言和 upgrade 操作表达的缓存一致性
需求是合理的，错误的是用 raw spin upgrade 跨越可能发生文件系统 I/O/调度的事务边界。

当前只把这一把跨操作事务锁改为 `axsync::Mutex<()>`：

- `vendor/axfs-ng-vfs/src/node/mod.rs` 使用一个 `TransactionMutex`，所有原 read/upgrade 入口统一
  调用 `lock()`；per-inode cache 和短 registry 临界区仍保留原 spin mutex；
- `vendor/axfs-ng-vfs/Cargo.toml` 显式依赖 `axsync` 的 `multitask` feature，`Cargo.lock` 和
  `.cargo-checksum.json` 同步更新；
- 没有 shard、hash 路由或目录代码移植；临时逐 metadata `warn!` 已去掉，避免串口日志本身把
  cagent 从毫秒级拖到数百秒。

[metadata mutex 诊断日志](../../hardware-ls2k1000la-20260808-dwmac-atds32-mutex-yield-metadata-mutex-smp1.log)
确实越过了前两处停点并在 L7626-L7668 建立本地 TCP 连接，但该镜像每次 metadata 操作都打印
多条 WARN，约到 234 秒才进入 TCP，且测试 timeout/reject 已被日志风暴污染，不能作为性能或
通过结果。去日志、显式使用 `axsync` 的当前镜像才是本轮上板对象。

### 16.4 新 watchdog：检测“持续在内核中可运行”，不检测“多久没 syscall”

旧策略只要 monitor task 每 5 秒被调度就一直喂狗，所以 L472 已经报告业务 22.3 秒无进展，
板子仍会无限挂住。反过来，简单采用“20 秒无 syscall 停止喂狗”也不正确：正确日志中的
buildstorm 可运行 331.8 秒，纯用户态计算不应被杀；`waitpid/read/accept/futex` 也可以合法地
长期阻塞。

当前策略分四种情况：

| 现场 | 判定与动作 |
|---|---|
| panic/assert/page fault | `vendor/axruntime/src/lang_items.rs` 立即 `system_reset()` |
| IRQ 关闭、调度器或 monitor 自身硬卡 | monitor 无法继续 ping，硬件 runtime timeout 10 秒后复位 |
| 同一线程在同一 syscall 内超过 20 秒，且状态持续为 `Running/Ready` | monitor 每 2 秒确认，停止 ping；异常持续则最多再等 10 秒硬件复位，恢复为健康状态则重新 ping |
| 长用户态计算，或 syscall 任务状态为 `Blocked` | 正常 ping，不把 buildstorm 或合法 wait/read/accept 当死锁 |

相关代码完整边界如下：

| 文件 | 作用 |
|---|---|
| `kernel/src/task/mod.rs` | 每个 LS2K 用户线程保存 active syscall 的进入时间和 syscall 号；原子时间戳为有效标志并做双读竞态校验 |
| `kernel/src/syscall/mod.rs` | syscall 分派前创建 guard；guard 的 `Drop` 保证正常返回和以后新增 early-return 都会清除 active 标志 |
| `kernel/src/watchdog.rs` | monitor 枚举用户 task，只对 `Running/Ready + active syscall + age > 20 s` 停止喂狗；2 秒检查，10 秒硬件窗口 |
| `kernel/src/entry.rs` | boot milestone 显式 ping；在 scheduler 用户流程建立时启动 monitor，受控卸载前 stop |
| `vendor/axplat-loongarch64-ls2k1000/src/watchdog.rs` | 从 DT 获取 MMIO/125 MHz clock；early boot 30 秒，硬件计数器上限约 34 秒 |
| `vendor/axplat-loongarch64-ls2k1000/src/power.rs` | DT syscon reboot/poweroff |
| `vendor/axruntime/src/lang_items.rs` | panic 直接 reboot，不等待 watchdog |
| `scripts/run_ls2k1000_serial_tftp.py` | Linux 卸载 `sda2`、重启、拦截 U-Boot、设置 `root=/dev/sda2`、TFTP 和长时间日志采集；Linux 等待由旧 45 秒改为 600 秒 |
| `scripts/check_ls2k1000_static.sh` | 拒绝旧的 syscall-frequency 策略、raw metadata upgrade 和 shard 常量，并执行状态机/双核交叉构建/ELF 检查 |

一个偶发的 `Ready` 采样不会立即复位：只要下次采样看到 syscall 返回或任务进入 `Blocked`，
monitor 就恢复 ping；硬件要连续 10 秒得不到 ping 才动作。这给短暂调度窗口留出容错，同时把
已观测的持续 LL/SC 活锁限制在约 30--32 秒内自动恢复。

## 17. 2026-08-09：从错误的 syscall 卡死判定收敛到 accepted socket 最终分配

本节是当前状态，覆盖第 16.4、16.5 节中的旧 watchdog 判定和旧待测镜像。结论已经进一步
收敛：**AHCI 初始化、`sda2` 和 ext4 在所有相关真机轮次中都正常；当前启动后故障发生在
cagent 的本地 TCP `accept4` 路径，不是 AHCI。**

### 17.1 三个依次被证伪的“卡死”判据

不能把“任务很久没有从 syscall 返回”直接等同于内核卡死。真机实验按单变量增加信息后，
依次排除了下面两种误判，并保留第三种可验证条件：

| 判据 | 真机结果 | 结论 |
|---|---|---|
| `Running/Ready + 同一 syscall > 20 s` | `simple_llm_server` 可长期停在 syscall 202 (`accept4`)，其他任务仍继续调度 | 错误；合法 `accept/read/wait` 和长编译都会被误杀 |
| cooperative mutex wait > 10 s | tid 47 等待 mutex `0xffffff8098635e10`，真实 owner tid 46 处于 `Blocked`/syscall 221；稍后 owner 和 waiter 都继续并退出 | 错误；live owner 后面的长竞争不是 orphan |
| mutex wait > 10 s，且 owner task 不存在或已经 `Exited` | cagent 服务端反复出现指针形态的 owner ID，等待永不自行结束 | 当前 watchdog 的唯一软件级停喂条件 |

[syscall 202 误判日志](../../hardware-ls2k1000la-20260809-axsync-address-diag-smp1.log) 在
L556 记录旧 runnable-syscall 判定，随后硬件 watchdog 自动回到 Linux；
[live owner 诊断日志](../../hardware-ls2k1000la-20260809-mutex-owner-diag-smp1.log) L3617 则直接给出
waiter/owner 两边的 task、状态、schedule count 和 syscall，证明仅看等待时长仍不充分。

最终 `kernel/src/watchdog.rs` 使用下面的固定策略，不存在“35 秒尝试”：

- 每 1 秒检查一次；
- mutex 必须已经显式进入 cooperative slow path，并持续超过 10 秒；
- 只有 `axtask::task_by_id(owner_id)` 查不到 owner 或 owner 为 `Exited` 才停止 ping；
- 硬件 runtime watchdog 再给 10 秒复位窗口；等待若恢复，立即恢复喂狗；
- 长 syscall、长用户态计算和 live-owner 竞争始终喂狗；monitor 本身若因 IRQ/调度器硬卡不能
  运行，硬件 watchdog 会自然复位；
- panic/assert/page fault 不等待上述窗口，由 panic handler 立即 reboot。

这里的 10 秒是“确认 owner 已经失效”的观测窗口，后面的 10 秒是硬件复位窗口；不是把每次
AHCI 或 `accept` 操作做 20/35 秒重试。AHCI 同步 COMRESET 仍只有一次、上限 5 秒，静态检查
继续拒绝 `35_000` 和多次同步 reset。

### 17.2 精确停点：`LocalTcpSocket::remote_endpoint()` 的第一把新锁

在 task wait marker 中加入 `#[track_caller]` 传播后，
[caller 定位日志](../../hardware-ls2k1000la-20260809-mutex-caller-diag-smp1.log) L553 得到：

```text
pid=31 tid=31 name="simple_llm_server" syscall=Some(202)
caller=vendor/axnet/src/local.rs:559:14
dead_owner_tid=18446743524129366976 (0xffffff800a77e3c0)
```

该版本的 L559 正是 `LocalTcpSocket::remote_endpoint()` 中的 `self.stream.lock()`。完整调用链为：

```text
simple_llm_server accept4 (syscall 202)
  -> kernel/src/syscall/net/socket.rs::sys_accept4
  -> axnet::SocketOps::accept
  -> TcpSocket::accept
  -> LocalTcpSocket::accept (从 listener queue 取出 LocalTcpStream)
  -> TcpSocket::new_local_connected
  -> LocalTcpSocket::new_connected
       stream: Mutex::new(Some(stream))
  -> 返回并移动 Socket/TcpSocket/LocalTcpSocket 大聚合值
  -> sys_accept4 在 fd 发布前调用 socket.peer_addr()
  -> TcpSocket::peer_addr
  -> LocalTcpSocket::remote_endpoint
  -> self.stream.lock()                   <-- 精确停点
```

这把 `stream` mutex 是 accepted socket 刚构造的新锁，尚未发布给其他任务，按语义 owner 必须
为 0。现场却不是任何 task ID，而是堆指针形态的数据：64-bit owner 两轮分别出现
`0xffffff800ab25000` 和 `0xffffff800a77e3c0`；把 owner 临时改成 32-bit 后仍出现
`0x0a9ce800`。因此问题不是“真实 owner 忘记 unlock”，也不是递归加锁断言本身错误；断言只是
让损坏状态更早可见。把 owner 缩成 32 bit 只截断了同一个坏指针，不能修复问题。

[orphan owner 日志](../../hardware-ls2k1000la-20260809-orphan-mutex-watchdog-smp1.log) L16084 和
[32-bit 反证日志](../../hardware-ls2k1000la-20260809-mutex-owner32-fix-smp1.log) L16150 都由硬件
watchdog 自动复位并返回 Linux，不需要人工按 reset。现场和此前大 `TaskInner` move 后必须在
最终 `Arc` 中重写原子调度字段的现象一致：固定的 `nightly-2025-05-20` 在移动大聚合值时会
产生错误的原子字段状态。它也解释了旧轮次为什么曾在同一类新 mutex 中看到
`Event::inner == 0x1`。

### 17.3 当前修复：先进入最终 `Arc`，再重置未发布的新锁

仅在 `axsync::RawMutex::lock()` 中抢占无效 owner 不是完整修复：即使 owner 被清零，已经污染
的 `Event::inner` 仍会在 mutex 析构时被 `Event::drop` 当作 `Arc` 指针释放。当前代码因此增加
了更窄、顺序明确的最终分配修复：

1. `sys_accept4` 先执行 `Arc::new(Socket(listener.accept()?))`，不再对仍会继续移动的栈上大值
   调用 `peer_addr()`；
2. 在该 `Arc` 仍由当前线程唯一持有、尚未进入 fd table 时，用 `Arc::get_mut` 取得独占引用；
3. 只重置 accepted TCP socket 的 `handle/bound/listener/stream` 四把新 cooperative mutex 的
   raw state，保护的数据（handle、endpoint、listener、stream）保持不变；
4. raw state 用 `ptr::write(RawMutex::new())` 覆盖，不运行可能已经持有坏指针的旧
   `Event::drop`；这个 unsafe API 明确要求“新建、独占、从未有 guard/waiter、尚未发布”；
5. 然后才设置 `O_NONBLOCK`、查询 `peer_addr()` 并通过 `add_file_like(Arc<Socket>)` 发布 fd。

如果最终分配前已经观察到非零 owner，axnet 会打印一次
`reinitialized moved accepted TCP mutexes`，并给出四把锁的旧 owner，作为真机验收的直接证据。
临时打印 listener/queue 地址的 `LOCAL_TCP_ACCEPT_LOCKS_REPORTED` 已删除。

`axsync` 中的 owner registry 恢复仍保留为后备：只有 owner ID 不对应任何 live task 或 owner
已经 `Exited` 时才允许 CAS 回收；真实 live owner 仍只能等待其正常 unlock。LoongArch 的竞争
慢路径继续使用 `yield_now()`，避免进入已在板上观察到坏指针的 heap-backed Event listener；
其他架构保持原 event-listener 阻塞路径。

### 19.1 手册能证明什么，真机又证明了什么

本地保存的《龙芯 2K1000LA 处理器用户手册 V1.0》和《龙芯 2K1000LA 处理器数据手册 V1.1》
明确芯片内是两个 LA264 核，但不定义 ALE/BADI 的实现细节。异常语义应以龙芯官方
[《LoongArch Reference Manual, Volume 1》](https://loongson.github.io/LoongArch-Documentation/LoongArch-Vol1-EN.html)
为准：普通 load/store 是否允许未对齐由实现和 `CSR.MISC.ALCLx` 共同决定；不允许时产生
Address aLignment fault Exception（ALE）；`CSR.ERA` 保存致异常指令 PC，`CSR.BADV` 保存坏地址，
`CSR.BADI` 按架构定义应保存同步异常的指令字。

板端 U-Boot 和 Linux 都把实际 CPU 识别为 LA264。真机 early trap 采样却稳定得到
`ECODE=0x09`、有效 ERA/BADV、`BADI=0x00000000`；这不是一次 CSR 被后续异常覆盖，因为值是在
异常入口第一时间输出，并在内核 early boot、用户态 `agent_lite`、`rustc` 和 `cargo` 上重复。
因此实现不能把“手册说 BADI 应有指令”当作 LA264 真机一定满足的前提：BADI 非零时优先使用，
为零时必须从仍然 4 字节对齐的 ERA 回读指令。此前把用户 ELF text 改成 64 KiB 对齐也没有改变
ALE，已经反证“只是 text 装载对齐错误”；真正触发点既有编译器合并生成的未对齐宽访存，也有
用户程序本身的合法可模拟访存。

### 19.3 BADI=0 fallback 通过启动，随后暴露用户页懒分配

`vendor/axcpu/src/loongarch64/trap.rs` 的 PLV0 路径现在优先用硬件 BADI，仅当其为零才从
`tf.era` volatile 读取 32 位指令。`vendor/axcpu/src/loongarch64/uspace.rs` 只在异常种类确实是
`AddressNotAligned` 且 BADI 为零时读取用户 ERA；page fault、syscall 和其他异常不会盲目
解引用 ERA。[BADI/ERA trace 真机日志](../../hardware-ls2k1000la-20260809-badi-era-fallback-smp1.log)
证明这条路径模拟了大量内核和用户未对齐访存，越过 early boot、allocator、VM、scheduler、
AHCI、ext4 并进入 `cagent-glibc`。该镜像逐异常打印，所以只作为机制证据，不作为性能结果。

去掉刷屏后的 [ERA fallback 干净日志](../../hardware-ls2k1000la-20260809-unaligned-era-clean-smp1.log)
给出了下一层精确失败：

- `agent_lite`：ERA `0x120001b08`、BADV 位于用户栈、BADI `0x29c01340`；反汇编为
  `st.d $zero,$s3,4`，模拟器报 `(n=8)`；
- `rustc`：真实 BADI `0x3828308e`，4 字节模拟失败；
- `cargo`：真实 BADI `0x380c1cad`，8 字节模拟失败；
- cagent 10 项因此 reject，buildstorm 的 toolchain/minibuild/compile 均 SIGBUS/135；init 于
  84.5 秒正常结束并自动 reboot 回 Linux。

`n=8` 不是解码器不知道 `st.d`，也不是 bytewise loop 不支持 8 字节。`unaligned.S` 已把
`st.d` 分解成八个 `st.b`；原始 ALE 在地址翻译/懒分配之前发生，用户栈页可能尚无 PTE。模拟器
改由 PLV0 执行第一个 `st.b` 时又产生 page fault，但 `kernel/src/mm/access.rs` 只允许处在
`access_user_memory()` 作用域内的内核代用户访问触发补页。旧调用没有设置该作用域，page-fault
handler 正确拒绝，exception table 把它转换成 `-1`，最终才显示 `(n=8)`。

当前单变量修复位于 `kernel/src/task/user.rs`：用户 ALE 的
`uctx.emulate_unaligned_at(BADV, BADI)` 由现有 `crate::mm::access_user_memory(|| ...)` 包裹。
合法 lazy page 可通过当前进程的 address space 补页后重试；无效/只读用户地址仍由
`unaligned.S` exception table 返回错误并发送 SIGBUS，不会把任意地址变成可访问。PLV0 内核地址
模拟路径没有改变。

### 20.3 当前调度修复为什么只删除这一处调用

`kernel/src/task/user.rs` 已删除每次用户态返回前的 `axtask::rebalance_current()`。没有把整个 SMP
负载放置删除，也没有引入固定分片：

- `vendor/axtask/src/api.rs::spawn_raw()` 仍调用 `select_run_queue()`，新任务按允许 CPU 集合进入
  当前最短 run queue；
- `vendor/axtask/src/run_queue.rs` 仍负责 run queue 选择和显式迁移后的入队；

- `kernel/src/task/rseq.rs::prepare_rseq()` 通过任务 `schedule_count` 观察真实调度/迁移，删除旧的

- `vendor/axtask/src/api.rs::rebalance_current()` 暂时保留为可显式调用的 API，但当前用户返回路径

这是一处单变量修复：A/B 的直接验收指标是新日志中 `rebalance-task` 数量必须为 0，而不是先

### 20.7 `CLOEXEC pipe` 实际是 Unix `SOCK_SEQPACKET`，单变量修复 socketpair 阻塞属性

20.6 中把故障暂归为 pipe FD nonblocking/close-reuse 的判断已被更精确的源码和真机证据覆盖。
[pipe 生命周期真机日志](../../hardware-ls2k1000la-20260809-pipe-wait-close-wake-wdt20m-smp2.log)
中，`rustfmt` 退出时两条写端都正常销毁，分别报告 `close_wakers=3`、`io_wakers=1`，父进程也已
继续进入正式 buildstorm；失败操作前没有 `MOSS_PIPE_READ_WOULD_BLOCK` 的 blocking-poll-return，
fanotify 路径也没有返回 `EAGAIN`。正式编译打印 7 条可识别的 `Compiling <crate>` 后，Cargo 仍在
约 626.4 秒由 `std/src/sys/process/unix/unix.rs:155` 报同一错误。各轮数量如下：

| 日志 | 可识别的正式 `Compiling <crate>` | 原始 `Compiling` 子串 | 结果 |
|---|---:|---:|---|
| 旧热路径 rebalance 真机 | 21 | 23 | Cargo worker panic，另有 2 条被串口内核日志截断而无 crate 名 |
| 去掉热路径 rebalance 真机 | 10 | 11 | 同一 panic，另有 1 条被截断 |
| pipe 生命周期真机 | 7 | 7 | 同一 panic |
| socketpair 最终地址修复真机 | 23 | 23 | 修复现场命中，跨过旧 panic 点，20 分钟内 panic 为 0 |
| QEMU pipe 生命周期基线 | 133 | 133 | `Finished release`，`BUILDSTORM_COMPILE ok=true` |

直接从比赛环境 `sdcard-la.img` 的固定 Rust 1.98 源码读取对应实现后，调用链已经确定：Linux 下
`Command::spawn` 在 `unix.rs` 创建的是
`Socket::new_pair(AF_UNIX, SOCK_SEQPACKET)`；标准库的 `Socket::new_pair` 调用
`socketpair(fam, ty | SOCK_CLOEXEC, 0, ...)`，没有请求 `SOCK_NONBLOCK`；第 155 行则是父进程从该
exec-status socket 阻塞读取。`CLOEXEC pipe` 只是标准库保留的历史错误文字，不代表 MOSS 的
`kernel/src/file/pipe.rs::Pipe`。MOSS 收到 `SOCK_SEQPACKET` 后走
`kernel/src/syscall/net/socket.rs::sys_socketpair()` → `DgramTransport::new_pair()`；它的
`GeneralOptions::recv_poller()` 只有在 `nonblock` 为 true 时才会把空队列的 `WouldBlock` 直接
返回用户态。

请求本身没有 `SOCK_NONBLOCK`，所以当前最小因果链是：固定 LoongArch nightly 在移动大的 Unix
socket aggregate 时偶发破坏其中 `GeneralOptions.nonblock: AtomicBool`（同类问题此前已经由
accepted socket 的 final-allocation 修复证实）→ 默认 false 变成 true → 父进程本应阻塞的
exec-status read 直接得到 `EAGAIN` → Rust 在 `unix.rs:155` panic。当前只修这一项：

- `sys_socketpair()` 先把两个完整 endpoint 放入最终 `Arc<Socket>`，再发布到 FD table；
- 在最终地址无条件写回调用者请求的 nonblocking 状态，包括最常见的 false，而不是只在请求
  `SOCK_NONBLOCK` 时写 true；
- 如果最终分配后的 blocking endpoint 在修复前已经读到 true，打印
  `MOSS_SOCKETPAIR_NONBLOCK_REPAIR`，记录 PID、socket type 和两端状态；
- pipe 生命周期诊断暂时保留用于排除回归，没有同时修改 `sys_close` 或 FD table，保证本轮 A/B
  仍是单变量实验。

[socketpair 修复静态检查](../../static-ls2k1000la-20260809-socketpair-final-nonblock-repair-wdt20m.log)
已 8/8 通过。待上板镜像

### 20.8 当前未完成不是 AHCI 卡死：板卡实际只运行在 500 MHz

最新日志中，正式编译最初并行启动 `compiler_builtins`、`core` 和 `libc` 等任务；其他短任务陆续
退出后，Task 501 `rustc` 从 uptime 437.391 秒持续运行到 watchdog deadline。该任务始终能返回
用户态、响应 timer tick 并被调度在 CPU1，CPU0 后期为空闲；所以这是仍在执行的单线程编译，不是
调度器静默卡死。按启动顺序判断 Task 501 很可能是 `core`，但日志没有记录完整 argv，因此只把
crate 对应关系作为推断，不作为修复依据。

硬件频率已经用手册、U-Boot 和 Linux 三方交叉确认：

| 证据 | CPU 频率 |
|---|---:|
| 《广东龙芯2K1000星云板用户手册 V1.2》规格表 | 800–1000 MHz |
| 手册 U-Boot 示例 | 800 MHz |
| 手册 10.5 节默认 `CORE_FREQ` 配置 | 900 MHz（1.05 V；1100 MHz 需 1.15 V） |
| 当前板 U-Boot | 500 MHz |
| 当前板 Linux `/proc/cpuinfo` 两个核心 | 500.00 MHz / 1000.00 BogoMIPS |

frequencies 均不存在，说明当前系统没有 cpufreq 驱动可以动态升频。手册明确说明频率由 U-Boot
源码 `include/configs/loongson_2k1000_dp.h` 中 `CORE_FREQ` 决定，修改后需要重新编译并烧录
U-Boot。MOSS 接管时看到的已经是 U-Boot 配好的 500 MHz，MOSS DT 和内核里也没有 CPU PLL 配置。

结论是：QEMU 基线有 12 个核心并在 376 秒完成，不能作为这块双核、500 MHz 真板的 20 分钟时限
目标；最新一轮已经证明 socketpair panic 消失，但低主频下冷编译 Rust `core` 仍可能超过剩余约
13 分钟。下一步应先在 Linux 上完成同一比赛环境的 500 MHz 实耗对照，再决定 20 分钟是否足够；
若确需恢复板卡标称性能，应按手册修改/烧录 U-Boot 到 800 或 900 MHz，并在改动前保存当前 SPI
镜像和确认供电电压，不能由 MOSS 内核盲写 PLL。

### 20.13 BSP2 U-Boot 的 RAM 链已经通过，前面的卡死来自装载地址和入口地址，不是 AHCI

20.12 末尾记录的初版链路判断还不完整。继续用异常寄存器、`bdinfo` 和逐阶段日志定位后，得到
两个互相独立、都发生在 Linux/AHCI 之前的问题：

1. 旧候选的 link/load address 是物理 `0x0ec00000`。factory U-Boot 运行时也占用这一带内存，
   因此把候选复制到这里会覆盖仍在执行复制和返回路径的 factory U-Boot。这个现象不是“BSP2
   U-Boot 本身启动慢”，也不能通过再等 35 秒解决。最终候选改为链接在物理 `0x0c000000`，其
   运行时 `bdinfo` 显示 `relocaddr=0x900000000dc00000`，不再与 factory 的活动映像碰撞。
2. legacy uImage header 的 entry 字段只有 32 bit，无法保存 cached DMW 地址
   `0x900000000c000000`。若让 `bootm` 自动执行，入口会被截成 `0x0c000000`，随即发生 TLB
   exception。最终流程是 `setenv autostart no`，只让 factory `bootm` 校验、复制并刷新 cache，
   返回提示符后再显式执行 `go 0x900000000c000000`。

### 20.14 串口传输失败是 BSP2 xyzModem 的块号边界问题，120 KiB 分段后稳定

板上没有建立可用的 TFTP 数据链，因此内核改用 CH340 串口 YMODEM。整文件在 460800 和
230400 baud 下都会在约 124/251 KiB 附近收到 NAK 或非法 ACK；把块放大到 240 KiB 仍会在单块
内部的同一边界失败。这是 BSP2 `xyzModem` 接收路径的块号边界行为，不是内核镜像损坏。

当前链路脚本 `scripts/run_ls2k1000_bsp2_chain.py` 只对传输做 120 KiB 分段，每段用新的
`loady` 会话装入连续 RAM，并逐段读取 U-Boot `filesize` 验证字节数；全部完成后把总长度恢复为
`0xa326d2`，最后由 `bootm` 对整份 legacy image 做数据 CRC。最终三轮 LSX 内核传输均完成 88/88

### 20.19 `sync + SysRq` 会留下 ext4 orphan 链，退出必须先 remount root 只读

buildstorm 本体通过后，第一轮收尾暴露了测试夹具问题，而不是 AHCI/编译失败：脚本先 `sync`，随后
直接写 `/proc/sysrq-trigger` 复位。`sync` 只保证脏页和日志提交，不负责像正常 shutdown 那样停止
写者、关闭文件和把根文件系统切成只读。Cargo 在构建中创建/删除大量临时 inode，因此复位后
`e2fsck -fn /dev/sda2` 报告 `corrupted orphan linked list` 并返回 4。

修复过程完整保留在
[sda2 修复日志](../../hardware-linux-ls2k1000la-20260811-sda2-post-buildstorm-repair.log)：停止 factory udev
的 private mount namespace、确认 `/dev/sda2` 未挂载后执行 `e2fsck -fy`，`repair_rc=1` 表示文件
系统已被修改；紧接着第二次 `e2fsck -fn` 五阶段全过，`verify_rc=0`，最终计数为
`96104/786432 files`、`2111713/3145728 blocks`。

当前 `scripts/run_ls2k1000_bsp2_chain.py` 的成功退出顺序已经固定为：

1. `swapoff` 并卸载 sda1；
2. 停止后台 watchdog pinger 并等待它退出；
3. `sync`；
4. `mount -o remount,ro /`，必须得到 `root_ro_rc=0`；
5. 才向 `/proc/sysrq-trigger` 写 `b`；
6. 若只读切换失败，不主动执行不安全复位，改由已启动的硬件 watchdog 兜底。

[新退出路径 smoke 日志](../../hardware-linux-ls2k1000la-20260811-linux612-root-ro-cleanup-smoke.log) 已打印
`Linux 6.12 ... smoke=PASS`、`EXT4-fs (sda2): re-mounted ... ro` 和 `root_ro_rc=0`，随后自动回到
factory Linux。复位后的[最终只读 fsck](../../hardware-linux-ls2k1000la-20260811-sda2-root-ro-cleanup-verify.log)
再次五阶段全过，`verify_rc=0`；说明新退出路径没有重新制造 orphan 链。

### 20.20 永久方案：新 6.12 默认启动，但旧 5.10 必须作为磁盘回退保留

当前稳定性已经足以进入“磁盘自主启动”阶段，但还不足以直接烧写 SPI。永久方案采用 A/B 而不是
删除旧内核：

1. sda1 保留原 `/boot/uImage`、factory Linux 和 SPI 备份，同时新增 `/boot/moss/`，存放经过哈希
   验证的 BSP2 RAM wrapper、6.12 LSX uImage、配置和校验清单；sda2 只存 12 GiB 比赛环境；
   `/swapfile-moss` 继续由新系统启动脚本启用。
2. 先构建“自主磁盘版”只读 BSP2 wrapper：factory U-Boot 只负责从 sda1 把 wrapper 装入已验证的
   `0x98000000`，wrapper 在 `0x0c000000` 启动后再从 sda1 加载 6.12，并以 `root=/dev/sda2`
   启动。该阶段不依赖主机 TFTP，也不改 SPI。
3. 第一次只提供 U-Boot 菜单/一次性命令选择新系统；完成连续冷启动、cagent、buildstorm、看门狗
   复位和 fsck 验收后，再把默认项指向新 6.12。旧 5.10 文件和原 factory boot command 始终保留，
   可从串口菜单回退。
4. 只有自主磁盘链稳定且验证 factory SPI 备份能够实际恢复，才评估是否烧写 BSP2 SPL/U-Boot。
   磁盘链已满足需求时，可以永久不刷 SPI，降低变砖风险。

截至本节，已完成的是 1 GiB+swap 的完整工作负载和安全退出验证；“把新系统设成上电默认项”尚未
执行。这个边界是有意保留：factory 固件仍错误宣称 2 GiB，直接覆盖旧 `/boot/uImage` 会同时失去
已知可工作的恢复 Linux，不符合用户明确要求的“旧内核不要删”。下一步只实现并验证 sda1 上并存的
自主磁盘 wrapper，然后再切默认启动项。

### 20.21 MOSS 1 GiB buildstorm：20 分钟改为滑动无进展租约，并接入 sda1 swapfile

前两轮 MOSS 内存修复已经排除了“仍按 2 GiB 分配”和“只管理到 632 MiB”这两个问题。多 bank
bitmap allocator 在真机可管理约 935 MiB，clean-only page-cache reclaim 和 16 MiB heap expansion
上限也把原先约 683 秒的失败点推迟到了 1119/1178 秒，但正式 buildstorm 仍以
`SIGBUS/OutOfMemory` 结束。最后一轮在 600 秒附近已经达到 `used=839 MiB`、匿名
`virt_mem=398 MiB`、page cache 243 MiB；Linux 6.12 的无 swap 对照又在 rustc anon RSS 721 MiB
时 OOM。因此下一步是补齐匿名页换出，不再继续调整零散阈值。

看门狗的 20 分钟含义已经固定为“连续无推进 20 分钟”，不是“从开机算满 20 分钟”：

- monitor 每秒统计用户任务数量、任务 ID 集合和累计 `schedule_count`；任何变化都把
  `last_progress_ns` 更新为当前时间；
- 启动、受控关机等显式里程碑也调用 `note_progress()` 顺延同一租约；
- 每 5 分钟同时打印总运行 `elapsed_s` 和连续无推进 `idle_s`，并附 build task、内存和 swap 统计；
- 只有 `now - last_progress >= 20 min` 才永久停喂；30 秒 LS2K 硬件 watchdog 随后自动复位；
- 正常 rustc 即使 40 多分钟才完成，只要仍在被调度，截止点会持续向后移动，不会在第 20 分钟被杀。

MOSS swap 复用 sda1 的 `/swapfile-moss`，不创建第三分区，也不改 sda2。启动 runner 先让仍拥有
ext4 的 factory Linux 执行 `filefrag -b4096 -v /swapfile-moss`，并同时读取 SATA sector size、sda1
起始 LBA 和文件字节数。只有 extent 逻辑页连续、物理/逻辑长度一致、总覆盖严格等于 2 GiB 时，
才把 `(logical_page, absolute_disk_lba, pages)` 注入 `/chosen`。MOSS 不解释或修改 sda1 inode/extent
元数据，只在 Linux 已停机后对已验证的数据块做 4 KiB raw AHCI I/O；logical page 0 永久保留 Linux
swap header，slots 从 1 开始。

第一轮 extent handoff 已留下明确的前置失败证据：15 个 extent 放在一条 U-Boot 命令时，factory
U-Boot 打印 `Too many args (max. 32)` 并进入 CPU exception，MOSS 尚未启动、磁盘也尚未写入。
修正后 runner 每个属性最多放 8 个 extent，并把 30 秒硬件 watchdog 的四条 MMIO 命令移到全部
TFTP/FDT 操作之前，后续即使固件命令异常也无需无限等待人工复位。修正版冷构建已通过：
`LS2K1000LA static checks passed: cpus=2 image=3883648 bytes`；真机 workload 结果尚待本节后续补录。

| `vendor/axdriver/src/lib.rs` | 仅 LS2K feature 导出 raw AHCI read/write/flush |
| `kernel/src/mm/aspace/backend/cow.rs` | 私有 4 KiB COW 页换出/换入、slot 生命周期、fork 引用、并发 fault 提交 |
| `kernel/src/mm/aspace/backend/mod.rs` | 分配前先回收 file cache，再在低水位触发当前进程匿名页换出 |
| `kernel/src/mm/aspace/mod.rs` | 只扫描 user/private/unlocked VMA；共享、locked 和 file folio 不换出 |
| `vendor/axfs/src/highlevel/file.rs` | 1 GiB 板低/目标水位提升至 192/256 MiB，先丢干净 file cache |
| `kernel/src/entry.rs`、`kernel/src/lib.rs` | 在首个用户地址空间建立前初始化 swap |
| `scripts/check_ls2k1000_static.sh` | 固化滑动租约、header 保留、extent 拆分和 TLB barrier 等静态约束 |

换出安全边界为：只接受 4 KiB、非 file-folio、frame refcount 恰为 1 的私有页；fork 共享页和已有
fault-plan pin 一律跳过。PTE 清除后先完成本地 page-table 修改和双核同步 TLB shootdown，之后才允许
AHCI 读取物理页；写盘成功才发布 swapped map 并释放 frame，I/O 失败则恢复原 PTE。换入先持有 slot
引用，在地址空间锁外完成磁盘读取，再用并发 PTE 提交重新核对 VMA/backend/slot；unmap、discard、
进程退出和 fork 均维护 slot 引用，避免提前复用。

这说明目标不是继续增大 swap 或微调水位，而是把回收器从“循环扫描”改成“工作集优先”。第二代
实现包含以下相互配合的结构性修改：

1. 每个私有 COW backend 增加 64-shard 软件工作集表；新分配页、COW 写时复制页和 swap-in 页都
   进入 120 秒活跃代。普通低水位回收跳过活跃代，避免刚换入就换出；真正分配失败时才允许越过
   该保护，保证不会为了保护热页而报假 OOM。
2. 地址空间回收不再每个 VMA 只取一个 128-page batch；它会多轮扫描直到达到本轮目标或确认已无
   可回收冷页。全局单轮上限从 4096 页提高为 8192 页，减少每释放 16 MiB 就立即重新进入回收的
   锯齿行为。
3. `RECLAIM_ACTIVE` 之外增加 wait queue：一个核心正在归还页时，另一个核心分配失败会等待该轮
   回收完成并重试，不能把“回收正在进行”误判成永久 OOM。
4. swapped map 中存在的 slot 必须成功增加引用；该不变量不再静默退化成 zero/file lazy fault，
   从而避免 slot 生命周期错误被伪装成合法缺页。

### 20.23 v5 越过 AHCI 饥饿断点；v6 用 PTE.D 二次机会替代固定时间猜测

v5 已在真机越过此前两个独立的固定失败点。它正常完成 AHCI initial recovery、cagent 和
buildstorm toolchain/minibuild；522.137 秒首次换出 8192 页时 `swap_in=0`，527.541 秒第二轮累计
换出 16384 页时 `swap_in` 仍为 0，且没有并发 ext4 admission timeout。v3 正是在第二轮后的
521 秒崩溃，因此这组结果证明稳定地址分配和 FIFO 仲裁都已命中各自问题，而不是仅靠延长超时。

v5 也暴露了固定 120 秒软件活跃窗的上限。600/900/1200 秒的结果为：

| 时刻 | swap used | 累计 out/in | rustc user/system ticks | I/O errors |
|---:|---:|---:|---:|---:|
| 600 s | 82 MiB | 49,152 / 28,054 | 7,166 / 17,155 | 0 |
| 900 s | 57 MiB | 90,112 / 74,895 | 20,325 / 34,009 | 0 |
| 1200 s | 246 MiB | 180,224 / 116,689 | 36,340 / 48,007 | 0 |

其中 816.56 秒时，早先 refault 页的 120 秒保护集中到期，swap 实占从上一轮约 119 MiB 降到约
45 MiB 后又换出 8192 页。这证明固定时间只是在延后错误选择，不能回答页面在保护期间是否真的
被访问。v5 虽然保持正确运行且 1200 秒 I/O 量低于第一代的 256,482/191,514，但还不能作为最终
内存策略。

v6 改成硬件反馈的二次机会，不再只凭时间猜测：LoongArch PTE 的 `W` 表示映射允许写，`D` 表示
当前翻译自上次清零后发生过写。主动回收第一次看到过期且 D=1 的匿名页时，只清 D、保留 W，并
完成双核 TLB shootdown；下一次真实写触发 PageModify，现有 COW fault 路径恢复 D 并把该页晋升。
经过 5 秒观察期仍保持 D=0 的页才进入换出。swap-in 是上一轮选择错误的直接 refault 证据，因此
该页永久退出主动回收集合；只有物理页分配真实失败时，`allow_recent` 强制路径才可以越过保护，
不会产生假 OOM。

为避免扫描本身占住地址空间锁，每次最多检查 8192 页；遥测增加 `swap_probes` 和
`swap_refaults`，真机可以直接核对 D 位采样量和被保护的 refault 数。Generic PTE 和多级页表只
增加可选 `clear_dirty() -> Option<bool>` 能力，非 LoongArch 架构默认不支持、不改变原行为；I/O
失败恢复使用 VMA 的真实权限，不会把临时 D=0 错当成永久只读。

v6 已通过全部 LS2K 静态约束、两核/1 GiB 冷构建和现有外设状态机测试。由于线程 `stime` 会把
阻塞在 syscall 内的时间计入，不能直接代表 CPU 利用率，本版又在每核 idle task 的 WFI 前后累计
真实空闲纳秒；5 分钟遥测将分别打印 CPU0/CPU1 的区间 `busy_percent` 和 `idle_ms`，可直接区分
“双核计算”和“一核计算、一核等待换页”。同一计数器也修正滑动租约：任务创建/退出或每秒真实
非空闲 CPU 达到单核容量的 10% 才续租，cargo 的周期性 futex 空唤醒只保留为诊断计数，不再能
让已经停滞的任务无限续期。build task 快照也保留活动 syscall 的前三个原始参数；例如 `write(64)`
会直接显示 fd/buffer/length，从而区分 pipe 背压和普通文件写回。该内存架构随后与 20.24 的终端
信号重构合并为最终 v6；最终镜像名称、哈希和真机状态以 20.24 为准。

### 20.24 终端信号链路重构：`Ctrl+C` 已在真机形成完整闭环

v5 在第 93 个 `Compiling` 长时间无真实 CPU 推进时，串口输入 `Ctrl+C` 没有任何效果。检查后确认
不是一个“缺少 Ctrl+C 特判”的局部问题，而是接收中断、异步等待、行规程和作业控制四层没有形成
闭环：NS16550 在早期启动后没有在 tty reader/waker 就绪时启用 RX 中断；IRQ event waker 是永久
挂载而不是消费后屏蔽、下次等待前重臂；行规程把 `ISIG` 错误地依赖 `ICANON`，并会把信号控制字符
继续送入输入队列；`TIOCSPGRP` 忽略用户传入的 pgid，始终选择调用者自身。任意一层失效都会让
终端看似正常输出、却不能中断前台编译。

本轮按整条链路重构，而不是只在 buildstorm 脚本里捕获字符：

1. `axplat`/`axhal` 增加显式、幂等的 `enable_rx_interrupt()`；LS2K1000 的 NS16550 仍以 `IER=0`
   完成早期启动，只有 ntty reader 先注册 waker 后才打开 RX-data-available 中断，消除“中断早于
   等待对象发布”的竞态。
2. `axtask` 的 event-waker 改成 one-shot：IRQ 后先屏蔽源再唤醒 PollSet，每次消费者重新等待时
   才重臂；首次注册还安装 hook-only marker handler，UART 字节不会再被平台误报为 unhandled IRQ。
3. n_tty 行规程按 termios 语义独立处理 `ISIG`：VINTR/VQUIT/VSUSP 分别产生
   SIGINT/SIGQUIT/SIGTSTP，控制字符被消费，除 `NOFLSH` 外清空输入；禁用值 0 不再误匹配普通 NUL。
4. `TIOCSPGRP` 现在真正读取用户 pgid、查找进程组并校验同一 session；进程组送信即使某个成员已
   退出返回 ESRCH，也继续向其余成员投递。

启用 RX 后暴露出的两个启动期问题也一起修掉。第一版冷启动在 `MOSS_MEMORY` 后被早期 30 秒看门狗
复位，因此 axruntime 在 allocator、MMU、platform、scheduler、IRQ、devices、SMP、constructors 和

[smoke-v1](../../hardware-ls2k1000la-20260811-v6-tty-signal-smoke.log) 和
[smoke-v2](../../hardware-ls2k1000la-20260811-v6-tty-signal-smoke-v2.log)，不能把失败记录删除后当作未发生。

最终 [smoke-v3](../../hardware-ls2k1000la-20260811-v6-tty-signal-smoke-v3.log) 给出了真机闭环证据：

### 20.25 v6 压力闭环否决同步逐页回收；v8 改为后台补水并补齐多线程信号唤醒

最终 v6 的完整长跑没有复现 AHCI 错误或 OOM，但性能数据否决了它作为可用方案。完整 buildstorm
进入第一个 arceos-helloworld 后出现 23 条 `Compiling`；300 秒时 CPU0/CPU1 区间利用率为
73.8%/34.7%，到 600 秒后变为约 94--99%/0.1%，说明标准库编译进入单 rustc 热点。真正的问题在
900 秒后：可用内存每下降一页就从分配线程同步进入回收，回收批次长期只有 1--3 页，而每批又打印
一条 `MOSS_SWAP reclaim`。1200 到 1500 秒间 rustc 的 user ticks 仅从 31,995 增至 32,339，system
ticks 却从 75,274 增至 104,990；CPU0 1500 秒区间利用率 98.7%，但约 300 秒只获得 3.44 秒用户态。
这不是“Cargo 没输出”的猜测，而是同步扫描、PTE.D 探测、小批 AHCI I/O 和串口 warn 把编译线程
变成内核活锁式慢进展。1500 秒时仍只有 23 条 `Compiling`，swap out/in 为
169,716/126,147，`swap_io_errors=0`。

压力现场也补充了 20.24 smoke 未覆盖的多线程信号问题。向 UART 真正写入 `0x03` 后，1822.940 秒
立即打印 `MOSS_TTY_SIGNAL signo=SIGINT foreground_pgid=10` 和 `^C`，证明 RX IRQ、行规程和进程组
投递仍然有效；但 rustc 换页线程继续运行。进程级 signal manager 当时只返回第一个未屏蔽 tid 供
内核唤醒；该 tid 若正与线程退出/任务表清理竞态，`get_task(tid)` 失败后不会再尝试同进程的其他
线程。修复后信号在 process pending queue 中仍只入队一次，但返回并唤醒全部未屏蔽 tid，最终仍
只有一个线程能 dequeue，消除了 stale-first-thread 丢唤醒；每个终端目标进程会打印
`MOSS_TTY_SIGNAL_DELIVERY ... interrupted_threads=N`。watchdog 的 build task 快照也新增 pgrp，
后续可直接核对 cargo/rustc 是否仍属于 tty 前台组。

v8 的内存策略不再由每个缺页线程维护高水位：

1. 低于 192 MiB 时只把当前地址空间去重后放入队列；单一 kernel worker 每次最多回收 2048 页，
   每批释放地址空间锁，并持续补到 256 MiB。
2. 一轮只完成 PTE.D 清零、尚无候选时，worker 等待 5 秒观察窗再扫；锁冲突只等 10 ms。普通分配
   不再重复扫描，也不再为每个小批打印 warn。
3. 只有可用内存跌到 64 MiB 紧急水位，或物理页分配真实失败，才允许当前线程越过工作集保护做
