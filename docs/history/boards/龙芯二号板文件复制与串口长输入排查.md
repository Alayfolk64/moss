# LS2K1000LA 复制与串口长输入排查

更新日期：2026-08-12

本文用于排查两类容易混淆的问题：

1. 从宿主机向串口终端粘贴一段较长的命令或文本，板上收到的内容缺字、截断或变形；
2. 在 MOSS 中使用 `cp` 复制文件，命令报错或复制后的文件不完整。

两类问题经过的路径不同，必须分开检查。以下命令均按“宿主机”和“板子 MOSS”标明，
每次只执行一条。

## 1. 当前已确认的现场与代码事实

- 当前宿主机使用 `picocom -b 115200 /dev/ttyUSB0` 操作 MOSS。
- LS2K1000LA 串口驱动已由“IRQ 只唤醒任务”改为“IRQ 立即清空 NS16550 FIFO”，收到的数据先
  进入 8 KiB 软件 RX 环，再唤醒 TTY。代码见
  `vendor/axplat-loongarch64-ls2k1000/src/console.rs`。
- TTY 每轮使用 80 字节暂存数组，已完成的一行也先进入 80 字节 ring buffer；但正在编辑的
  canonical line 使用 `Vec<u8>`，会按需增长。因此当前实现不是“命令最多只能有 80 个字符”。
  代码见 `kernel/src/pseudofs/dev/tty/terminal/ldisc.rs`。
- TTY 收到字符后仍会逐字回显，但回显和 shell 行编辑在任务上下文执行，不再阻塞硬件 FIFO
  搬运。公共无堆分配环形缓冲见 `vendor/axplat/src/console_rx.rs`。
- 自动 runner 已取消每字符等待 10 ms 的 `write_paced()`；`shell_command()` 现在一次写入整行，
  同时保留对 BusyBox `ash` ANSI 光标位置查询的响应。
- VisionFive 2 使用同一个 8 KiB RX 环和平台托管 waker，避免旧的通用 one-shot IRQ hook 在每次
  唤醒后屏蔽 PLIC UART source。VF2 镜像已构建通过，仍需 VF2 实板复测。

## 2. 先判断是哪一类复制

如果问题发生在把宿主机剪贴板内容粘贴进 `picocom` 时，执行第 3 节。

如果是在板上输入 `cp` 后报错，执行第 4 节。

如果要把源码、脚本或镜像从宿主机放到板上，不应通过串口粘贴文件内容，直接使用第 5 节的
网络传输。

## 3. 串口长输入排查

### 3.1 宿主机确认串口程序

在宿主机执行：

```bash
ps
```

`ps` 显示当前终端启动的进程。正常情况下应看到 `picocom`。

如果还没有打开串口，在宿主机执行：

```bash
picocom -b 115200 /dev/ttyUSB0
```

`-b 115200` 设置波特率；`/dev/ttyUSB0` 是当前 CH340 串口设备。

### 3.2 板子确认当前目录

在板子 MOSS 执行：

```bash
pwd
```

`pwd` 显示当前目录。提示符固定显示 `starry:~#`，不能依靠提示符判断目录。

回到 root 用户主目录：

```bash
cd /root
```

`cd` 切换目录；`/root` 是已有现场测试文件所在的位置。

### 3.3 对比短命令与长粘贴

先手工输入一条短命令：

```bash
echo short-input-ok
```

如果完整输出 `short-input-ok`，说明串口基本收发和 shell 都在工作。

然后粘贴实际会出问题的那一整行，但先不要按 Enter，观察屏幕上的回显：

- 回显已经缺字或字符顺序异常：问题位于串口 RX、IRQ 唤醒或 TTY 消费路径，不是 `cp`；
- 回显完整，按 Enter 后程序才报错：保存完整错误，转到第 4 节检查文件系统或具体命令；
- 只有多行一起粘贴才出错：逐行输入能通过只是临时规避，仍按串口突发输入问题记录。

按 `Ctrl+C` 清除这条尚未执行的测试输入。当前 MOSS 中 `Ctrl+C` 向前台进程组发送 `SIGINT`，
不会直接重启板子。

### 3.4 当前安全用法

普通单行命令可以直接粘贴；一次粘贴多行时，仍应等上一行执行结束再发下一行。不要把脚本正文、
源码或大段配置当作串口文件传输协议，文件应使用第 5 节的网络方法。

若短命令也开始缺字，先退出 `picocom`：依次按 `Ctrl+A`、`Ctrl+X`。然后重新打开：

```bash
picocom -b 115200 /dev/ttyUSB0
```

重新打开仍丢字时，保留最短复现文本和回显，不要立即把问题归因于磁盘。

## 4. 板上文件复制排查

以下命令都在板子 MOSS 执行。

### 4.1 查看磁盘空间

```bash
df -h /
```

`df` 查看文件系统容量；`-h` 使用 GiB、MiB 等可读单位；`/` 指当前挂载为 MOSS 根的
`/dev/sda3`。重点看 `Avail`，不要把它和内存混为一谈。

### 4.2 查看内存与 swap

```bash
free -h
```

`free` 查看 RAM 和 swap；`-h` 使用可读单位。文件复制通常不要求空闲内存等于文件大小，
但持续 OOM 会导致进程被杀死。

### 4.3 执行复制并保留原始错误

例如复制现有的小文件：

```bash
cd /root
```

```bash
cp rustc-help.txt /tmp
```

`cp` 复制文件；第一个路径是源文件，`/tmp` 是目标目录。命令没有输出通常表示成功。

紧接着查看退出状态：

```bash
echo $?
```

`0` 表示成功；非 `0` 表示失败。不要添加隐藏错误输出的重定向。

检查目标是否存在：

```bash
ls -l /tmp/rustc-help.txt
```

`-l` 显示文件大小等详细信息。

分别计算源文件和目标文件的摘要：

```bash
sha256sum /root/rustc-help.txt
```

```bash
sha256sum /tmp/rustc-help.txt
```

两行摘要完全相同，才能确认内容一致。

### 4.4 根据原始错误继续定位

- `No space left on device`：先处理 `/dev/sda3` 空间，不是串口问题；
- `Input/output error`：立即停止反复写入，保存 `dmesg` 中的 AHCI、SATA、ext4 错误；
- `Killed` 或 OOM 信息：检查 `free -h`，再检查 swap 是否工作；
- `Read-only file system`：文件系统已经只读，先保存错误，不要继续强行写入；
- `Permission denied`：检查目标目录权限；当前 root shell 通常不应被普通权限阻止。

发生 `Input/output error` 后执行：

```bash
dmesg
```

`dmesg` 显示内核日志。保留从第一次 `error`、`timeout`、`AHCI`、`SATA` 或 `EXT4` 开始的
完整串口输出，不要只截最后一行。

## 5. 宿主机向 MOSS 传文件的稳定方法

串口适合输入短命令，不适合传文件。当前板子和宿主机已经使用 `192.168.88.2` 与
`192.168.88.1` 直连，可用 HTTP 传输。

### 5.1 宿主机提供文件

在宿主机进入待传文件所在目录：

```bash
cd /home/wuxun/Projects/moss
```

该目录是当前 MOSS 仓库。然后执行：

```bash
python3 -m http.server 8000
```

该命令临时提供当前目录中的文件；`8000` 是端口。传输结束后按 `Ctrl+C` 停止服务。

### 5.2 板子下载文件

在板子 MOSS 执行：

```bash
cd /root
```

```bash
wget 'http://192.168.88.1:8000/docs/history/boards/龙芯二号板文件复制与串口长输入排查.md'
```

这条命令下载本文档，并保存为 `/root/龙芯二号板文件复制与串口长输入排查.md`。验证这条链路后，
只需把 URL 最后的路径换成真正需要传输的文件。

下载结束后执行：

```bash
sync
```

`sync` 把尚在缓存中的文件数据刷新到磁盘。

最后在宿主机执行：

```bash
sha256sum 'docs/history/boards/龙芯二号板文件复制与串口长输入排查.md'
```

在板子执行：

```bash
sha256sum '龙芯二号板文件复制与串口长输入排查.md'
```

两端摘要相同才算传输完整。

## 6. 排查记录格式

每次问题只记录以下五项：

1. 问题发生在串口粘贴还是板上 `cp`；
2. 输入的原始命令；
3. 屏幕回显是否在按 Enter 前就已经缺字；
4. `echo $?`、`df -h /`、`free -h` 的原始输出；
5. 若有 I/O 错误，保存完整 `dmesg`。

有这五项后才能判断下一步是扩充串口 RX 缓冲和减少回显阻塞，还是修复 AHCI/ext4、空间或
内存策略。

## 7. 2026-08-12 真机复现结果

修复前在 `moss-onsite-final.bin`、115200 波特率、MOSS `starry:~#` 上完成 A/B 对照。
宿主机将完整命令一次写入串口，模拟终端粘贴一整行。

### 7.1 最短稳定复现

TTY 默认开启回显时，粘贴：

```bash
echo T0016abcdefghijZ
```

这条命令正文只有 21 个可见字符，加 Enter 共发送 22 字节。预期输出是
`T0016abcdefghijZ`，真机实际只执行了 `ec`：

```text
ec
/bin/sh: ec: not found
starry:~# o T0016abcdefgh
```

作为基线，正文 13 个可见字符、加 Enter 共 14 字节的命令完整通过。复测恢复回显后的
22 字节命令，仍得到相同失败，因此不是偶发现象。

### 7.2 关闭回显的对照

在板子执行：

```bash
stty -echo
```

`stty` 修改当前 TTY；`-echo` 关闭板端逐字符回显。关闭后输入内容不会显示，这是预期行为。

在回显关闭时，宿主机仍然一次性突发发送完整命令，结果如下：

| payload 字节 | 完整命令字节 | 结果 |
|---:|---:|---|
| 16 | 22 | 通过 |
| 64 | 70 | 通过 |
| 256 | 262 | 通过 |
| 512 | 518 | 通过 |

测试结束后恢复回显：

```bash
stty echo
```

`echo` 重新开启板端逐字符回显。本轮已经执行该命令，当前板端回显已恢复。

### 7.3 节流对照

保持回显开启，对同一条 262 字节命令逐字符发送：

| 每字符等待 | 结果 |
|---:|---|
| 2 ms | 失败，内容缺失 |
| 5 ms | 失败，内容缺失 |
| 10 ms | 失败，内容缺失 |
| 20 ms | 通过 |

因此修复前 runner 使用的固定 10 ms/字符对更长单行并不充分。20 ms/字符只能作为临时规避，
不能代替内核修复；修复后该节流代码已经删除。

### 7.4 已确认的根因链

这次 A/B 已排除磁盘、`cp`、shell 行长度和 80 字节 canonical line 上限。真实路径是：

1. 宿主机一次性把整行送入 NS16550；
2. RX IRQ 只唤醒 `tty-reader` 任务，没有在硬件中断处理阶段把 FIFO 立即搬入软件 RX ring；
3. `InputReader::poll()` 每取一个字符就在 `term.echo()` 分支同步调用 `output_char()`；
4. `output_char()` 最终进入 LS2K1000 `ConsoleIf::write_bytes()`；
5. `Ns16550::put()` 对每个回显字符轮询等待 TX holding register 空闲；
6. `tty-reader` 等待并发送回显期间不能继续清空 RX FIFO，后续粘贴字节发生丢失。

关闭 `echo` 后 518 字节突发完整通过，是“同步回显阻塞 RX 消费”的直接真机证据。80 字节
TTY 暂存和队列会影响长行如何分批处理，但不是本次 22 字节即失败的直接上限。

仅扩大 TTY 的 80 字节 buffer，不能消除 IRQ 调度前和逐字符回显期间的硬件 FIFO 溢出。

### 7.5 已实施的修复

本轮没有重写整套 TTY，而是按 Linux 8250 驱动的职责边界重构平台串口 RX：

1. `vendor/axplat/src/console_rx.rs` 新增公共、无堆分配的 8 KiB RX 环，保存软件丢弃计数、
   UART 硬件 overrun 计数和当前 TTY waker；
2. `ConsoleIf` 新增 `register_rx_waker()`。LS2K 和 VF2 返回“平台托管”，其他平台仍保留原来的
   通用 one-shot IRQ waker；
3. LS2K 和 VF2 都先注册真实 UART handler，再开启 device RX interrupt；handler 每轮最多抽取
   256 字节，先入软件环，释放锁后再唤醒 TTY；
4. NS16550 FIFO 在早期初始化时启用并清空，触发阈值设为 1 字节；
5. canonical、`Ctrl+C` 信号和回显仍由 TTY 任务处理，IRQ 中不做打印、分配或 shell 工作；
6. runner 删除固定逐字节节流，恢复一次 `serial.write()` 发送完整 shell 命令。

Linux 的对应原则是 `serial8250_rx_chars()` 在硬中断中有界地清空 UART，再把字节推入 TTY
缓冲；本实现复用 MOSS 现有 TTY，只补齐缺失的平台 RX 层。

### 7.6 修复后实板验收

验收镜像为 `moss-2k1000la-shell.bin`，SHA-256：

```text
be13cf02173a7fa1dea41daf287d53b1c858003bb57a3545efed099253c2e2c9
```

镜像从 `/dev/sda3` 启动，保持 TTY 回显开启。宿主机对每条测试使用一次 `serial.write()`，没有
逐字符等待：

| 完整单次写入 | 结果 |
|---:|---|
| 22 字节 | 原最短稳定复现命令完整回显并输出正确结果 |
| 70 字节 | 完成标记正确，命令完整执行 |
| 262 字节 | 完成标记正确，命令完整执行 |
| 518 字节 | 完成标记正确，命令完整执行 |

这已经覆盖并消除了修复前“14 字节通过、22 字节稳定截断”的故障。1024 字节交互行会进入
BusyBox `ash` 的超长行重绘慢路径，30 秒内没有作为通过项；此时 `Ctrl+C` 仍能立即清行并返回
提示符。它不能用于反证 UART 丢字，也不应作为文件传输方式。普通命令验收上限按已通过的
518 字节记录，更大的文本用 HTTP、TFTP 或文件复制。

宿主机检查结果：公共 RX 环 3 个测试通过；LS2K 完整 7 阶段静态检查通过，生产和交互镜像
均为 6,402,688 字节；`make kernel-vf2` 通过。VF2 本轮没有连接实板，所以只记录构建通过，
不写“VF2 实板已修复”的结论。
