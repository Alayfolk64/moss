# MOSS 现场赛应用适配、排障与调试总手册

更新日期：2026-08-19

当前代码分支：`dev`；历史证据以提交 `a67688d7` 为起点，并包含本轮双板网段与部署流程整理。
适用平台：QEMU RISC-V64、QEMU LoongArch64、VisionFive 2、LS2K1000LA。

本文不是一份“所有软件都永远通过”的宣传材料，而是一份现场使用的工程手册。它把当前代码、现有
文档、Git 全历史、保存下来的日志和本轮实板串口记录放到一条因果链中。每一项都会区分：在哪个平台、
哪个提交、哪个根文件系统上通过；哪些只是历史结果；哪些当前没有重跑；哪些明确失败或被安全放弃。

## 0. 先看这里：现场五分钟判断

遇到问题时不要先改代码，也不要先怀疑“镜像坏了”。按下面顺序做，通常五分钟内就能知道问题属于哪一层。

```sh
uname -a
cat /etc/os-release
echo "$PATH"
mount
df -h
free -h
ip addr
ip route
cat /etc/resolv.conf
date -u
```

这组命令依次确认：架构和内核、Alpine/Debian、命令搜索路径、根文件系统、空间、内存、网卡、路由、
DNS 和系统时间。软件不存在时先运行：

```sh
command -v python3
command -v gcc
command -v redis-server
```

`command -v` 没有输出，表示当前根文件系统里没有这个命令，或者它不在 `PATH`。它不表示内核损坏。

网络问题按四层检查：

```sh
ping -c 3 192.168.88.1
ping -c 3 223.5.5.5
ping -c 3 pypi.org
wget -O /dev/null https://pypi.org/
```

- 网关不通：先查网卡、地址、掩码、路由和宿主直连网口。
- 网关通，公网 IP 不通：先查宿主转发、NAT、防火墙或比赛网络出口。
- 公网 IP 通，域名不通：查 `/etc/resolv.conf`。
- 域名和 ping 都通，HTTPS 不通：查 TCP、系统时间、CA、TLS 和代理；不能再只归因于 DNS。

程序卡住时，先另开串口或 QEMU 终端检查：

```sh
ps
cat /proc/meminfo
cat /proc/interrupts
dmesg
```

若没有第二终端，先等当前命令的明确超时；需要中断时只按一次 `Ctrl+C`。不要连续粘贴命令，因为串口
输入、程序输出和 shell 回显会混在一起，容易把测试工具问题误判成内核问题。

### 0.1 本文的证据标签

| 标签 | 含义 |
| --- | --- |
| 当前实测 | 在当前 `dev` 或本轮实板镜像上取得了原始输出 |
| 历史实测 | 某个历史提交和明确平台上通过，但当前 HEAD 没有完整重跑 |
| QEMU 实测 | 只证明对应 QEMU 架构，不自动代表实板 |
| 实板实测 | 在 VF2 或 LS2K1000LA 上运行过真实命令 |
| 构建通过 | 只证明编译和产物检查，不代表目标启动 |
| 文档声明 | 仓库历史中有说明，但没有足够的原始验收日志 |
| 未通过 | 已经有明确失败原文 |
| 安全放弃 | 为避免人工复位、文件系统损坏或无限活锁，停止该实板路径 |

历史文档曾把大量原始日志放在 `tmp/`，这些日志没有全部进入 Git。本文能从历史报告确认的内容写成
“历史实测”；只有路径、没有原文的内容只记录路径，不伪造输出。以后新增日志统一放在仓库的 `tmp/`
目录，不放到系统 `/tmp`。

### 0.2 最重要的定位链：从第一条错误找到源码

现场最容易浪费时间的做法，是看到最后一个崩溃函数就立刻修改它。正确顺序是先保存现场，再区分
“最早制造损坏的位置”和“最后发现损坏的位置”。最快可执行的链条是：

```text
固定镜像和日志
  → 取第一条异常的 PC、故障地址和异常类型
  → 确认异常来自用户态还是内核态
  → 找到与运行镜像完全对应的带符号 ELF
  → GDB 查函数，反汇编故障点前后指令
  → 用寄存器算出指令实际访问的地址
  → 沿函数和数据所有权向上找“谁制造了错误状态”
  → 写最小探针，并在 Linux 上跑同一输入
  → 只修改共同语义所在的函数
  → 单元测试、双 QEMU、相关实板逐层回归
```

#### 0.2.1 第一步只保存证据，不重启、不重编

先记录：

```sh
git rev-parse HEAD
sha256sum kernel-rv kernel-la 2>/dev/null
date -u
```

再从串口日志保存下面字段：

```text
第一条 error/warn/panic 的完整上下文
PC：RISC-V 的 sepc，LoongArch 的 ERA
故障地址：stval 或 BADV
故障指令：LoongArch 的 BADI；若为 0 也要原样记录
异常类型：page fault、SIGILL、SIGBUS、breakpoint、timeout
所有通用寄存器
backtrace
运行的内核、根文件系统、CPU 数和内存
```

不要只截图最后一屏。内存已被破坏时，最后可能死在 allocator、调度器或日志锁中；它们可能只是第一个
碰到坏指针的受害者。先在日志里找第一处异常：

```sh
rg -n -m 1 'Page Fault|SIGILL|SIGBUS|panicked|ERROR|WARN|timeout' tmp/run.log
rg -n -C 20 'Page Fault|SIGILL|SIGBUS|panicked' tmp/run.log
```

第一条命令找最早行号，第二条看上下文。没有保存原始日志时，不要用一次新运行的输出替代旧现场，二者
应分别编号。

#### 0.2.2 第二步确认 ELF，错一个字节都不能拿来定位

本仓库的 `kernel-rv`、`kernel-la` 可能是启动包装文件；它们不是最适合还原 Rust 源码的 ELF。现场
QEMU shell 构建对应的符号文件通常在：

```text
build/site-rv/moss-dev_riscv64-qemu-virt.elf
build/site-la/moss-dev_loongarch64-qemu-virt.elf
```

仓库目录名变化时前缀会变化，实际用下面命令寻找：

```sh
find build/site-rv build/site-la -maxdepth 1 -name '*.elf' -type f
file build/site-rv/*.elf
file build/site-la/*.elf
```

必须保证符号 ELF 和运行内核来自同一次构建。最可靠的方法是在每次保存故障时一起保存并计算哈希：

```sh
mkdir -p tmp/repro-01
cp build/site-rv/*.elf tmp/repro-01/
cp build/site-rv/kernel-rv tmp/repro-01/
sha256sum tmp/repro-01/* > tmp/repro-01/SHA256SUMS
```

如果当时没有保存 ELF：

1. 先找构建目录是否还在；
2. 再确认 Git 提交、配置和工具链完全相同；
3. 用相同配置重新生成带 DWARF 的镜像并重新复现；
4. 不要拿当前新编的 ELF 去解释旧 PC，因为链接地址可能已改变。

现场目标可用 `DWARF=y` 保留调试信息：

```sh
make DWARF=y site-rv
make DWARF=y site-la
```

这两个目标会自动启动 QEMU；保存 ELF 后按 `Ctrl+A`、`X` 退出。不能把 `build/kernel-rv` 的初赛/决赛
ELF 用于解释 `site-rv`，也不能把 QEMU ELF 用于解释 VF2 或 LS2K 实板内核。

#### 0.2.3 第三步：先用 GDB，三条命令定位函数和指令

假设日志给出的内核 PC 是 `0xffffffc0803f4f24`：

```sh
gdb-multiarch path/to/moss.elf
```

GDB 中：

```gdb
set pagination off
info symbol 0xffffffc0803f4f24
info line *0xffffffc0803f4f24
x/12i 0xffffffc0803f4f0c
list *0xffffffc0803f4f24
```

这些命令分别回答：

- PC 属于哪个函数以及函数内偏移；
- 对应哪个源文件、哪一行；
- 故障前后执行了哪些指令；
- DWARF 能否还原附近源码。

如果程序正在 QEMU 中运行，连接 stub 后再看寄存器：

```gdb
target remote 127.0.0.1:1234
info registers
x/12i $pc-16
bt
```

不要只看 `bt`。优化后的 Rust/C 可能内联，栈也可能已经损坏；“PC 对应的真实机器指令 + 指令使用的
寄存器”通常更可靠。

#### 0.2.4 第四步：不用 GDB 也能反汇编

浏览整个 ELF：

```sh
rust-objdump -d -C path/to/moss.elf | less
```

在 `less` 中输入 `/函数名` 搜索，`n` 找下一处，`q` 退出。只看 PC 附近时：

```sh
rust-objdump -d -C \
  --start-address=0xffffffc0803f4ee0 \
  --stop-address=0xffffffc0803f4f40 \
  path/to/moss.elf
```

也可用 LLVM：

```sh
llvm-objdump -d --demangle path/to/moss.elf | less
llvm-readelf -h -S -s path/to/moss.elf | less
```

工具用途要分清：

| 工具 | 最快回答的问题 |
| --- | --- |
| `file`、`readelf -h` | ELF 是什么架构，是否拿错文件 |
| `readelf -l` | 解释器、加载段、虚拟地址 |
| `readelf -A` | 二进制声明了哪些 ISA 扩展 |
| `nm -n` | 地址附近有哪些按地址排序的符号 |
| `gdb info symbol` | 一个 PC 属于哪个函数 |
| `gdb info line` | 一个 PC 对应哪一源码行 |
| `objdump -d` | CPU 实际执行了什么指令 |
| `objdump -S` | 有 DWARF 时把源码和汇编交错显示 |

`addr2line` 可以一条命令批量转换地址：

```sh
addr2line -C -f -i -e path/to/moss.elf \
  0xffffffc0803f4f24 0xffffffc0803f4ef2
```

若宿主 `addr2line` 不认识目标架构，改用 `gdb-multiarch` 的 `info line *地址`，不要通过强行减一个猜测
偏移来得到“看起来合理”的源码行。

#### 0.2.5 第五步：从汇编计算真正访问的地址

反汇编不是为了截图，而是要把寄存器代入指令。RISC-V 例子：

```asm
ld a1, 648(a2)
```

若日志中 `a2 = 0xffffffc0d1d28c10`，则实际读取地址是：

```text
0xffffffc0d1d28c10 + 648 = 0xffffffc0d1d28e98
```

再问三个问题：

1. 该地址在用户空间、内核映射还是 MMIO？
2. 它应由哪张页表映射，权限应该是什么？
3. 基址寄存器为什么会得到这个值，是对象已释放、索引越界，还是 TLB/PTE 已过期？

LoongArch 未对齐异常还要同时看 `ERA`、`BADV`、`BADI`。`BADI=0` 不表示“没有故障指令”；LA264
可能在地址未对齐异常中把 BADI 留为 0，此时当前代码会从 `ERA` 读取指令字。然后按 load/store 宽度、
基址和索引寄存器重新计算有效地址。历史上只相信 BADV 的第一次修复仍失败，就是靠这一步发现索引式
`stx.d` 的真实地址计算与原假设不一致。

#### 0.2.6 用户程序崩溃：先处理 PIE 和动态库偏移

用户态 `SIGILL`/`SIGBUS` 的 PC 不能直接拿内核 ELF 查询。先确定命令实际来自哪个文件：

```sh
command -v rustc
file "$(command -v rustc)"
readelf -h -l -A "$(command -v rustc)"
```

非 PIE 可直接：

```sh
gdb "$(command -v rustc)"
```

若是 PIE 或 PC 落在共享库，必须保存进程映射：

```sh
cat /proc/PID/maps
```

先找到覆盖 PC 的映射行，再按下式求 ELF 内偏移：

```text
ELF offset = runtime PC - mapping start + mapping file offset
```

把这个 offset 交给对应的主程序或 `.so` 做 `info symbol`/反汇编。找错动态库时，即使工具返回了函数名，
结论也没有意义。若目标程序很快退出，可在原生 GDB 中 `start` 后读取 `info proc mappings`。

#### 0.2.7 没有崩溃、只是返回错 errno：用最小 C 探针

`ip`、APT、nginx、OpenSSH 都可能只是因一个 syscall 语义不同而退出。若目标有 `strace`，先用：

```sh
strace -f -tt -s 128 -o trace.log command arguments
tail -80 trace.log
```

没有 `strace` 时，不要给整个应用加日志。写一个只调用目标 syscall 的几十行 C 探针，打印：

```text
返回值、errno、输出结构体、长度字段、poll 事件、调用前后 fd flags
```

同一个探针分别在 Linux 和 MOSS 运行。差异出现后，按 syscall 名快速找入口：

```sh
rg -n 'pub fn sys_recvmsg|pub fn sys_select|pub fn sys_lseek' kernel/src
rg -n 'impl Pollable|fn poll|fn recv' vendor/axnet kernel/src
```

接着沿真实调用链读代码，不要全仓库盲搜应用名。例如 `ip addr` 的主链是：

```text
sys_sendmsg
  → NetlinkSocket::send/enqueue_request
  → response queue
  → Pollable::poll
  → sys_recvmsg/recv_impl
  → sockaddr_nl 写回用户空间
```

探针若证明 `recvmsg` 数据正确、只有 `msg_name` 错，修改点就应在地址 copyout；不应重写整套 netlink，
也不应在检测到进程名 `ip` 时返回特制数据。

#### 0.2.8 卡死：先证明在等什么

QEMU 卡死时用 GDB：

```gdb
info threads
thread apply all bt 20
```

判读顺序：

1. 所有 CPU 是否停在同一把锁；
2. 某 CPU 是否关中断等待另一个 CPU 的 IPI；
3. 等待队列中是否缺少 wake；
4. 所有 CPU 都 idle 时，目标任务是否已丢失或睡眠条件永远不再变化；
5. 只有一个 CPU 忙时，是否是无界 poll、IRQ 风暴或日志刷屏。

实板不能直接接 QEMU stub，应先用最小输入缩短复现，再在同架构 QEMU 中打断点；若只在实板出现，给
状态转换点增加有界计数日志，而不是在中断或轮询循环中逐次打印。逐次打印会改变时序，甚至制造新的
串口活锁。

#### 0.2.9 从函数回到真正的错误源

拿到函数名后按以下顺序查：

```sh
rg -n 'fn function_name|struct TypeName|impl .*TypeName' kernel vendor
git log --oneline -- path/to/file.rs
git blame -L START,END path/to/file.rs
git show COMMIT -- path/to/file.rs
```

- `rg` 找当前实现和所有调用者；
- `git log` 找行为何时变化；
- `git blame` 找某个设计假设由哪个提交引入；
- `git show` 只看该提交对目标文件的改动，不直接回退整条历史。

然后把函数分为“发现错误”和“制造错误”两类。历史 RISC-V page fault 最后落在 allocator 和 scheduler，
但反汇编算出的地址位于应永久存在的 direct-map；继续比较失败/成功日志中的 Boot HART，再审计所有
logical CPU ID 进入 SBI RFENCE 的位置，才找到 CPU ID 边界和启动页表 root 竞态。完整证据链见
[RISC-V page fault 复现](../history/repro/riscv-pagefault-20260812-run01/README.md)。

#### 0.2.10 最快定位到可修改源码的判定表

| 现场证据 | 下一条命令 | 优先源码层 |
| --- | --- | --- |
| 明确内核 PC | `gdb info symbol`、`x/12i` | 该函数及其数据生产者 |
| 用户 `SIGILL` | `readelf -A`、反汇编 PC | 工具链 ISA、异常上下文 |
| 用户 `SIGBUS` | 算访存有效地址 | unaligned 模拟、映射/文件截断 |
| syscall 返回错误 errno | Linux/MOSS 最小探针对照 | `kernel/src/syscall/` ABI 边界 |
| `poll/select` 卡住 | 打印请求事件和返回事件 | Pollable、wait queue、wake |
| 网络小包通、HTTPS 不通 | 抓 SYN/ACK、检查 checksum | router 统一出口、驱动描述符 |
| 多核才失败 | 所有 CPU 栈、CPU/hart 映射 | COW、TLB shootdown、IPI、锁 |
| 重启后文件为零 | `sync`、哈希、只读 fsck | page cache、writeback、ext4 元数据 |
| 只在一块板失败 | DT、IRQ、DMA 状态 | 平台驱动；不要改共用 syscall |

到这一步才开始改代码。一个合格的定位结论至少要能说清：哪条指令失败、操作了哪个地址、这个地址本应
由谁维护、Linux 的语义是什么、应改哪个共享函数，以及为什么不会影响另一个架构。

## 1. 当前四个平台、产物和根文件系统

### 1.1 五个常用 make 入口

当前根目录 [Makefile](../../Makefile) 保留五个普通入口：

```sh
make all
make site-rv
make site-la
make site-vf2
make site-2kla
```

| 命令 | 用途 | 产物或行为 |
| --- | --- | --- |
| `make all` | 初赛/决赛通用 QEMU 内核 | 生成 `kernel-rv`、`kernel-la`；设备树 CPU 数决定 init |
| `make site-rv` | 现场 RISC-V QEMU | QEMU 为 16 核 8 GiB，编译后自动启动 shell |
| `make site-la` | 现场 LoongArch QEMU | QEMU 为 8 核 8 GiB，编译后自动启动 shell |
| `make site-vf2` | VF2 实板 | 只生成 `build/site-vf2/moss-vf2.bin`，不传输、不启动 |
| `make site-2kla` | 龙芯实板 | 只生成 `build/site-2kla/moss-2kla.bin`，不传输、不启动 |

`make all` 中的 `CPU_CAPACITY=256` 是编译时容量上限，不表示 QEMU 真有 256 核。运行时读取设备树：
单核进入初赛 `init_pre.sh`，多核进入决赛 `init_final.sh`。现场 shell 目标使用 `site-init`，进入
`init_site.sh`，这三条路径不要混为一谈。

### 1.2 当前根文件系统

| 平台 | 当前现场根文件系统 | 说明 |
| --- | --- | --- |
| QEMU RV64 | `alpine-linux-riscv64-ext4fs.img` | 当前 QEMU 实际加载的文件，位于仓库根目录 |
| QEMU LA64 | `sdcard-la-pub.img` | 当前 QEMU 实际加载的文件，位于仓库根目录 |
| VF2 | 由 U-Boot `root=` 指向 SD 卡目标分区 | 历史使用过 Debian p2、Alpine p3/p4，启动前必须确认 |
| LS2K1000LA | 由设备树/启动参数指向 SATA 分区 | 历史上 Debian 常用 `/dev/sda2`，Alpine 常用 `/dev/sda3` |

以上入口按 2026-08-20 的 Makefile 核对。Makefile 仍先检查 `images/rootfs/site-rv.img` / `site-la.img`，与实际加载路径不同；该问题尚未修改，见[操作指南](../guides/README.md)。

QEMU 的 `-snapshot` 允许本次启动中创建文件、安装包和修改 IP，但退出后不会写回基准镜像。需要验证
持久化时，必须用工作副本启动并在退出后执行只读 `e2fsck -fn`，不能拿快照模式证明持久化。

板卡的设备名可能变化。不要在另一块板上照抄 `eth0`、`/dev/sda2` 或 `/dev/mmcblk1p2`。先查：

```sh
ip -brief link
lsblk -f
findmnt /
cat /proc/cmdline
```

### 1.3 当前网络基线

QEMU user networking 默认由 DHCP 获取 `10.0.2.15/24`，网关一般是 `10.0.2.2`。两块实板为了

### 1.4 内存值为什么会矛盾

历史文档里同时出现过“LS2K1000LA 是 1 GiB”“U-Boot 报 2 GiB”“编译上限 2 GiB”。三者不是同一个
概念：

- `MEM=2G` 是 MOSS 能管理的物理地址范围上限；
- U-Boot 的 DRAM 表可能来自固件，历史上曾被证明存在错误；
- Linux 和 MOSS 启动日志中的实际可用页数才是本轮运行证据。

现场必须重新看：

```sh
free -h
cat /proc/meminfo
dmesg | grep -i memory
```

MOSS 侧看启动日志里的 `MOSS_DTB memory_bytes=` 和 `MOSS_MEMORY managed_mib=`。不要用 Makefile 的
2 GiB 配置反推实体板一定有 2 GiB。

## 2. 报错应该怎么看

### 2.1 先保存完整现场

QEMU 交互日志可这样保存：

```sh
mkdir -p tmp
script -q -f tmp/site-rv.log -c 'make site-rv'
```

`script` 同时保存程序输出和终端交互；`-f` 让内容及时落盘。龙芯串口示例：

```sh
script -q -f tmp/ls2k-serial.log -c 'picocom -b 115200 /dev/ttyUSB0'
```

串口设备名必须按 `ls /dev/ttyUSB* /dev/ttyACM*` 的实际结果替换。执行有风险的上板动作前，记录：

```sh
git rev-parse HEAD
sha256sum build/site-2kla/moss-2kla.bin
date -u
```

### 2.2 错误分层

| 现象 | 首先属于哪层 | 第一项证据 |
| --- | --- | --- |
| `/bin/sh: python3: not found` | 根文件系统/包安装/PATH | `command -v python3`、`apk info python3` |
| `No such package` | 包名或索引 | `apk update`、`apk search` |
| `temporary error` | DNS、路由、下载或仓库 | `ip route`、`resolv.conf`、直接 wget 索引 |
| `Network unreachable` | 路由或内核发送路径 | `ip route get`、公网 IP、TCP SYN 抓包 |
| `Resource temporarily unavailable` | syscall 返回 `EAGAIN` | 检查 fd 是否应阻塞、poll/唤醒路径 |
| `SIGILL` | CPU 指令、工具链或异常处理 | `file`、`readelf -A`、异常 PC/BADI |
| `SIGBUS` | 未对齐、文件映射或截断 | fault 地址、指令、映射长度、Linux 对照 |
| 服务 ready 前连接失败 | 启动时序或服务真实失败 | 服务日志、监听端口、进程状态 |
| 命令完成但重启后文件为零 | 页缓存/写回/ext4 | `sync`、只读 fsck、落盘前后哈希 |
| 多核才卡住 | 调度、锁、IPI、TLB 或 per-CPU 状态 | 单核/双核 A/B、所有 CPU 栈 |

应用报错只是入口。例如 APT 卡住不代表“APT 需要特殊适配”，它曾经分别暴露 TTY `O_NONBLOCK`、
管道 `lseek`、`select` 对 `POLLHUP` 的处理问题。正确修复必须落到共用 syscall、文件或网络函数，
让其他程序一起获得 Linux 语义；不要在应用名上写特殊判断。

### 2.3 与 Linux 对照的固定方法

在 Linux 上使用同一架构、同一根文件系统和同一普通命令。至少保存：

```sh
command; echo "rc=$?"
strace -ff -o linux-trace command
dmesg | tail -n 100
```

然后回答五个问题：

1. Linux 最后一条成功 syscall 是什么？
2. MOSS 返回的 errno、结构体字段或唤醒事件哪里不同？
3. 这个差异是 POSIX/Linux ABI 要求，还是某个 libc/应用自己的假设？
4. 应修改 syscall 共用层、VFS、网络栈、驱动还是测试合同？
5. 修复后如何证明没有破坏另一架构和 VF2？

没有 `strace` 时，可以先运行更小的 C 程序，只保留一个 syscall。查接口定义优先使用：

```sh
man 2 recvmsg
man 2 select
man 7 netlink
grep -R 'struct sockaddr_nl' /usr/include/linux
```

Linux 源码对照时，从 syscall 入口沿真实调用链看返回值、锁和 copy_to_user，不要只搜索同名函数。
驱动问题还要对照设备树 binding、寄存器手册和 Linux 对应驱动；Linux 能工作只说明硬件与接线大体可用，
不能证明 MOSS 的 DMA、cache、描述符或中断实现正确。

## 4. 基础用户空间与系统工具

### 4.1 BusyBox、basic、bash 与常用命令

#### 历史适配内容

初赛镜像同时带 musl 和 glibc 用户空间。`src/init_pre.sh` 先用 `/glibc/busybox --install -s /bin`
补齐 shell 和基础命令，再根据当前架构建立动态加载器链接。历史上出现过三类启动问题：

1. `/bin/sh` 不存在或不能执行，init 在真正进入测例前失败；
2. ELF 的 `PT_INTERP` 指向 `/lib/...`，镜像实际把加载器放在 `/musl` 或 `/glibc`；
3. 同一个 `/lib/libc.so` 被错误地留在另一种 libc 状态，后续动态程序装载失败。

历史提交 `1e9a5489` 为 shell 增加 BusyBox fallback，`ecc93e39` 修复 glibc 动态加载。当前 init 明确
切换 `musl_runtime` 与 `glibc_runtime`，避免两个运行时混用。

#### 普通验证命令

```sh
/bin/sh -c 'echo shell-ok'
busybox | head
printf 'alpha 10\nbeta 20\n' > data.txt
grep alpha data.txt
sed 's/alpha/ALPHA/' data.txt
awk '{ total += $2 } END { print total }' data.txt
find . -name data.txt
```

这些命令覆盖 shell、重定向、文件创建、管道、查找、文本过滤和聚合。只运行 `busybox --help` 只能
证明二进制装载，不能证明文件和管道语义。

#### Linux 对照重点

- 脚本失败先用 `file /bin/sh`、`readelf -l /bin/sh` 看解释器；
- `ENOENT` 不一定是 shell 文件不存在，也可能是 ELF interpreter 不存在；
- `Permission denied` 要同时看文件 mode、挂载 `noexec` 和凭据；
- 管道末端卡住要检查仍存活的 writer fd，而不是只看读进程。

### 4.2 coreutils、findutils、grep、sed、awk、util-linux

历史基础用户空间合同不是版本检查，而是组合真实文件操作：递归查找、排序、摘要、替换、聚合和
`flock` 竞争。Git/Vim 后来暴露的问题也证明，简单 `touch` 成功不能代表完整 VFS 语义正确。

`flock` 的最小检查：

```sh
flock lockfile sh -c 'echo first >> result.txt'
flock lockfile sh -c 'echo second >> result.txt'
cat result.txt
```

遇到文件“看得到但重启消失”时依次检查：

```sh
stat result.txt
sync
sha256sum result.txt
```

退出 MOSS 后再由 Linux 对目标分区执行 `e2fsck -fn`。`sync` 返回只说明提交动作完成，最终是否落盘
仍要用重启后哈希和 fsck 证明。

### 4.3 procps：ps、pgrep、free、uptime、kill

procps 会同时读取 `/proc`、时钟、内存统计和进程状态。历史验收使用真实子进程：启动 `sleep`，由
`pgrep` 找到，再用 `kill` 终止并等待回收。

```sh
sleep 30 &
pid=$!
ps
pgrep sleep
kill "$pid"
wait "$pid"
free
uptime
```

如果 `ps` 看不到进程，先区分 `/proc` 未挂载、procfs 字段缺失和进程已经退出。如果 `kill` 返回 0
但进程不退出，查信号 pending、阻塞掩码、线程组投递和阻塞 syscall 是否被唤醒。

### 4.4 SysVinit 与 OpenRC

MOSS 直接进入目标根文件系统时，通常不是由 systemd 或 OpenRC 作为 PID 1 启动。历史验收因此只
补齐标准运行目录和普通服务脚本，再用用户会输入的命令检查：

```sh
rc-service moss-openrc-probe start
rc-service moss-openrc-probe status
rc-service moss-openrc-probe stop
```

Debian 使用：

```sh
service moss-sysv-probe start
service moss-sysv-probe status
service moss-sysv-probe stop
```

安装脚本出现 `systemctl`、`insserv` 或 systemd specifier 错误，不等于软件包一定安装失败。必须检查
APT/dpkg 返回值、包状态和最终服务功能。但也不能直接忽略：若返回值非零或服务不可用，仍是失败。

### 4.5 musl、glibc 与 libctest

历史双环境验收同时覆盖：

- musl 动态加载器与 Alpine 包；
- glibc/libc6 的 pthread、TLS、`dlopen` 和 libm；
- libctest 的字符串、时间、文件、线程和动态装载语义。

历史问题包括 musl dynamic runtime 路径错误、glibc 测例一度被关闭，以及 `utime` 语义不一致。
提交 `b8a69005`、`70b2c8cb`、`1356ea76` 分别记录了相关修复。当前 `compat_binary_patches=0`，说明
旧的二进制字节补丁不是当前默认路径；现场不能重新打开它们来掩盖内核错误。

检查一个程序实际使用哪个 libc：

```sh
file program
readelf -l program
ldd program
```

若 `ldd` 不可用，以 `readelf -l` 中的 `Requesting program interpreter` 为准。

## 5. 网络工具和包下载故障链

### 5.1 iproute2 与 `ip addr`

#### 第一阶段：netlink 基础语义缺失

早期基础用户空间文档只敢运行 `ip -Version`，因为当时没有完整 `NETLINK_ROUTE`。后来真正运行：

```sh
ip link show
ip address show
ip route show
```

发现 MOSS 已发送 `NLMSG_DONE`，iproute2 却继续等待。Linux 的 netlink 响应来自内核，
`recvmsg` 写回的 `sockaddr_nl.nl_pid` 应为 0。旧实现没有填写 `msg_name`，用户缓冲区保留随机值，
iproute2 因而丢弃完成消息。

历史修复 `773cef79` 实现 `RTM_GETLINK`、`RTM_GETADDR`、`RTM_GETROUTE`，并统一填充内核源地址。
QEMU RV、QEMU LA 和 VF2 随后通过普通三条查询。

#### 第二阶段：龙芯 copyout 地址错误

2026-08-18 的龙芯实板仍出现 `ip addr` 无返回。最小 netlink probe 表明内核已经生成消息，问题在
`recvmsg` 的地址和控制字段写回。提交 `09b5b718` 把网络接收结果集中到函数中，再按用户提供的
`msg_namelen`、iov 和控制缓冲区安全 copyout，避免零散一行行修补。

本轮用户串口最终得到：

```text
1: lo: <LOOPBACK,UP> mtu 65536 state UP qlen 1000
    inet 127.0.0.1/8 scope host lo
2: eth0: <BROADCAST,MULTICAST,UP> mtu 1500 state UP qlen 1000
    inet 192.168.88.2/24 brd 192.168.88.255 scope global eth0
```

这是当前实板 `ip addr` 成功的证据，但不代表历史基础用户空间整组已在当前 HEAD 重跑。

#### 第三阶段：LS2K 网络 poll 活锁

历史实板曾打印：

```text
network poll budget exhausted; yielding with deferred work still pending
TEST FAILED: MOSS shell command timed out: ... ip link show ...
```

旧循环在 PHY 不可用或 RX 持续有工作时，一轮内一直处理网络，其他任务得不到调度。修复把一次网络
服务和一次驱动 poll 都限制为有界工作量，剩余工作交给下一调度轮。它只证明系统级活锁被打断；在
当时的日志里 `ip link show` 仍没完成，因此历史总报告正确地把该轮记为失败。

#### 修改地址

先看当前接口名，再操作：

```sh
ip -brief link
ip addr flush dev eth0
ip addr add 192.168.88.2/24 dev eth0
ip link set eth0 up
ip route add default via 192.168.88.1
```

星光二号当前网段应改成 `192.168.89.2/24` 和 `192.168.89.1`。接口不叫 `eth0` 时必须替换；不要
为了“通用”对所有接口循环 flush，那可能清掉串口中转 Linux 的管理网络。

### 5.2 ping 刷 `Resource temporarily unavailable`

龙芯串口曾出现每两个正常回复之间打印大量：

```text
ping: recvfrom: Resource temporarily unavailable
```

最终统计仍是 3 发 3 收。这不是宿主机梯子产生的文本，也不是 ICMP 真丢包；它表示阻塞 raw socket
的 `recvfrom` 错误地返回了 `EAGAIN`，BusyBox ping 立即重试，于是刷屏。

#### 排查过程

1. `ip addr` 正常，排除 netlink 查询卡住；
2. 网关三次都收到回复，排除基本链路和 ARP 完全失败；
3. 同一镜像在 LoongArch 更容易出现，检查 raw socket 的阻塞标志；
4. 发现大型 `RawSocket` 聚合对象在构造后移动，受影响的 LoongArch 工具链可能破坏其中字节原子状态；
5. 把完整状态放入最终 `Box<RawSocketInner>`，所有字段在最终地址原位构造，外层只移动一个指针。

提交 `d845e6c8` 实现该修复。修复后网关与公网 IP 的三包测试都没有再出现 EAGAIN 刷屏。

Linux 对照时重点检查：socket 是否创建为 `SOCK_RAW`、是否设置 `O_NONBLOCK`、`recvfrom` 前 poll
是否报告可读。阻塞 fd 没收到包时应睡眠，被信号打断可返回 `EINTR`；不应无条件返回 `EAGAIN`。

### 5.3 DNS、路由、TCP 与“宿主机梯子”

本轮最容易误判的一条链是：

1. `ip addr` 有 `192.168.88.2`；
2. 网关能 ping；
3. `/etc/resolv.conf` 一度为空或内容不稳定；
4. 写入 DNS 后域名和公网 IP 都能 ping；
5. pip 仍报 `Network unreachable`，APK 间歇报 `temporary error`。

到第 4 步时 DNS 已经工作，继续归因于“解析失败”是不对的。第 5 步说明 TCP/UDP 发送路径仍有问题。
MOSS router 是 IP 层设备，不提供 Linux 网卡那种 checksum offload 元数据；旧路径把 checksum 为 0
的 TCP/UDP 包交给物理设备，公网设备会丢弃。`d845e6c8` 在发往物理设备前统一补齐 IPv4/IPv6 的
TCP/UDP checksum，并保留分片包边界。

宿主代理可能影响出口，但判断方法不是“终端开着梯子所以一定有问题”，而是看真实路由和抓包：

```sh
ip route
sudo nft list ruleset
sudo tcpdump -ni any host 192.168.88.2
```

如果看到板端 SYN 发出、宿主转发、远端 SYN-ACK 返回，代理不是当前阻塞点。如果连 SYN 都没有，先查
板端路由或内核发送。如果 SYN 到宿主但没转发，再查 NAT、防火墙和策略路由。

### 5.4 APK

本轮原始错误：

```text
fetch https://dl-cdn.alpinelinux.org/alpine/v3.21/main/loongarch64/APKINDEX.tar.gz
WARNING: updating ... temporary error (try again later)
ERROR: libbz2-1.0.8-r6: temporary error (try again later)
```

`apk add python` 还会得到 `python (no such package)`，因为 Alpine 3.21 的正确包名是 `python3`。
这两个错误必须分开：`python` 是包名问题；后续多个依赖的 `temporary error` 才是网络问题。

当前普通命令：

```sh
apk update
apk add python3
python3 --version
```

本轮修复网络与 DNS 后，实板下载约 470 KiB APKINDEX，`apk update` 识别 23722 个包，
`apk add python3` 完成，最终为 Python 3.12.14。这证明当时不是文件系统损坏。

历史应用验收为保证可复现，也使用过宿主预取、目标端 `apk verify`、
`apk --no-network --no-scripts add` 的离线闭包。离线安装用于固定输入，不等于网络已经通过；在线
`apk update` 和离线 APK 验签是两项不同证据。

### 5.5 APT 与 dpkg

历史 SQLite/APT/curl 验收在 Debian 根文件系统中运行普通：

```sh
apt-get update
apt-get install -y sqlite3
dpkg-query -W sqlite3
```

APT 依次暴露了三个内核语义问题：

- TTY 内层再次阻塞，导致 fd 的 `O_NONBLOCK` 失效；
- 对管道 `lseek` 返回 `EPIPE`，Linux 应返回 `ESPIPE`；
- 等待 dpkg 管道 EOF 时，`select` 没把 `POLLHUP/POLLERR` 视作 readfds 可读。

提交 `ce484d39`、`2bf11283` 修复这些共用语义。实板 RTC 曾停在 2022 年，Debian 快照签名会被判为
尚未生效；正确做法是在启动 APT 前一次性同步 UTC，不能在 APT 验签中途突然跳时间。

安装阶段可能出现：

```text
insserv: FATAL: service mountkernfs has to exist for service procps
sysctl: setting key "kernel.core_pattern": Bad file descriptor
Failed to replace specifiers in '/tmp/systemd-private-%b-*'
```

MOSS 不是完整 systemd PID 1，包脚本的环境探测可能失败。判定标准仍是 APT 返回 0、dpkg 状态为
installed、真实应用能运行、最后能 sync 和 fsck；不能只看到一条 warning 就判整轮失败，也不能
忽略非零返回值。

### 6.3 GCC 与 G++

历史 LS2K 现场软件报告中 GCC 完成 help、编译和运行；后续四平台工具链验收还用 G++ 构建并运行

```sh

EOF

```

```sh
cat > hello.cpp <<'EOF'
#include <iostream>
int main() { std::cout << "g++-ok\n"; }
EOF

./hello-cpp
```

GCC/G++ 问题分三层：

- `gcc: not found`：根文件系统未安装或 PATH 不完整；
- 编译器自身 SIGILL：检查工具链构建时假定的 CPU 扩展，例如 LSX；
- 产物运行 SIGILL/SIGBUS：检查产物 ELF 属性、实际 CPU、未对齐指令和 MOSS 异常处理。

检查命令：

```sh
gcc -v
file hello
readelf -h hello
readelf -A hello
```

历史龙芯 BSP2 路径中 `/bin/sh` SIGILL 的直接根因是 Linux defconfig 漏开 LSX，而不是 AHCI 或根文件
系统损坏。这个案例说明：同一二进制在原厂 Linux 和新 Linux 的差异，可能来自内核是否允许某类 CPU
上下文，而不一定来自文件内容。

### 6.4 GNU Make、CMake 与 pkg-config

历史工具链验收覆盖 Make 并行/增量构建，以及 CMake 通过 `find_package(PkgConfig)` 找到本地静态

### 6.5 Rust、rustc 与 Cargo

历史现场验收用 rustc 编译运行，后续工具链验收还运行 Cargo offline build。最短命令：

```sh

EOF

```

Cargo 最小工程：


龙芯上 Rust 工具链历史问题包括：

- glibc 2.41 与旧 Linux 5.10 接口不匹配；
- 工具链或 shell 使用 LSX，但新内核配置未保存相关扩展上下文；
- BuildStorm 高并发下 COW、mprotect、exec 和文件系统放大了内核锁问题；
- 1 GiB 内存路径需要 swap/reclaim，不能简单解释成“rustc 坏了”。

判断文件系统是否损坏：先比较二进制哈希和动态加载器，运行 `rustc --version` 与最小程序。如果固定
位置总是 SIGILL/SIGBUS，再查指令；如果每次随机崩溃并伴随 I/O/fsck 错误，才提高文件系统损坏的
优先级。重新烧录可能消除坏文件，但不会修复 CPU 扩展、内核 syscall 或网络语义。

### 7.3 PostgreSQL

历史 PostgreSQL 17 合同包括 `initdb`、启动 postmaster、TCP 建表/插入/聚合、fast stop。结果：

```text
POSTGRESQL_MUSL_OK 3:60:alpha,beta,gamma
```

当前 MOSS 历史验收显式使用：

```text
dynamic_shared_memory_type = mmap
```

这是因为 System V dynamic shared memory 当时没有纳入完整合同；SQL、fork backend 和 TCP 没有被
跳过。它属于明确记录的兼容配置，不能扩写成“System V shm 已通过”。

龙芯实板曾出现新 accepted socket 的字节原子关闭标志保留 slab 旧值，backend 第一次 `recv` 返回

这与 raw socket 的原位构造问题同属 LoongArch 大对象移动/原子状态风险，但不是同一个对象。

排查顺序：

```sh

cat postgresql.log
ss -lnt
pg_isready
```

必须区分 `initdb`、postmaster ready、backend accept、SQL 和停机五个阶段。

### 7.7 Dropbear 与 OpenSSH

历史基础用户空间验收用真实 ED25519 公钥、loopback TCP 和远程命令，依次测试 Dropbear、OpenSSH。
OpenSSH 暴露的内核语义包括：

- 未绑定 TCP/UDP `getsockname` 应返回 unspecified 地址和 0 端口，而不是 `ENOTCONN`；
- 未设置 `SO_BINDTODEVICE` 时查询应成功并返回空值；
- `setuid`、`setgid` 永久降权和 `PR_SET_NO_NEW_PRIVS` 继承；
- preauth chroot 后 `getrandom` 不能依赖当前根目录的 `/dev/urandom`。

提交 `5c4b45c0`、`93ada027` 修复这些共用路径。历史 seccomp prctl 只做兼容成功返回，没有执行完整
过滤规则，因此不能写成“OpenSSH seccomp 沙箱已实现”。

普通客户端命令：

```sh
ssh root@127.0.0.1 'echo ssh-ok'
```

失败时加一次 `-v` 查看阶段；不要默认使用 `-o StrictHostKeyChecking=no` 和关闭认证来制造通过。

## 8. 初赛应用、性能负载与 LTP

当前 [init_pre.sh](../../src/init_pre.sh) 在 musl 和 glibc 两轮启用：basic、BusyBox、cyclictest、iozone、
iperf、libcbench、libctest、lmbench、LTP、Lua、netperf。每组打印统一 start/end 标记。现场判断首先
看组标记是否完整，再看组内原始输出；不能因为脚本最后继续运行就把组内失败忽略。

### 8.1 iozone

iozone 覆盖顺序写/重写/读、随机读写、倒序读、跨步读、stdio、pread/pwrite、preadv/pwritev 等路径。
当前评分子项和命令见 [性能测试及其子项](../benchmarks/性能测试及其子项.md)，历史优化与原始结果位于
`docs/benchmarks/iozone/` 和 `docs/evidence/saved_logs/`。

历史问题不只是“磁盘慢”：

- 页缓存每次读取都重新访问 ext4，吞吐低；
- 全局锁持有期间做块 I/O，并发线程互相阻塞；
- 文件 truncate/append 后页缓存与 inode size 不一致；
- dirty folio 被回收或文件关闭时没有完整写回；
- append 内容重启后变成零，说明元数据先于数据暴露。

最小功能检查先用小文件：

```sh
dd if=/dev/zero of=iozone-check.bin bs=1M count=4
sync
sha256sum iozone-check.bin
```

正式评测不要自行改块大小、线程数或文件大小，因为结果不可和历史数据比较。性能修改必须固定架构、
CPU、内存、根镜像和冷/热缓存状态，再做 A/B。

### 8.2 iperf 与 iperf3

初赛 iperf 包含基础、并行、反向的 TCP/UDP 带宽。历史修复 `8e1766a3` 补齐 socket 兼容性，
`deee93b3` 修复 UDP 无法运行；后续结果记录了本地 listener、lazy peer address、socket fast close、
UDP 无路由唤醒、ring buffer 和 LoongArch user-copy 等单变量实验。

`src/init_pre.sh` 在每个 libc 组前后都清理 `iperf`/`iperf3` 守护进程，因为 `iperf -s -D` 会脱离
原脚本 PID。若不清理，第二轮可能连接到上一轮服务，制造假通过或端口占用。

手工最小检查分两个 shell。服务端：

```sh
iperf3 -s
```

客户端：

```sh
iperf3 -c 127.0.0.1
```

UDP 再单独运行：

```sh
iperf3 -c 127.0.0.1 -u
```

loopback 只能证明协议栈本地路径，实板 GMAC 还要对宿主地址运行。吞吐测试失败先保留 control connection
和 data connection 各自错误；“连接成功但 0 bit/s”与“连接被拒绝”不是同一问题。

### 8.3 netperf

netperf 包含 UDP_STREAM、TCP_STREAM、UDP_RR、TCP_RR、TCP_CRR。历史脚本中的 `netserver -D`
存在启动竞态，因此当前 init 在第一个控制连接前等待 1 秒，并在两轮之间清理 `netperf`、`netserver`。

服务端：

```sh
netserver
```

客户端基础检查：

```sh
netperf -H 127.0.0.1
```

如果固定等待能稳定通过，要继续确认是真实服务 ready 还是掩盖死锁。正确的长期合同应等待监听端口或
ready 标记，而不是不断扩大 sleep。

### 8.4 lmbench

lmbench 的 36 个子项覆盖 syscall、read/write/stat/fstat/open、select、signal、pipe、fork/exec、
page fault、mmap、文件创建删除、文件/管道带宽和多进程 context switch。

历史 `lat-fs` 曾卡死，修复集中在文件创建删除、目录项、锁和进程回收；后续性能优化又涉及 read/write
fast path、stat/fstat、fault-around 和 select。文档和日志位于 `docs/benchmarks/lmbench/`。

现场不要只看总分。某一子项出现异常时，先找到它对应的 syscall 组合。例如：

- `lat_syscall`：syscall 入口/返回固定开销；
- `lat_proc fork`：地址空间 clone、COW、进程树、wait；
- `lat_fs`：create/unlink、dentry/inode、ext4；
- `lat_ctx`：pipe/futex、调度和唤醒；
- `lat_pagefault`：mmap、缺页、页缓存和 TLB。

Linux 对照必须用同样进程数和文件大小，且不能拿宿主原生硬件耗时直接作为 QEMU 绝对目标；主要比较
哪个子项数量级异常，以及修改前后的相对变化。

### 8.5 libcbench

libcbench 主要测 libc 字符串、内存、分配、线程等路径，也会放大 user copy、匿名页缺页和 heap/mmap
策略差异。历史实验包括 heap 预映射、匿名 fault-around、mmap record fast path 和 thread table
fast path，结果保存在 `docs/benchmarks/libcbench/`。

优化必须先定位具体子项。全局预映射大量 heap 可能让一个分配测试变快，却增加启动内存并破坏别的
工作负载。历史 PCP 页缓存实验也出现“理论上更快，端到端更慢”，最终保留了回退节点。

### 8.6 cyclictest

cyclictest 测无压力/压力下单线程和多线程唤醒延迟。它依赖高精度 timer、sleep、调度策略、优先级、
affinity 和信号。历史 LoongArch musl 的部分 `sched_*` 是 ENOSYS stub，曾有二进制补丁实验；当前
`compat_binary_patches=0`，不能把补丁当默认修复。

历史问题包括 LoongArch pthread_cancel、sleep 卡住、RR 优先级/时间片和 waker reschedule。当前结果
与单变量实验保存在 `docs/benchmarks/cyclictest/`。

最小检查：

```sh
cyclictest --help
```

正式命令以比赛脚本为准。若程序启动即报调度权限或 `ENOSYS`，先检查 `sched_getscheduler`、
`sched_setscheduler`、`sched_getparam`、`sched_setparam` 的 Linux errno；不要把实时策略直接改成普通
策略后仍按 cyclictest 结果计分。

### 8.7 libctest

libctest 历史上暴露 dynamic loader、临时路径、`utime` 和个别阻塞测例问题。它是 libc API 与 Linux
syscall 语义之间的桥：同一个失败可能来自 libc 自己的实现，也可能来自 MOSS 返回值。

排查方法：

1. 确认失败运行的是 musl 还是 glibc；
2. 查看失败函数最终发起哪个 syscall；
3. 在 Linux 的同一 libc 上运行同一二进制；
4. 若两种 libc 预期不同，不能拿 glibc 行为强行修改 musl；
5. 只跳过确定会无限卡住且已有记录的测例，不能把失败批量注释掉。

### 8.8 LTP

当前 [ltp_testcases.sh](../../src/ltp_testcases.sh) 有 535 条启用用例。本文把 LTP 作为一个完整应用，
不把 535 条名字重复抄一遍；现场以该文件为唯一启用清单：

```sh
awk 'NF && $1 !~ /^#/ {print}' src/ltp_testcases.sh | wc -l
```

#### 用例类别与对应内核层

| 类别 | 代表用例 | 主要内核层 |
| --- | --- | --- |
| 进程 | fork、clone、execve、wait | task、地址空间、信号、进程树 |
| 内存 | mmap、mprotect、brk、mremap | VMA、PTE、COW、TLB |
| 文件 | open、fcntl、flock、xattr、fsync | fd、VFS、inode/dentry、ext4 |
| I/O | pipe、readv/writev、sendfile、splice | pipe、页缓存、短读写、offset |
| 事件 | poll、select、epoll、eventfd | wait queue、就绪位、EOF/HUP |
| 网络 | socket、bind、accept、getsockopt | socket state、地址、阻塞唤醒 |
| 时间 | timer、clock、adjtimex、nanosleep | timer wheel、时钟、信号 |
| 同步 | futex、robust list | key、等待队列、原子状态、退出清理 |
| 权限 | uid/gid、capability、prctl、chroot | credentials、继承、proc/dev |
| 调试 | ptrace | stop 状态、寄存器、内存、信号 |

#### 历史适配主线

- 2025 年先补 mmap/mprotect、iovec、poll/epoll、fadvise、chroot/chown/accept 等基础语义；
- 2026 年 4 月围绕 fcntl、accept、解释器名、init 选择和 ptrace Summary 收敛；
- 5 月补 execveat、futex 时间与等待；
- 6 月逐步打开更多用例，修复超时、输出统计和 LTP 选择；
- 当前 init 从内嵌 `LTP_CASES` 或 `ltp_testcases.sh` 逐条运行，并打印时间戳。

`src/init_pre.sh` 每条用例后会打印评测需要的：

```text
FAIL LTP CASE <name> : 0
```

这个固定文本中的 `0` 是评测格式，不应脱离上下文理解成“测试失败”。真实判定要看用例自己的 TPASS、
TFAIL、TBROK、Summary 和组统计。

#### 典型错误

- RV 旧 musl `clone04` wrapper 对 NULL stack 解引用；
- musl `epoll_create(size)` 忽略非法 size，与 LTP 的 Linux 预期不同；
- `gethostbyname_r`、`gethostname` 在 musl/glibc 的边界语义不同；
- ptrace05/06 不输出 Summary，评测无法计分；
- futex_cmp_requeue、timer、epoll 在时序下卡死；
- fcntl lock、pipe EOF、poll HUP 与 Linux 不同。

历史曾准备二进制字节补丁，但当前默认关闭。优先修复 MOSS 内核；只有明确属于旧测试二进制或 libc
自身且无法重编译时，才可把兼容补丁记录为输入修复，并验证目标字节完全匹配，不能盲写 offset。

#### 单项复现

先把用例名写入 `some_testcases` 或使用现有测试入口，只跑一个 case。保留用例完整 stdout/stderr、
开始结束时间、CPU/内存和当前 libc。用 Linux 同二进制对照 errno 后，再沿 syscall 入口定位。

## 9. 决赛应用：CAgent 与 BuildStorm

当前 [init_final.sh](../../src/init_final.sh) 只做两件事：运行 `/glibc/cagent_testcode.sh` 和
`/glibc/buildstorm_testcode.sh`。它按 `uname -m` 选择架构，不额外读取大量参数。

### 9.1 CAgent

CAgent 覆盖基础命令、时间、系统信息、网络状态、文件目录操作和并发进程。它不是一个单一 syscall
测试，因此某一阶段停住要先找到最后一条应用命令。

LS2K 实板历史故障链：

1. DWMAC link up，但描述符步长与 ATDS 不一致；
2. `event-listener` 内部指针被观察为 `0x1`；
3. raw `spin::RwLock` upgrade 在单核形成活锁；
4. 错误 watchdog 把“长时间没有 syscall”当卡死；
5. 后续定位到 accepted socket 最终分配和锁状态。

这条历史说明：有串口输出、CPU 忙或定时器跳动，都不能证明工作负载有进展。watchdog 应看明确阶段
或可验证进度，且必须有不可延长的绝对上限。

### 9.2 BuildStorm

BuildStorm 在用户态运行真实 Rust 工具链，完整编译数百 crate，综合覆盖动态链接、fork/exec、线程、
COW、mmap/mprotect、文件系统、多核同步和内存压力。历史最终报告给出 RV/LA 满分路径，但任何新的
内存、调度或文件系统修改都可能使它回归。

#### 主要历史故障链

- 缺页长期持有 AddrSpace 写锁，所有并发 fault 串行；
- 三阶段缺页减少锁时间后，嵌套 fork 看到不完整页表状态；
- COW 快路径在关中断状态发同步跨核 TLB flush，形成死锁；
- 单独移植 COW 优化后，BuildStorm 全核 idle，根因是缺少配套 wake/owner 语义；
- `vfork` 退化成普通 COW fork，增加大量复制；
- per-CPU page cache 理论上减少全局锁，实际端到端变慢，最终回退；
- 多线程进程执行 execve 时，兄弟线程和地址空间清理不完整；
- 龙芯 1 GiB 路径 OOM，加入 swap 后又出现交换抖动和同步逐页回收停顿；
- SMP2 syscall 返回热路径频繁迁移，形成 migration storm；
- CLOEXEC pipe 实际由 Unix `SOCK_SEQPACKET` 实现，阻塞属性错误；
- root remount 前强制复位留下 ext4 orphan chain。

详细历史见 [MOSS 开发典型困难](moss开发典型困难与解决方式.md) 和 [BuildStorm 优化报告](../reports/buildstorm-report/main.typ)。

#### 正确分析方法

1. 固定 CPU、内存、镜像、提交和冷启动状态；
2. 记录 setup、minibuild、full build 分阶段耗时；
3. 看 QEMU 宿主 CPU，区分 guest busy、guest idle 和 I/O wait；
4. 用 GDB stub 采所有 vCPU 栈；
5. 需要时使用 guest profiler 记录锁等待、off-CPU、fault 和 I/O；
6. 一次只改一条机制，RV 与 LA 分别跑；
7. 端到端无收益就保留回退提交，不用微基准代替结果。

外部 GDB 会 stop-the-world，采样轮的 BuildStorm 时间不能与无采样基线比较。历史报告中 `496.08 s`
明确只用于热点发现，不能对比无采样 `483.23 s`。

## 10. xv6：编译宿主与目标启动必须分开

### 10.1 四平台作为 LLVM 编译宿主

历史四平台都在 Alpine musl 中完成 GCC/G++、make、Git、Rust/Cargo、LLVM 的真实工作，并用 LLVM
构建固定提交 `7d01506` 的 MIT xv6-riscv。产物包含：

```text
kernel/kernel
fs.img
user/_sh
```

再用 `llvm-readelf` 确认 RISC-V ELF。这证明四种 MOSS 平台能作为编译宿主，不表示四块目标硬件都
能启动为 QEMU virt 编写的 xv6 内核。

### 10.2 RISC-V QEMU

在 RV MOSS 原生编译和 LA MOSS 交叉编译得到的 xv6-riscv 产物，历史上都复制回宿主并由
`qemu-system-riscv64 -machine virt` 启动，进入 shell 后运行 `mkdir`、`echo`、`cat`、`grep`、
`wc`、`ls`、`rm` 通过。

这里应检查两个阶段：

1. MOSS 内构建命令返回 0、产物存在且 ELF 架构正确；
2. 新 QEMU 真正启动该产物并进入 xv6 shell。

### 10.3 VF2 xv6

VF2 移植基于 `GerfautGE/xv6-mars` 固定提交
`3ee0574c570fb750a6327b7c2c07a7f05634fb49`。历史构建依次遇到：

```text
clang: error: argument unused during compilation: '-fno-plt'
ld.lld: error: section '.text' address (0x0) is smaller than image base (0x10000)
error[E0463]: can't find crate for `core`
Assertion failed: fbn < MAXFILE (mkfs/mkfs.c: iappend: 253)
```

分别通过编译器能力探测、LLD `--image-base=0`、把可选 Rust 用户程序从默认构建解耦、采用可容纳
普通命令的 RELEASE 配置修复构建。

唯一实体启动进入 xv6 主函数后错误启动 JH7110 E24 hart 0：

```text
xv6 kernel is booting
hart 1 starting
sbi_trap_error: hart0: mcause=0x0000000000000005 mtval=0x0000000040048060
```

JH7110 只有 hart 1 至 4 是 U74 应用核，补丁随后限制拓扑。但按“实板接近需要人工复位即停止”的
安全规则，修复后没有第二次实板启动，所以状态是“构建通过、实板启动未通过”，不能覆盖失败事实。

### 10.4 LoongArch xv6

LoongArch 改写基于 `Junkher/xv6-loongarch` 固定提交
`fd994904f3230f0eaa51bda251f7e9c4bc7bf1a0`。第一轮入口的 `la.global $t0, 0f` 生成 GOT relocation，
LLD 21 对本地符号 addend 处理后取到错误地址，清 BSS 又把初始化数据变成零。

修复采用可核验的高半区入口序列、去掉错误的编译阶段 `-no-pie`、给 LLD `--image-base=0`，并恢复
缺失的 `_wc`、`_zombie`。QEMU LoongArch 最终进入 xv6 shell 并通过文件命令。

LS2K1000LA 实板 U-Boot 能加载并执行产物，但没有出现 `init: starting sh`，硬件 watchdog 自动回到
原厂 Linux。状态仍是“QEMU 启动通过、实板未通过”。

## 12. GDB 调试：先区分两种 GDB

MOSS 有两条完全不同的 GDB 路径：

1. **宿主机 GDB 连接 QEMU stub**：调试 MOSS 内核，QEMU 暂停所有 vCPU；
2. **MOSS 内原生 GDB**：在目标系统里通过 ptrace 调试用户程序。

看到“GDB 通过”时必须说清是哪一种。二者的断点实现、符号文件和故障层次不同。

### 12.1 宿主 GDB 调试 RISC-V MOSS 内核

先用和现场相同的 site 配置构建带 DWARF 的内核：

```sh
make DWARF=y site-rv
```

该命令编译后会正常启动 QEMU；看到 shell 后按 `Ctrl+A`、`X` 退出。真正带函数符号且与 site 配置一致
的 ELF 在 `build/site-rv/`，启动包装文件 `kernel-rv` 主要装载裸二进制，不适合还原 Rust 源码。
先找 ELF：

```sh
find build/site-rv -maxdepth 1 -name '*.elf' -type f
```

终端 1 启动暂停的 QEMU。命令与现场 `site-rv` 保持 2 核 2 GiB 和同一根文件系统，只多加 GDB：

```sh
qemu-system-riscv64 -machine virt -kernel build/site-rv/kernel-rv \
  -m 2G -smp 2 -nographic -snapshot \
  -drive file=images/rootfs/site-rv.img,format=raw,if=none,id=disk \
  -device virtio-blk-device,drive=disk \
  -device virtio-net-device,netdev=net \
  -netdev user,id=net -S -gdb tcp::1234
```

`make DWARF=y kernel-rv` 生成的是初赛/决赛配置。如果调试的是 `site-rv`，不要拿 `build/kernel-rv/`
中的 ELF 混用，即使两边函数名相同，feature、地址和代码布局也可能不同。

终端 2：

```sh
gdb-multiarch build/site-rv/moss-dev_riscv64-qemu-virt.elf
```

仓库目录名改变时 ELF 前缀也会改变，以上文件名要使用 `find` 的实际输出。在 GDB 中：

```gdb
set pagination off
target remote 127.0.0.1:1234
break __axplat_main
continue
info registers
x/16i $pc
bt
```

`-S` 表示 CPU 上电后暂停；`-gdb tcp::1234` 开启端口。没有 `-S` 时，连接前早期启动已经跑过，早期
断点可能永远遇不到。

### 12.2 宿主 GDB 调试 LoongArch MOSS 内核

同样先用 site 配置构建，QEMU 启动后按 `Ctrl+A`、`X` 退出：

```sh
make DWARF=y site-la
find build/site-la -maxdepth 1 -name '*.elf' -type f
```

终端 1：

```sh
qemu-system-loongarch64 -kernel build/site-la/kernel-la \
  -m 2G -smp 2 -nographic -snapshot -accel tcg,thread=multi \
  -drive file=images/rootfs/site-la.img,format=raw,if=virtio \
  -nic user,model=virtio-net-pci -S -gdb tcp::1234
```

终端 2：

```sh
gdb-multiarch build/site-la/moss-dev_loongarch64-qemu-virt.elf
```

然后使用同样的 `target remote`、断点、寄存器和反汇编命令。若 GDB 不能自动识别架构，先检查 ELF
是否真是 LoongArch；不要拿 `kernel-la` 包装文件或 RISC-V ELF 强制 `set architecture`。

### 12.3 地址到源码

只有一个异常 PC 时，最简单：

```sh
gdb-multiarch path/to/moss.elf
```

GDB 中：

```gdb
info symbol 0xffffffc0803f4f24
x/8i 0xffffffc0803f4f18
list *0xffffffc0803f4f24
```

也可以：

```sh
rust-objdump -d -C path/to/moss.elf | less
```

只看一段地址：

```sh
rust-objdump -d -C --start-address=0xffffffc0803f4ee0 \
  --stop-address=0xffffffc0803f4f40 path/to/moss.elf
```

`-C` 还原 Rust 符号。PC 在 allocator `deallocate` 并不自动证明 allocator 有 bug；要继续看被释放对象、
物理页生命周期和调用栈。现有完整案例见
[RISC-V page fault 复现](../history/repro/riscv-pagefault-20260812-run01/README.md)。

### 12.4 多核卡死

连接 QEMU stub 后：

```gdb
info threads
thread apply all bt 20
```

重点判断：

- 所有 CPU 是否都在 idle；
- 是否多个 CPU 等同一把锁；
- 一个 CPU 是否关中断后等待另一个 CPU 的 IPI；
- 是否反复停在用户地址，内核 ELF 无法展开；
- 是否只有一个 CPU 在网络/存储 poll，其他任务饿死。

仓库脚本 `scripts/sample_qemu_guest_stacks.py` 可周期采所有 vCPU 并生成 folded stacks。它失败后会重新
连接并 detach，避免异常退出把 QEMU 永久停住。外部采样看不到完整用户态栈，也不能准确统计 off-CPU
和锁等待；这些是方法边界。

### 12.5 QEMU 指令和异常日志

需要看最早异常时可给 QEMU 增加：

```text
-D tmp/qemu.log -d in_asm,int,mmu,cpu_reset,guest_errors
```

日志可能很大，只在最小复现中使用。常见技巧：

- 在异常入口断点，记录 PC、fault address、cause、BADI；
- 比较进入异常前一条指令和返回 PC；
- `SIGILL` 查指令编码与 CPU extension；
- `SIGBUS/AddressNotAligned` 查访存宽度和地址低位；
- page fault 查 VMA、PTE、权限位、物理 frame 引用；
- 多核 TLB 问题查 logical CPU ID 与 hardware hart ID，SBI/PLIC 必须使用正确硬件 ID。

### 12.6 MOSS 内原生 GDB

当前文档 [原生 GDB 双架构实现与验收指南](../history/boards/原生GDB双架构实现与验收指南.md) 记录 QEMU RISC-V64、
LoongArch64 的 GDB 15.2 通过：断点、backtrace、寄存器、内存、`stepi`、源码单步和 continue。

统一 QEMU 入口：

```sh
./scripts/run_qemu_gdb_native.sh all
```

板卡入口存在：

```sh
./scripts/run_hardware_gdb_native.sh vf2
./scripts/run_hardware_gdb_native.sh ls2k1000la
```

但现有正式指南明确写了当时没有完成硬件 GDB 实测，因此这里只把它们记为入口，不记为两块实板通过。

原生 GDB 所需内核能力包括 ptrace attach/stop、寄存器读写、目标内存读写、软件断点、单步、procfs
元数据和 wait/signal。软件断点写共享代码页前必须先做 COW，否则一个被调试进程会修改其他进程的
代码；提交 `bbeb77ec` 修复了这一点。

非 PIE 是当前显式验收边界，不等于所有 PIE/ASLR 调试场景都已验证。

## 13. 板级故障如何与应用故障分开

### 13.1 LS2K1000LA AHCI

龙芯启动早期依次遇到：探测期间错误睡眠触发调度断言、`PI=0`、HBA reset 状态丢失、COMRESET、
AHCI 成功后 SMP/IPI 崩溃。详细时间线见
[龙芯调试状态报告](../history/boards/龙芯二号板调试状态报告-20260808.md)。

排查顺序是设备树端口掩码 → BAR/MMIO → HBA reset → 端口状态机 → DMA/barrier/cache → IRQ → 块设备
注册 → rootfs。根文件系统还没挂载时，后面的 GCC、Redis 报错没有分析价值。

### 13.2 VF2 SD/MMC 和 GMAC

VF2 网络“link up”不等于数据面正确。要继续验证 PHY、DMA descriptor、cache、tail pointer、MAC
filter、中断和 RX/TX 恢复。详细依据见
[VF2 网卡驱动实现与验收](../history/boards/星光二号板网卡驱动实现与验收.md)。

SD 卡路径同时有硬件可靠性、VFS 语义和性能三层问题。若 Git/Vim 写入异常，先在 QEMU 同根文件系统
复现；QEMU 正常而 VF2 异常，再查 SD 驱动/cache。两边都异常，优先查共用 VFS/ext4。

### 13.3 串口复制与命令粘贴

历史量化结果中，开启同步逐字符 echo 时约 22 字节输入就可能失败；关闭 echo 后 518 字节可以通过。
根因不是 shell 命令长度，而是 UART RX IRQ 只唤醒任务，任务同步回显又阻塞 RX FIFO。

修复使用 8 KiB RX ring、批量回显、低延迟唤醒和记录级锁。文件复制应优先 HTTP/TFTP，并用 SHA-256
核对；base64 粘贴只适合小文件。完整方法见
[龙芯文件复制与串口排查](../history/boards/龙芯二号板文件复制与串口长输入排查.md)。

## 14. 现场应用命令速查

本节只放容易复制的普通命令。第一次先跑功能，再决定是否跑压力；不要一上来用复杂参数覆盖原始错误。

### 14.1 下载工具

```sh
curl -I https://pypi.org/
wget -O /dev/null https://pypi.org/
```

历史 `5c4b45c0` 修复 curl 连接准备时未绑定 socket 的 `getsockname` 语义。curl 能下载而 ping 失败时，
说明 TCP 数据面可能正常、raw ICMP 路径仍有问题；ping 正常而 curl 失败时，继续查 TCP、时间、CA、
TLS 和代理。

本地 HTTP 可用于把公网因素排除。宿主机：

```sh
python3 -m http.server 8000
```

板端：

```sh
wget http://192.168.88.1:8000/
```

VF2 当前宿主地址改为 `192.168.89.1`。本地成功、公网失败，问题在出口之后；本地也失败，先查板端
TCP、宿主防火墙和直连网口。

### 14.2 netcat

宿主监听：

```sh
nc -l 9000
```

板端连接：

```sh
nc 192.168.88.1 9000
```

输入一行并确认对端收到。再反向测试，才能同时覆盖板端 connect 和 accept。netcat 没有完整 HTTP/TLS
状态机，适合先判断纯 TCP，不替代 curl、SSH 或真实服务验收。

### 14.3 服务快速检查

| 应用 | 启动/检查 | 结束 | 成功证据 |
| --- | --- | --- | --- |
| nginx | `nginx -t`、`nginx`、`curl http://127.0.0.1/` | `nginx -s stop` | 配置通过且返回 HTTP 正文 |
| Redis | `redis-server --daemonize yes`、`redis-cli ping` | `redis-cli shutdown` | `PONG`、set/get 正确 |
| MariaDB | `service mariadb start`、`mysqladmin status` | `mysqladmin -uroot shutdown` | TCP/SQL、重启持久化 |
| PostgreSQL | `pg_ctl start`、`pg_isready` | `pg_ctl -m fast stop` | ready、SQL 查询、正常停机 |
| Mosquitto | `mosquitto -d` | `killall mosquitto` | pub/sub 收到固定正文 |
| SSH | `ssh root@127.0.0.1 'echo ssh-ok'` | 按所用 init 停 sshd | 远程命令返回 0 |

`killall` 只适合单独的现场测试实例。正式验收优先用服务自己的 shutdown 命令，并等待进程消失。

### 14.4 编译器快速检查

### 14.5 时间

生成板端可复制的 UTC 设置命令：

```sh
date -u '+busybox date -u -s %Y%m%d%H%M.%S'
```

把输出复制到板端执行。设置后检查：

```sh
date -u
```

HTTPS、APT 签名和 Git TLS 都依赖合理时间。调时应在软件启动前完成，不要在数据库或包管理运行中途
跳时钟。

### 16.2 目标端日志

优先看：

```sh
dmesg
cat /proc/interrupts
cat /proc/meminfo
cat /proc/mounts
ps
```

应用日志位置由根文件系统和配置决定：nginx 通常在 `/var/log/nginx/`，PostgreSQL/MariaDB 可从启动
命令或服务脚本找到，APK/APT 默认直接写终端。找日志使用：

```sh
find /var/log -type f
```

不要默认 `2>/dev/null`，它会隐藏真正错误。只有确认是预期噪声时才单独过滤。

### 16.3 QEMU 和宿主

QEMU 控制台记录用户输出、内核日志和 panic；`-d` 日志记录指令、异常和 MMU，但不替代内核日志。
宿主还应保存 QEMU 退出码、CPU/内存占用和工作镜像 fsck：

```sh
e2fsck -fn images/rootfs/site-rv.img
```

基准镜像正在运行或以读写方式挂载时不要 fsck。QEMU `-snapshot` 下基准镜像未被写入，持久化验收
必须检查实际工作副本。

### 16.4 原始错误的记录格式

每次新问题按下面格式写进日志或 issue：

```text
platform=
git_commit=
kernel_sha256=
rootfs_or_partition=
cpu_memory=
exact_command=
exit_code=
last_success_marker=
first_error_line=
recovery_result=
filesystem_check=
```

“卡住了”“网络不行”无法复现；最后成功标记和第一条错误通常比最后一屏重复日志更有价值。

## 18. 现场安全边界

### 18.1 什么时候停止实板尝试

满足任一条件就停止当前路径，先恢复原厂 Linux：

- 只能靠反复串口输入或人工复位维持进度；
- watchdog 无法保证自动返回；
- 目标分区仍挂载却准备 fsck、刷写或复位；
- 同一失败重复出现且没有新的单变量证据；
- 串口已失控，无法确认写盘和卸载状态。

成功或失败都应：结束应用 → `sync` → 正常退出/卸载 → 自动复位 → Linux 只读 fsck。前面的应用标记
通过但文件系统检查失败，整轮仍不算通过。

### 18.2 烧录前

```sh
lsblk -f
findmnt
sha256sum image-file
```

确认设备和分区，不能只看 `/dev/sdX` 名称。分区镜像与整盘镜像不同；把分区镜像写到整盘会破坏分区
表。详细流程只使用当前板卡烧录文档，不从旧聊天或 `tmp/` 脚本拼接命令。

### 18.3 修改代码的原则

1. 先最小复现并保存原始错误；
2. 与 Linux 同命令、同输入对照；
3. 找到共享语义和真实调用链；
4. 用函数封装修复，不散落应用特判；
5. 先 QEMU RV/LA，再验证相关实板；
6. 网络共用层修改必须确认不影响 VF2；
7. 文件系统修改必须跑持久化与 fsck；
8. 性能修改必须保留基线和回退节点。

### 18.4 仍然存在的明确边界

- 当前历史证据不能证明所有应用已在 `a67688d7` 之后完整重跑；
- LS2K 的历史 app 通过与后来 netlink 失败都是真实记录，必须按时间理解；
- 在线 pip `requests` 在最新网络修复后的最终安装原文尚未归档；
- Alpine MariaDB 的目标端 `mariadb-install-db` 没有纳入通过；
- 历史 MariaDB 优雅停机曾超时，KILL/recovery 通过不等于 graceful shutdown 通过；
- System V dynamic shared memory 未作为 PostgreSQL 历史合同；
- OpenSSH seccomp 只做兼容返回，不是完整 sandbox；
- 原生 GDB 的正式文档只确认 QEMU 双架构，实板入口存在但不能写成已验收；
- VF2 与 LS2K 的 xv6 实板启动没有通过；
- X11 只有历史说明，没有完整运行证据；
- QEMU `-snapshot` 不能证明根文件系统持久化。

## 19. 到现场后的推荐顺序

1. 记录提交、内核哈希、根分区、CPU、内存和 UTC。
2. 运行第 0 节系统检查，先确认没有挂错根文件系统。
3. 检查 `ip addr`、路由、DNS、本地 HTTP，再检查公网 HTTPS。
4. 对目标应用先运行普通功能命令，保留返回值和日志。
5. 功能通过后才跑压力或并发。
6. 失败时按 syscall/子系统缩小，不直接重烧镜像。
7. 在 Linux 上运行同一输入，比较 errno、结构体、poll 事件和文件结果。
8. 修改共用函数，先回归两个 QEMU 架构，再碰实板。
9. 结束后 sync、正常退出、自动恢复和 fsck。
10. 把新原始日志放入仓库 `tmp/`，把最终结论补进受版本控制文档。

这套顺序的目标不是“尽量少报错”，而是让每一个报错都能回答：发生在哪一层、Linux 为什么不同、
修改为什么正确、是否影响另一架构，以及用什么证据证明已经闭环。
