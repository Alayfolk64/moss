# lmbench 第一轮低风险优化记录

记录日期：2026-06-13

## 1. 背景

比赛使用的 lmbench 脚本会反复执行短小操作，用来放大内核固定开销。与本轮修改关系较大的项目有：

- `lat_syscall`：系统调用进入、返回及公共检查开销。
- `lat_pipe`：父子进程通过两个管道传递 1 字节数据，观察管道操作和进程切换延迟。
- `bw_pipe`：连续传输较大数据，观察管道吞吐。
- `lat_ctx`：多个进程通过管道传递 token，观察上下文切换成本。

代码分析发现，当前实现里有几类工作会在热路径上重复发生：

1. 没有进程使用 ptrace 时，每次返回用户态仍会访问 ptrace 全局表。
2. 管道已经可读或可写时，仍然先创建 future 和 waker，再尝试实际读写。
3. 管道操作结束后会调用 `PollSet::wake()`，即使没有任务等待，也会进入惰性初始化和锁路径。

这些操作本身没有错，但对 lmbench 这类微基准不划算。一次额外的锁、一次 `Arc` 引用计数或一次堆分配，都会直接反映到微秒级结果中。

## 2. LTP 约束

性能优化不能破坏现有 LTP 行为。项目当前运行的 LTP 列表覆盖了 pipe、ptrace、signal、poll、fork、exec 和 wait 等接口，其中 pipe 相关用例会检查：

- 管道方向错误时返回 `EBADF`。
- 非阻塞读写返回 `EAGAIN`。
- 读端关闭后写入产生 `SIGPIPE`，同时返回 `EPIPE`。
- 写端关闭后，读操作在数据耗尽时返回 EOF。
- 阻塞读写可以被信号打断并返回 `EINTR`。
- `PIPE_BUF` 范围内的写入及部分传输行为。
- `F_GETPIPE_SZ`、`F_SETPIPE_SZ` 和 `FIONREAD`。

ptrace 用例则依赖 trace 关系、stop 状态、wait 事件、attach、detach 和信号转发。

因此，这一轮只做“状态未启用时提前返回”和“第一次尝试即可完成时直接返回”。只要操作需要阻塞，或者相关功能已经启用，代码仍进入原来的完整路径。

## 3. 修改范围

本轮修改涉及以下文件：

- `kernel/src/file/pipe.rs`
- `kernel/src/syscall/task/ptrace.rs`
- `vendor/axpoll/src/lib.rs`
- `vendor/axpoll/tests/tests.rs`
- `vendor/axsync/src/mutex.rs`
- `vendor/axtask/src/task.rs`
- `vendor/axpoll/.cargo-checksum.json`
- `vendor/axsync/.cargo-checksum.json`
- `vendor/axtask/.cargo-checksum.json`
- `Cargo.toml`
- `Cargo.lock`

vendor 源码发生变化后，Cargo 会校验 `.cargo-checksum.json`。因此同步更新了对应文件的 SHA-256，避免离线构建时把本地修改误判为损坏的 vendored dependency。

## 4. ptrace 空状态快路径

### 4.1 原来的路径

用户任务每次从内核返回用户态前都会检查信号。信号检查又会调用：

```text
ptrace_wait_if_stopped()
ptrace_is_traced()
```

这两个函数原来都会直接获取 `PTRACE_TABLE` 的全局自旋锁。绝大多数程序没有被 ptrace 跟踪，但仍要为每次系统调用支付查表成本。

lmbench 的 `lat_syscall null` 会反复执行 `getppid()`，这类公共路径开销会被完整计入结果。read、write、stat、pipe 等测试也会受到影响。

### 4.2 修改方式

在 `kernel/src/syscall/task/ptrace.rs` 中增加：

```rust
static PTRACE_ACTIVE: AtomicBool = AtomicBool::new(false);
```

没有任何 trace 关系时，以下函数读取原子标志后直接返回：

```text
ptrace_has_wait_target()  -> false
ptrace_take_wait_event()  -> None
ptrace_wait_if_stopped()  -> return
ptrace_is_traced()        -> false
```

`PTRACE_TRACEME` 或 `PTRACE_ATTACH` 成功建立关系时，将标志设为 `true`。进程退出或 `PTRACE_DETACH` 删除关系后，根据表是否为空更新标志。

### 4.3 为什么不改变 ptrace 语义

`PTRACE_ACTIVE == false` 只表示 ptrace 表为空。此时原实现查表后也会得到“未跟踪”，所以提前返回与原结果一致。

建立 trace 关系时，代码先持有 `PTRACE_TABLE` 锁，再把原子标志设为 `true` 并插入记录。其他任务看到 `true` 后仍会获取原来的锁，不会观察到半写入状态。

ptrace 已启用时没有绕过任何检查。stop、wait、信号截获、权限和错误码仍由原代码处理。

### 4.4 预期影响

这项修改主要减少普通系统调用返回路径上的全局锁访问，可能改善：

- `lat_syscall`
- `lat_sig`
- `lat_pipe`
- 其他由大量短系统调用组成的测试

它不会提高 ptrace 自身的执行速度。ptrace 启用后仍走完整路径。

## 5. pipe 同步成功快路径

### 5.1 原来的路径

管道的 `read()` 和 `write()` 原来无条件执行：

```text
block_on()
  -> 创建当前任务的强引用
  -> 分配 AxWaker
  -> 构造 Context
  -> poll interruptible future
  -> 尝试实际读写
```

即使管道中已经有数据，或者缓冲区有足够空间，也要先完成这些准备工作。

在 lmbench 的管道 ping-pong 中，进程被唤醒后通常马上执行一次很小的读写。此时 future 只会被 poll 一次，然后立即返回。future 没有提供阻塞能力，却仍产生了创建 waker、维护 `Arc` 和进入异步状态机的成本。

### 5.2 修改方式

把不负责阻塞的实际操作拆成两个内部函数：

```text
try_read()
try_write()
```

新的读路径为：

```text
检查 fd 方向和零长度
检查当前任务是否已被信号中断
直接 try_read()
  -> 成功、EOF 或其他错误：立即返回
  -> 非阻塞且 WouldBlock：返回 EAGAIN
  -> 阻塞且 WouldBlock：进入原 poll_io 路径
```

写路径采用同样结构：

```text
检查 fd 方向和零长度
检查当前任务是否已被信号中断
直接 try_write()
  -> 全部写完：立即返回
  -> 非阻塞且写入部分数据：返回已写字节数
  -> 非阻塞且没有空间：返回 EAGAIN
  -> 阻塞且没有写完：进入原 poll_io 路径继续等待
```

真正需要等待时，仍然调用原来的：

```rust
block_on(poll_io(...))
```

### 5.3 为什么保留 interrupt 检查

原来的 `poll_io()` 外层使用 `interruptible()`。future 第一次被 poll 时，会先读取并清除任务的 interrupt 标志；如果已有待处理信号，系统调用返回 `EINTR`，不会先操作管道。

如果同步快路径直接读写，就可能在信号已经到达时抢先传输数据，改变 LTP 可观察到的顺序。

为保持原行为，在 `TaskInner` 中抽出：

```rust
pub fn take_interrupt(&self) -> bool
```

原来的 `poll_interrupt()` 改为调用该函数，pipe 同步路径也调用同一个函数。两条路径读取和清除的是同一原子状态，因此 `EINTR` 的优先级没有变化。

### 5.4 保留的 pipe 行为

`try_read()` 和 `try_write()` 只是把原闭包中的同步读写代码移到独立函数，没有修改缓冲区规则：

- 读错管道端仍返回 `EBADF`。
- 写入无读端管道仍发送 `SIGPIPE` 并返回 `EPIPE`。
- 空管道且写端关闭时仍返回 EOF。
- 非阻塞操作没有进展时仍返回 `EAGAIN`。
- 非阻塞写已经传输一部分数据时返回实际字节数。
- 阻塞写只完成一部分时继续等待剩余空间。
- 成功读后仍唤醒等待写入的任务。
- 成功写后仍唤醒等待读取的任务，并保留异步 I/O 通知。
- 管道容量、`FIONREAD` 和 poll 就绪条件没有变化。

### 5.5 预期影响

这项修改减少立即成功的 pipe 操作中的 future 和 waker 成本，主要面向：

- `lat_pipe`
- `bw_pipe`
- `lat_ctx`

实际收益取决于管道在测试时有多少操作可以立即完成。发生阻塞时，执行流程与修改前基本相同。

## 6. PollSet 空唤醒快路径

### 6.1 原来的路径

pipe 每次成功读写都会唤醒另一侧的等待者：

```rust
self.shared.poll_rx.wake();
self.shared.poll_tx.wake();
```

`PollSet` 使用 `Lazy<Mutex<Inner>>`。原来的 `wake()` 会直接访问 `Lazy` 并获取锁。第一次调用可能创建一个容量为 64 的 waker 数组，即使当前没有任何任务注册等待。

在 lmbench 中，许多 wake 发生时对端正在运行或尚未进入等待状态。此时唤醒集合为空，初始化数组和加锁没有实际作用。

### 6.2 修改方式

`PollSet` 增加一个原子标志：

```rust
has_waiters: AtomicBool
```

注册 waker 时，在持有 `inner` 锁的情况下把标志设为 `true`。`wake()` 先读取该标志：

```text
false -> 直接返回 0
true  -> 获取 inner 锁并执行原唤醒流程
```

取走所有 waker 后，将标志恢复为 `false`。

### 6.3 并发时序

`has_waiters` 只是空集合提示，不代替 `inner` 锁。真正的 waker 数组仍由原来的互斥锁保护。

注册顺序是：

```text
获取 inner 锁
设置 has_waiters = true
写入 waker
释放 inner 锁
```

唤醒顺序是：

```text
读取 has_waiters
获取 inner 锁
取走当前 waker 数组
设置 has_waiters = false
释放 inner 锁
唤醒取出的任务
```

如果注册和唤醒并发，锁会串行化数组修改。唤醒完成后才注册的 waker 会留给下一次事件；这与原实现一致。

### 6.4 回归测试

在 `vendor/axpoll/tests/tests.rs` 增加了 `register_after_empty_wake`：

1. 对空 PollSet 调用 `wake()`，应返回 0。
2. 随后注册一个 waker。
3. 再次调用 `wake()`，应返回 1。
4. 计数器必须只增加一次。

该测试用于防止空唤醒快路径错误地阻止后续注册。

## 7. 本轮没有修改的部分

第一轮没有处理下列问题：

- `select` 零超时路径中的 `Vec` 分配和 `Arc` 克隆。
- 每次系统调用的 timer accounting。
- async fcntl 全局表查询。
- pipe 的专用等待队列和调度器直接交接。
- fork、exec、open、mmap 等中高风险路径。

这些改动牵涉更多错误码、信号、权限、页表或资源继承语义，需要单独对照 LTP 用例处理。

## 8. 检查结果

本轮验收范围限定为静态检查，没有取得可用的内核编译、LTP 或 lmbench 结果。完成的检查包括：

- `git diff --check` 无补丁格式错误。
- 检查 pipe 的 `EINTR`、`EAGAIN`、`EPIPE`、EOF 和部分写入路径。
- 检查 ptrace 标志在 attach、traceme、detach 和进程退出时的更新。
- 检查 PollSet 注册和唤醒时的锁与原子操作顺序。
- 检查所有修改过的 vendor 文件，其 SHA-256 与 `.cargo-checksum.json` 一致。

因此，目前能确认的是代码路径和语义保持一致。性能提升幅度以及 LTP 是否完全无回归，仍需以后用相同镜像、相同 QEMU 参数进行实测，不能从静态检查直接推导。

## 9. 预期结果

本轮优化针对的是高频、无状态或立即成功的路径：

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 无 ptrace 关系的 syscall 返回 | 获取全局 ptrace 表锁 | 一次原子读取 |
| 可立即完成的 pipe 读写 | 创建 future 和 waker 后读写 | 直接读写 |
| 无等待者的 PollSet wake | 初始化或访问内部数组并加锁 | 一次原子读取后返回 |
| 真正需要阻塞的 pipe 操作 | `poll_io` 等待 | 仍使用 `poll_io` |
| ptrace 已启用 | 完整状态检查 | 完整状态检查 |

这类修改的好处是影响范围清楚：正常热路径少做工作，复杂状态继续使用原实现。它不会消除 pipe 的调度和上下文切换成本，但能减少每次传递附带的固定开销。

## 10. starry-smoltcp 依赖固定

### 10.1 编译失败现象

完成 loopback 路径优化后，`axnet` 编译时出现十个接口缺失错误，涉及：

- `TxToken::set_dst_addr()`
- `DeviceCapabilities::loopback_transmission_unit`
- `IpAddress::is_loopback()`
- UDP socket 的 `connected_endpoint()`、`set_connected_endpoint()` 和 `enqueue_recv_with()`

这些接口都已经存在于仓库的 `vendor/starry-smoltcp`，调用位置与定义也能逐项对应。报错说明构建时的 `axnet` 没有使用这份定制源码，而是解析到了未包含上述扩展的注册表版本。

### 10.2 根因

`vendor/axnet/Cargo.toml` 依赖的包名是 `starry-smoltcp`，库名仍为 `smoltcp`。此前 `Cargo.lock` 将该包记录为 crates.io 来源，根目录的 `[patch.crates-io]` 又没有覆盖它。

在完全使用本地 vendor 目录的环境里，这种配置有时也能工作，但依赖选择会受到 Cargo 配置和缓存状态影响。对于已经直接修改过源码的依赖，只更新 `.cargo-checksum.json` 不足以保证所有构建环境都选中仓库内版本。

### 10.3 修复方式

根 `Cargo.toml` 增加：

```toml
starry-smoltcp = { path = "vendor/starry-smoltcp" }
```

同时删除 `Cargo.lock` 中 `starry-smoltcp` 的 registry `source` 和 `checksum` 字段，使锁文件按 path 包记录它。

本次修复没有修改 TCP、UDP、路由或系统调用逻辑，只固定依赖来源。静态解析命令显示：

```text
starry-smoltcp v0.12.1-preview.1 (D:\2026OS\moss\vendor\starry-smoltcp)
└── axnet v0.2.2-preview.1
```

因此，`axnet` 会使用与本轮 loopback 优化配套的 API。LTP 所依赖的网络语义没有在这次修复中发生变化。

## 11. 第二轮：调度与同步低风险优化

### 11.1 优化目标

`lat_pipe` 每轮在两个进程之间传递 1 字节数据。`lat_ctx` 使用多组管道传递 token，并把管道本身的开销从结果中扣除。两项测试都会频繁执行下面的流程：

```text
尝试读取空管道
注册 waker 并阻塞
对端写入并唤醒
任务重新进入运行队列
```

第一轮已经减少了管道可立即读写时的 future 和 waker 开销。这一轮继续处理真正发生阻塞时的固定成本，但不修改调度策略、时间片、信号顺序和 pipe 的错误码。

### 11.2 PollSet 唤醒时复用存储

`PollSet` 内部保存一个容量为 64 的 waker 数组。修改前，每次有效唤醒都会执行：

```rust
core::mem::replace(&mut *guard, Inner::new())
```

`Inner::new()` 会重新分配数组。旧的 `Inner` 在锁外析构，并唤醒其中的任务。这样能避免在持锁状态下运行 waker，但 `lat_pipe` 和 `lat_ctx` 的每次 token 传递也会多出一次堆分配和释放。

现在由 `Inner::take_wakers()` 把已初始化的 waker 移到栈上数组，随后把原数组的游标清零：

```text
持有 PollSet 锁
把有效 waker 移到栈上
清空游标并保留原堆内数组
释放锁
逐个唤醒任务
```

原来的堆内数组会被下一轮注册继续使用。waker 仍在锁外执行，所以重入注册不会死锁，唤醒数量和容量覆盖规则也没有变化。

新增的 `repeated_register_and_wake` 测试连续执行 128 轮注册和唤醒，用来检查存储复用后不会遗留旧 waker，也不会漏掉新注册。

### 11.3 Mutex 无等待者解锁快路径

pipe 的环形缓冲区由 `axsync::Mutex` 保护。修改前，每次解锁都会调用：

```rust
self.event.notify(1);
```

大多数 pipe 读写没有线程等待这把锁。此时通知不会唤醒任务，却仍可能初始化 `Event` 的内部队列并执行同步操作。

`RawMutex` 现在维护 `waiters: AtomicUsize`。只有线程已经注册 listener、确认锁仍被占用并准备阻塞时，才计入等待者。解锁路径在等待者数量为零时直接返回，不再访问 `Event`。

为避免丢唤醒，等待和解锁之间采用下面的顺序：

```text
等待方：注册 listener -> waiters 加一 -> 再次读取 owner
解锁方：清空 owner -> 读取 waiters -> 必要时 notify
```

`owner` 和 `waiters` 的交叉检查使用 `SeqCst`。如果解锁方看到零个等待者，随后登记的等待方会在再次读取 `owner` 时看到锁已经释放，不会进入休眠；如果解锁方看到等待者，则继续调用原来的 `Event::notify(1)`。

这项修改没有改变锁的所有权检查、竞争时的自旋次数、listener 排队方式或一次只唤醒一个等待者的行为。

### 11.4 对 lmbench 和 LTP 的影响

预期受益项目如下：

| 项目 | 减少的工作 |
| --- | --- |
| `lat_pipe` | 有效唤醒时的 waker 数组分配；pipe 缓冲锁的空通知 |
| `lat_ctx` | 每次 token 交接附带的相同固定开销 |
| `bw_pipe` | 高频缓冲区加锁和解锁时的空通知 |
| 其他 pipe、poll、socket 路径 | 使用 `PollSet` 或无竞争 `axsync::Mutex` 时的固定开销 |

LTP 可观察到的 pipe 行为没有变化。阻塞读写仍通过原来的 `poll_io` 和 `block_on`，信号中断、EOF、`EAGAIN`、`EPIPE`、部分写入以及 poll 就绪条件均未改动。Mutex 有真实等待者时也继续走原通知路径。

### 11.5 本轮检查

按照本次任务约束，没有编译内核，也没有运行 lmbench、LTP 或单元测试。完成的静态检查包括：

- `git diff --check` 无格式错误。
- 检查 `PollSet` 中每个初始化的 waker 都被移出并恰好唤醒一次。
- 检查唤醒期间新注册的 waker 会留在复用后的原数组中，等待下一次事件。
- 检查 Mutex 等待者登记、解锁检查和取消等待之间不存在已知的丢唤醒窗口。
- 更新 `vendor/axpoll` 和 `vendor/axsync` 的 SHA-256 校验记录。

性能提升幅度仍需以后使用相同镜像和 QEMU 参数实测。本轮能确认的是热路径减少了堆分配和无效通知，阻塞与唤醒语义保持不变。
