# RISC-V BuildStorm AddrSpace 写锁持有者报告

## 结论

本轮已经在 `AddrSpace` 写锁的获取与释放边界加入持有者探针，并从全新
RISC-V 镜像完整跑完 cagent、tg-xtask 预构建和正式 BuildStorm。结果明确：

1. 写锁累计持有时间最大的不是 `mmap` 或 `mprotect`，而是
   `exit clear`、`exec clear` 和 `clone`。
2. `mprotect` 调用次数极多，但单次写锁平均只持有约 39 微秒；它已不是
   长临界区。
3. 第一版“每次回收 256 个 4 KiB 页”的实现产生了 39 万到 70 万次清理批次，
   回收线程占两个构建阶段非 idle CPU 样本的 30.8%，并使完整编译比上一轮
   慢约 4%。这是一项已经由完整测量否定的方案。
4. 退出和 `execve` 的旧地址空间已经死亡，不再承担正常用户缺页。正确的近期
   处理是把整次清理移出退出/exec 的同步路径，由后台线程对一个旧地址空间
   清理一次，而不是为了反复释放“死亡地址空间的锁”切割 VMA。
5. 仍然作用于活地址空间的 `clone` 才是下一项需要真正按
   prepare/execute/commit 拆分的长写锁路径。

本报告中的完整性能数据对应提交 `965bd66e` 的第一版分批回收实现。根据本轮
证据，代码随后已改为异步整空间清理；后者只做构建和短时正确性验收，本报告
不会把尚未完整测量的修正版宣称为提速。

## 写锁持有者排名

### 预构建

普通持有者按 1/16 抽样。表中的“估算调用”是抽到的次数乘 16；
`exit clear` 和 `exec clear` 没有抽样，因此它们的批次数是精确值。

| 持有者 | 估算累计持锁 | 估算调用/精确批次 | 平均每次 | 最大实测样本 |
|---|---:|---:|---:|---:|
| `exit clear` | **306.57 s** | 393,719 | 0.779 ms | 48.75 ms |
| `exec clear` | **252.87 s** | 708,143 | 0.357 ms | 7.48 ms |
| `clone` | **247.24 s** | 1,552 | **159.31 ms** | **445.26 ms** |
| `munmap` | 87.17 s | 50,240 | 1.735 ms | 166.25 ms |
| `mprotect` | 57.56 s | 1,468,896 | **0.039 ms** | 25.70 ms |
| `madvise` | 25.30 s | 4,320 | 5.857 ms | 207.29 ms |
| `mmap` | 4.69 s | 104,912 | 0.045 ms | 0.57 ms |
| 其他 | 1.51 s | 32,704 | 0.046 ms | 14.15 ms |
| `mremap` | 0.06 s | 1,216 | 0.047 ms | 0.19 ms |
| fault fallback / file eviction | 0 | 0 | 0 | 0 |

`mprotect` 的估算调用数 1,468,896 与独立精确计数 1,468,873 只差 23 次，
说明 1/16 持有者抽样在这一高频事件上非常稳定。

|---|---:|---:|---:|---:|

| `clone` | **125.41 s** | 1,024 | **122.47 ms** | **356.82 ms** |

| `munmap` | 38.82 s | 21,712 | 1.788 ms | 171.81 ms |

| `madvise` | 9.55 s | 2,336 | 4.089 ms | 67.78 ms |

累计持有时间是跨任务、跨地址空间的 task-time。不同地址空间上的锁可以同时
被持有，所以各行不能相加后当作墙钟时间。它适合判断持有者量级和长尾，
不适合直接计算阶段占比。

## 为什么确认是 clear 和 clone，而不是 mprotect

`mprotect` 的特点是调用多、单次短：

- 预构建精确调用 1,468,873 次；
- 每次只验证和访问 1 个 VMA；
- 写锁平均约 39 微秒；
- 累计持有时间只有 `exit clear` 的 18.8%。

`clone` 刚好相反：调用量小，但单次长达 122～159 毫秒，最大样本达到
356～445 毫秒。在这段时间内，同一进程地址空间的缺页读锁、futex 用户地址
访问以及其他内存系统调用都会被阻塞。它是真正会把活地址空间短时间串行化的
写锁持有者。

`exit clear` 和 `exec clear` 的总量最大，但本轮实现把每个旧地址空间切成
大量 1 MiB 虚拟区间，所以表中的“次数”实际是清理批次，并不等于退出或
exec 的进程数。其异常数量本身就是实现问题的证据。

## 第一版分批回收为什么变慢

第一版每批最多处理 256 个 4 KiB 页，即 1 MiB 虚拟地址范围。每一批都会：

1. 获取 `AddrSpace` 写锁；
2. 从 `BTreeMap` 再次寻找第一个 VMA；
3. 对 VMA 执行 `unmap` 或 `shrink_left`；
4. 遍历该虚拟范围的页表；
5. 释放锁；
6. 重新入队并 `yield`。

完整预构建中发生：

- 393,719 个 exit 清理批次；
- 708,143 个 exec 清理批次；
- 合计 1,101,862 次写锁、BTree 和调度循环。

正式阶段还有 555,836 个清理批次。虚拟地址范围可能很大而驻留 PTE 很少，
按虚拟字节切批会反复扫描稀疏范围。CPU 栈直接显示回收线程落在
`clear_batch -> shrink_left/unmap_area -> backend unmap -> page-table unmap`
以及 BTree 删除/再平衡中。

| 阶段 | CPU 总样本 | idle | 非 idle | 分批回收样本 | 占非 idle |
|---|---:|---:|---:|---:|---:|
| 预构建 | 44,782 | 26,670 | 18,112 | 5,573 | **30.77%** |
| 正式阶段 | 26,735 | 18,600 | 8,135 | 2,501 | **30.74%** |

这不是“释放锁后提高并行度的必要代价”，因为这些锁属于已经退出或已经被
exec 替换的旧地址空间。正常 rustc 线程不会再进入这些地址空间处理新缺页。
把旧地址空间切成数十万批，几乎没有可受益的活 reader。

## AddrSpace 等待也没有改善

从 workload off-CPU folded 栈按最终阻塞点重新聚合：

| 阶段 | 版本 | 读锁等待 | 写锁等待 | 合计 |
|---|---|---:|---:|---:|
| 预构建 | 上一轮 | 88.25 s | 9.81 s | 98.06 s |
| 预构建 | 本轮分批回收 | **176.84 s** | **14.20 s** | **191.05 s** |
| 正式 | 上一轮 | 59.46 s | 4.99 s | 64.45 s |
| 正式 | 本轮分批回收 | **87.96 s** | **8.67 s** | **96.63 s** |

预构建 AddrSpace 总等待增加 94.82%，正式阶段增加 49.95%。原因包括：

- 一个后台 writer 高频到达，使 writer-preference 锁反复阻止新 reader；
- 回收线程重复占用 CPU、页表锁和底层 backend 锁；
- 每批末尾的 `yield` 增加调度开销；
- 多次 VMA 缩减和 BTree 更新没有减少需要回收的实际 PTE。

这组结果同时否定了“只要把长写锁切短就一定更快”。锁临界区是否应切分，
必须先判断该锁是否仍保护活读者，以及切分是否增加重复工作。

## 已采用的修正

根据完整测量，退出和 exec 回收保留异步队列，但改成：

```text
exit / exec
    |
    +-- 切断当前任务与旧 AddrSpace 的正常使用
    |
    +-- 将旧 AddrSpace 放入后台回收队列
            |
            +-- 每个请求取得一次写锁
            +-- 一次 clear 完整回收
```

这样仍然把昂贵的逐 VMA、逐 PTE 清理移出了退出和 `execve` 的同步关键路径，
但不再重复拆 VMA、入队和调度。它不是最终的“锁外回收”：

- 页表和 `MemorySet` 当前仍共同位于 `AddrSpace` 内；
- backend `unmap` 还要维护 COW 引用、文件映射反向记录和页表项；
- 在没有先转移这些对象所有权之前，不能把 `clear()` 简单搬到锁外。

真正的锁外回收需要先在短临界区中把已死亡地址空间的整个
`MemorySet + PageTable` 所有权摘走，再让独占回收对象执行 backend 清理。
这需要同时保证退出任务不再使用旧 SATP，不能用一段未经验证的
`unsafe` 绕过现有所有权模型。

## 下一步优先级

### 1. 拆 clone，而不是继续拆 mprotect

`clone` 是活地址空间上最长的写锁持有者。建议按 generation 校验拆成：

1. prepare：短锁内记录 VMA、backend 引用和父页表版本；
2. execute：锁外分配子页表、复制元数据、准备 COW 变更；
3. commit：重新取写锁，校验 generation，批量更新父 PTE 并安装子映射；
4. stale：有限次数重新 prepare，之后才回退到完整锁路径。

难点是 `clone_map` 会把父页表的可写 PTE 改成 COW，只复制子页表而不提交父
PTE 会破坏语义。因此这里不能只把现有函数机械地移到锁外。

### 2. 为死地址空间增加可转移的 ReclaimImage

将 `MemorySet`、用户页表根和 backend 清理状态组合成只被回收线程拥有的
`ReclaimImage`。退出/exec 在切换页表后用短锁完成所有权转移，后台不再需要
取得原 `AddrSpace` 写锁。这才是严格意义上的“锁内摘除、锁外回收”。

### 3. 回收按驻留对象组织，不按虚拟字节组织

如果仍需要分批释放内存，批次应以以下对象计数：

- 实际存在的 PTE；
- backend 中实际登记的 COW/file pages；
- 或整个 VMA。

不能再按 1 MiB 虚拟范围切批。后者对稀疏映射的复杂度和实际驻留页面数不
成比例。

### 4. 保留当前持有者探针

下一次完整测量应继续保留这些事件，并额外记录：

- 每次 `exit/exec` 的 VMA 数、驻留 PTE 数和回收页数；
- `clone` 的 VMA/PTE 数、父 PTE COW 更新数；
- 写锁等待队列中的 reader/writer 数；
- 后台回收队列长度与积压页数。

只有在下一次干净镜像完整运行中，正式编译时间低于 567.41 秒且 AddrSpace
读锁等待回落，才能认为回收/clone 改造真正有效。
