# RISC-V BuildStorm `memset` 字宽优化失败记录

## 结论

本轮不能作为性能结果。

`lwext4` 的弱符号 `memset` 从逐字节循环改为“对齐头部 + 4 个 `size_t`
批量写入 + 尾部”后，使用全新官方 RISC-V 镜像进行的第一次全程测试在
预构建阶段发生文件系统内容异常：

- `ar` 先报告
  `00c879ee3285a50d-montgomery.o: file format not recognized`；
- 正式阶段复用同一个 `target` 后，汇编器报告同一路径
  `Is a directory`；
- BuildStorm 以 `rc=101` 失败，计时阶段仅运行 92.15 秒；
- 运行器在 315.94 秒收到 profile-ready 标记，但这是测试失败后的退出，
  不是完整 BuildStorm 成功。

因此，本目录中的 112 张 SVG 只记录了失败前后的局部执行路径，不得和完整
基线比较，也不能用于计算优化收益。

## 测试条件

- 架构：RISC-V 64
- QEMU：8 GiB、8 vCPU、`-snapshot`
- 根文件系统：从官方压缩镜像重新解压
- 镜像 SHA-256：
  `c03c6091eb1c400d4c1f400130d11810b00e18811d4e5c201e7f75802dfafde0`
- 内核：`PROFILE=y`
- 采样丢失：profile dump 正常生成；SVG 共 112 张

## 失败证据

关键日志位于 `console.log`：

1. 第 301–355 行：预构建阶段的 `ring` 对象文件格式错误；
2. 第 391–448 行：正式阶段重新生成同一路径时发现目标已成为目录；
3. 第 458 行：
   `BUILDSTORM_COMPILE mode=multi ok=false rc=101 elapsed_s=92.15`。

日志还出现 4 次 inode 元数据缓存失效警告。该警告在早期成功基线中也曾
偶发一次，所以单凭警告不能证明 `memset` 写越界；但本轮警告次数上升并和
目录项异常同时出现，说明必须按文件系统一致性故障处理。

## `memset` 的独立验证

对实际从 RISC-V `liblwext4-riscv64.a` 提取出的 `ulibc.c.o` 进行了符号重命名，
随后使用 `riscv64-linux-musl-gcc` 静态链接，并由 `qemu-riscv64` 执行测试。

覆盖范围：

- 起始地址偏移：0–31；
- 长度：0–4096；
- 填充值：`0`、`1`、`0x55`、`0x80`、`0xff`、`0x1234`；
- 总用例数：786,624；
- 每个用例检查返回地址、目标区内容及前后哨兵。

全部用例通过。反汇编还确认：

- 填充值扩展常量为 `0x0101010101010101`；
- 主循环每轮执行 4 条对齐 `sd`，写 32 字节；
- 头尾仅使用 `sb`；
- 未发现目标范围外写入。

这排除了普通的长度、对齐、填充值扩展错误，但不能排除更宽存储改变并发
可见性后暴露既有竞态。

## 全新镜像复现

第二次运行复用了完全相同的内核二进制，只重新解压官方镜像并再次校验
SHA-256。它在预构建约 90 秒、进度 101/446 时触发：

```text
Unhandled Supervisor Page Fault @ 0xffffffc0802f9af4
fault_vaddr=VA:0xffffffc0c54cf000 (READ)
```

故障 PC 位于
`PageTable64<M, PTE, H>::drop` 遍历下一级页表的 `ld a0, 0(s1)`，说明待遍历
页表页已经不可访问。第二次失败形式和第一次的目录项/对象文件损坏不同，
但两次都发生在高并发预构建早期，且此前逐字节版本能完成同一全程负载。

因此该优化判定为可复现的系统级回归并已撤销。独立函数测试通过只证明
顺序语义正确，不能证明把内核全局 `memset` 的访问粒度从字节改为 8 字节
不会触发当前内核中的并发可见性或生命周期缺陷。

## 数据使用限制

- `run.json` 的 `status=complete` 只表示成功导出 profile dump；
- 不能把 315.94 秒解释为完整工作负载耗时；
- 不能把失败阶段的 CPU/off-CPU 占比和此前完整运行作差；
- 只有 cagent、完整预构建及正式 BuildStorm 全部成功后，才生成正式迭代报告。
