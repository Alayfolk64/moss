## P0: 让 `sched_setscheduler` / `sched_setaffinity` 作用到目标 tid

**原来的问题**

cyclictest 会为测试线程设置实时优先级和 CPU affinity。当前源码里的 `sys_sched_setaffinity()` 只设置当前任务，`sys_sched_setscheduler()` 直接返回成功但不保存 priority。用户态以为设置成功，内核实际没有改变目标线程调度属性。

当前代码引用：

```rust
// kernel/src/syscall/task/schedule.rs
pub fn sys_sched_setaffinity(
    _pid: i32,
    cpusetsize: usize,
    user_mask: *const u8,
) -> AxResult<isize> {
    ...
    // TODO: support other threads
    axtask::set_current_affinity(cpu_mask);
    Ok(0)
}
```

```rust
// kernel/src/syscall/task/schedule.rs
pub fn sys_sched_setscheduler(_pid: i32, _policy: i32, _param: *const ()) -> AxResult<isize> {
    Ok(0)
}
```

**修改方向**

实验阶段的有效方向是按 `pid/tid` 找到目标任务，而不是只改 current。`sched_setscheduler` 需要读取 `sched_param.sched_priority`，把 `SCHED_FIFO/SCHED_RR` 的 priority 写入目标任务；`sched_setaffinity` 也应写入目标任务的 CPU mask。

建议落地形态：

```rust
// 伪代码，表达应落地逻辑
let task = get_task_by_tid_or_current(pid)?;
let param = vm_load(param_ptr)?;
task.set_priority(param.sched_priority);
task.set_affinity(cpu_mask);
```

**为什么能提速**

cyclictest 的 stress 项依赖测试线程在负载下及时被调度。如果 priority/affinity 没有作用到目标线程，stress 下线程可能长时间拿不到 CPU，结果缺项或延迟极大。target priority/affinity 生效后，4 项都能解析。

**对应收益**

| NO_STRESS_P1 | 1862.000000 us | 1996.000000 us | 1.000000 |

**当前状态**

这部分在结果文件中验证过收益，但当前源码仍是 stub 或 current-only 版本，不能写成已保留代码。后续应优先重新落地。

## P1: RR 调度器支持 priority

**原来的问题**

即使 syscall 层读取了 priority，如果底层 RR scheduler 不保存、不比较 priority，也不会改变实际选中的任务。

当前代码引用：

```rust
// vendor/axsched/src/round_robin.rs
pub struct RRTask<T, const MAX_TIME_SLICE: usize> {
    inner: T,
    time_slice: AtomicIsize,
    links: Links<Self>,
}
```

```rust
// vendor/axsched/src/round_robin.rs
fn pick_next_task(&mut self) -> Option<Self::SchedItem> {
    self.ready_queue.pop_front()
}

fn set_priority(&mut self, _task: &Self::SchedItem, _prio: isize) -> bool {
    false
}
```

**修改方向**

给 `RRTask` 增加 priority 字段，`set_priority()` 真正更新它，`pick_next_task()` 优先选正 priority 或更高 priority 的任务。

建议落地形态：

```rust
// 伪代码
priority: AtomicIsize,

fn set_priority(&mut self, task: &Self::SchedItem, prio: isize) -> bool {
    task.priority.store(prio, Ordering::Release);
    true
}
```

**为什么能提速**

cyclictest 线程被设置成实时优先级后，调度器必须把它们排在普通 stress 负载前面。否则 stress 测试下 wakeup 延迟会被普通任务淹没。

## P2: wake 后必要时重新调度

**原来的问题**

timer 到期后 waker 把 cyclictest 线程放回 ready queue。如果当前任务继续运行，测试线程仍要等下一次主动让出或 tick，wakeup latency 会变大。

当前代码引用：

```rust
// vendor/axtask/src/future/mod.rs
fn wake_by_ref(self: &Arc<Self>) {
    if let Some(task) = self.task.upgrade() {
        *self.woke.lock() = true;
        select_run_queue::<NoPreemptIrqSave>(&task).unblock_task(task, false);
    }
}
```

**修改方向**

对需要抢占的高优先级任务，wake 后触发 resched。不能让所有 wake 都无条件抢占，否则会伤害 lmbench context switch 和普通吞吐。

**为什么能提速**

cyclictest 测的就是“timer 到期到线程运行”的延迟。高优先级线程被唤醒后越快抢占当前任务，Max latency 越低。

## P3: timer 分辨率声明

**原来的问题**

cyclictest 会检查 timer resolution。当前 `clock_getres()` 返回 1us，会让用户态认为内核 timer 分辨率较粗。

当前代码引用：

```rust
// kernel/src/syscall/time.rs
if let Some(res) = res.nullable() {
    res.vm_write(timespec::from_time_value(TimeValue::from_micros(1)))?;
}
```

**修改方向**

如果底层 timer 能支持更细粒度，应返回 1ns 级别声明。但这只是能力声明，不等于真实 wakeup latency 已优化。

**为什么能提速**

这项主要避免 cyclictest 降级或告警。真实速度仍取决于 timer queue、wakeup 和调度器。
