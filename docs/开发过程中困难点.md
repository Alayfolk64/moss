# MOSS 开发中的四个典型困难及解决方式

  ## 1. PCP 每核物理页缓存：理论上更快，第一次实现反而变慢

  ### 问题现象

  MOSS 原来分配 4 KiB 物理页时，所有 CPU 都要访问同一个全局物理页分配器。多核并发缺页时，大量 CPU 竞争同一把锁。

  因此我们引入 PCP（Per-CPU Page Cache）：

  每个 CPU 保存一小批空闲物理页
  分配时优先从本 CPU 获取
  本地没有时再批量访问全局分配器

  这个思路理论上可以减少全局锁竞争，但第一次实现后，BuildStorm 性能反而下降。

  ### 根本原因

  最初的 PCP 命中快路径使用了较重的 SpinNoIrq。即使本 CPU 缓存中已经有空闲页，每次分配一个页面仍然需要：

  - 关闭本地中断；
  - 修改内核抢占计数；
  - 获取和释放自旋锁；
  - 恢复抢占和中断状态。

  由于 BuildStorm 会产生大量缺页和物理页分配，这些看起来很小的操作被执行数百万次，最终抵消了减少全局锁竞争带来的收益。

  另外，早期实验混入了其他修改，使性能下降很难单独归因。

  ### 解决方式

  重新拆分快路径和慢路径：

  PCP 命中：
      只获取本 CPU 的轻量 IRQ 锁
      直接弹出一个空闲页

  PCP 为空：
      关闭抢占
      获取全局分配器锁
      一次批量补充多个页面

  PCP 过满：
      批量归还全局分配器

  全局内存不足：
      回收所有 CPU 的 PCP 页面后重试

  只有同时操作“当前 CPU 缓存”和“全局分配器”的慢路径才显式关闭抢占，普通命中路径不再做重复的抢占状态维护。

  ### 最终效果与经验

  优化后的 PCP 将正式 BuildStorm 单次耗时从：

  1524.50 秒 → 1058.68 秒

  降低约 30.56%。

  这个问题说明：

  > “每核缓存”不天然等于高性能。优化是否有效，关键不只是减少了哪把大锁，还要检查最常执行的命中路径增加了多少额外操作。

  ## 2. CPU 数量正确，但物理 hart 与逻辑 CPU 编号映射错误

  ### 问题现象

  设备树能够正确识别 CPU 数量，但多核启动仍然出现：

  - 启动 CPU 没有进入逻辑 CPU 0；
  - 次级 CPU 启动失败；
  - IPI 发给错误的 CPU；
  - 远程 TLB 刷新目标错误；
  - VF2 被错误识别为 5 个可用 CPU。

  问题不在 CPU 数量，而在于把“物理 hart ID”和“MOSS 逻辑 CPU ID”当成了同一个编号。

  ### 根本原因

  RISC-V 中存在两套 CPU 编号：

  物理 hart ID：硬件和 OpenSBI 使用的编号
  逻辑 CPU ID：MOSS 调度器内部使用的连续编号

  OpenSBI 可能让非零 hart 进入内核。例如 QEMU 中实际启动 MOSS 的可能是物理 hart 4，而旧代码仍然把物理 hart 0 当作逻辑 CPU 0。

  VisionFive 2 又有一个特殊情况：

  hart 0    → S7 管理核心
  hart 1～4 → 四个 U74 应用核心

  S7 是真实 CPU 核心，但不具备供 MOSS 正常运行的完整 S-mode 和中断环境，不能作为普通 SMP CPU。旧设备树处理如果只统计节点，就可能错误地得到 5 个 CPU。

  ### 解决方式

  MOSS 启动时重新建立明确的双向映射：

  1. 从内核入口参数记录真正启动 MOSS 的物理 hart ID；
  2. 从设备树读取可用 CPU；
  3. VF2 上明确排除 S7/hart 0；
  4. 将真正启动内核的 hart 放在逻辑 CPU 0；
  5. 给其他 CPU 分配连续的逻辑编号；
  6. 在 HAL 硬件边界统一进行逻辑编号与物理编号转换。

  VF2 最终映射为：

  逻辑 CPU 0 → 物理 hart 1
  逻辑 CPU 1 → 物理 hart 2
  逻辑 CPU 2 → 物理 hart 3
  逻辑 CPU 3 → 物理 hart 4

  MOSS 内部调度使用逻辑编号；调用 OpenSBI、操作 PLIC、发送 IPI和远程 TLB 刷新时使用物理 hart ID。

  ### 最终效果与经验

  修复后，QEMU 和 VF2 都可以根据真实启动 hart 建立稳定的多核拓扑，VF2 四个 U74 核心能够正确启动。

  这个问题说明：

  > CPU 数量正确不代表 SMP 拓扑正确。内核必须明确区分“内部逻辑编号”和“固件可见的硬件编号”。

  ## 3. 2K1000LA 的 U-Boot 控制设备树不能直接交给 MOSS

  ### 问题现象

  最开始使用 U-Boot 的 fdtcontroladdr 启动 MOSS。MOSS 可以运行并输出串口日志，但无法正常初始化：

  - AHCI 控制器；
  - SATA 硬盘；
  - 网卡；
  - 根文件系统。

  这容易让人误以为 AHCI 或网卡驱动本身存在问题。

  ### 根本原因

  fdtcontroladdr 指向的是 U-Boot 自己使用的 control DTB，主要用于满足 U-Boot 的硬件操作需求，并不一定是交给操作系统的完整系统设备树。

  这份 control DTB 中缺少或没有按照 MOSS 支持的格式描述：

  /2k1000-soc/ahci@400e0000
  网卡和 PHY
  完整中断关系
  SATA 端口信息
  根文件系统启动参数

  因此，U-Boot 自己可以使用部分硬件，但 MOSS 无法根据这份设备树找到对应设备。

  设备树也不是内核扫描硬件自动生成的。SoC 内部的 UART、AHCI、中断控制器和时钟等设备通常不能自动枚举，必须由 bootloader 提前准备 DTB 并把内存地址传给内核。

  ### 解决方式

  改用经过真机验证的独立 board.dtb：

  电脑上的 /srv/tftp/board.dtb
          ↓ TFTP
  加载到开发板内存
          ↓
  U-Boot 设置启动参数
          ↓
  将 DTB 地址传给 MOSS

  启动前补齐或确认：

  - /chosen/bootargs 中的根分区；
  - ethernet0 指向正确网卡；
  - AHCI 的 ports-implemented = <1>；
  - AHCI 地址、中断和兼容字符串。

  最后通过：

  go MOSS入口地址 DTB地址

  同时把内核入口和设备树地址交给 MOSS。

  ### 最终效果与经验

  使用正确的 board.dtb 后，MOSS 能够识别 AHCI、找到 SATA 硬盘并挂载 /dev/sda2 或 /dev/sda3，网卡也能根据正确节点初始化。

  这个问题更准确的表述不是“厂商设备树一定有 bug”，而是：

  > U-Boot 自用的控制设备树和操作系统所需的系统设备树用途不同，不能因为 U-Boot 能用，就直接认为 MOSS 也能用。

  ## 4. VF2 真实文件操作暴露持久化与缓存一致性问题

  在 VF2 上运行文件追加、Git 和 Vim 时，出现了一个共同现象：

  > 程序明明显示保存成功，之后再次读取、清缓存或重启后，文件内容却不正确。

  但这个问题实际包含两个不同的文件系统错误。

  ### 子问题一：追加内容被错误清零

  文件追加后，内存页缓存中的内容正确，文件长度也正确，但重启或丢弃缓存后，追加区域全部变成 0x00。

  排查过程中曾怀疑：

  - SD 卡忙状态；
  - flush() 没有实现；
  - CMD13；
  - FIFO 访问错误。

  这些确实是驱动缺陷，但不是追加内容变零的最终原因。

  真正的执行过程是：

  页缓存把追加数据正确写入磁盘
          ↓
  ext4 提交新的文件长度
          ↓
  错误调用普通 set_len 扩容语义
          ↓
  旧 EOF 到新 EOF 之间被补零
          ↓
  刚写入的数据被再次覆盖

  解决时区分了两种扩容：

  用户调用 truncate/ftruncate：
      新增区域必须补零

  页缓存写回后提交文件长度：
      只修改 inode 长度，不能再次清零

  修复后通过 sync、丢缓存、重新读取和重启后的字节级比较验证。

  ### 子问题二：Git/Vim 命中了旧 dentry 和 inode 缓存

  出现过以下现象：

  - git commit 显示成功，紧接着 git log 却说没有提交；
  - 执行一次 ls .git/refs/heads 后，git log 又恢复；
  - Vim 显示文件已经写入，但 rustc 读取到 0 字节；
  - Rust 源文件中混入旧 .viminfo 的尾部内容。

  这里的数据不一定真的丢失，而是 MOSS 读取了旧缓存。

  首先，同一个真实目录可能存在多个 DirNode 包装，各自持有不同的目录项缓存。Git 创建或 rename 文件后，只刷新了其中一个包装，另一个包装仍然认为文件不存在。

  其次，ext4 删除文件后可能复用 inode 编号：

  旧 .viminfo → inode 100
  删除 .viminfo
  新 main.rs → 再次使用 inode 100

  旧缓存只使用“文件系统 + inode 编号”识别文件，于是把新的 main.rs 错认成旧的 .viminfo。

  最终修复包括：

  - 目录项版本精确到“目录 inode + 文件名”；
  - create、unlink、link、rename 后精准清理相应 dentry；
  - 跨目录 rename 按稳定顺序同时锁住两个目录；
  - inode 被删除和复用时，清理同号 inode 的旧页缓存与元数据缓存。

  ### 最终效果与经验

  修复后，文件追加能够在重启后保持正确，Git 的提交和查询结果一致，Vim 保存的文件也能被编译器正确读取。

  这两个子问题虽然根因不同，但共同说明：

  > write() 或应用程序返回“保存成功”，只代表当前操作已经完成，不代表页缓存、磁盘数据、文件长度、目录项和 inode 缓存已经全部保持一致。

  它们是在 VF2 真实工作负载中被发现的，但本质上是 MOSS 通用文件系统问题，并不是 VF2 硬件造成的。
