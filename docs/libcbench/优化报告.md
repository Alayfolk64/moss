# libcbench 优化报告

本文只整理 libcbench。libcbench 有 27 项，其中 malloc、pthread、stdio 会受内核影响，string、utf8、regex 主要是 libc/CPU 路径。以下按收益优先级整理。

## 结果概览

| 阶段 | 结果文件 | libc | 已解析 | 缺失 | 总分 |
| --- | --- | --- | ---: | ---: | ---: |
| 优化前 | `docs/libcbench/results/rv-current-0618-024935.md` | musl | 27 | 0 | 28.062125 |
| 复测对照 | `docs/libcbench/results/rv-current-recheck-0618-120912.md` | musl | 27 | 0 | 28.142728 |
| 最优代表结果 | `docs/libcbench/results/rv-anon-faultaround2-0618-025430.md` | musl | 27 | 0 | 28.181592 |
| 最终复测 | `docs/libcbench/results/rv-final-recheck-0618-121930.md` | musl | 27 | 0 | 28.167118 |

从第一轮当前值到最优代表结果提升 +0.119467。考虑复测波动后，稳定收益较小，所以 libcbench 适合作为通用优化的验证项，不适合单独做激进特化。

## P0: stdio / tmpfs / 普通文件 I/O

**原来的问题**

`b_stdio_putcgetc` 和 `b_stdio_putcgetc_unlocked` 会通过 libc stdio 在临时文件上反复 putc/getc。它们受 `/tmp`、open/close、read/write、通知路径开销影响。

**修改了什么**

不重复创建 `/tmp`，保持内核 pseudo fs 已挂载的 tmpfs。普通文件 I/O 复用 inotify/fanotify 无监听快路径，减少 stdio 热路径固定开销。

代码引用：

```rust
// kernel/src/pseudofs/mod.rs
mount_at(&fs, "/dev/shm", tmp::MemoryFs::new())?;
mount_at(&fs, "/tmp", tmp::MemoryFs::new())?;
```

```rust
// kernel/src/syscall/fs/io.rs
pub fn sys_write(fd: i32, buf: *const u8, len: usize) -> AxResult<isize> {
    ...
    let written = f.write(&mut VmBytes::new(buf, len))?;
    if written > 0 {
        notify_inotify_file(f.as_ref(), IN_MODIFY);
        notify_fanotify_modify(&f);
    }
    Ok(written as _)
}
```

无监听者时快速返回：

```rust
// kernel/src/syscall/fs/inotify.rs
if !has_inotify_watchers() {
    return;
}
```

**为什么能提速**

stdio 小读写调用次数多。无监听者时跳过通知准备，可以减少每次 putc/getc 周围的 syscall 固定开销。tmpfs 避免真实磁盘 I/O，符合临时文件预期语义。

**对应收益**

| 子项 | baseline | result | score |
| --- | ---: | ---: | ---: |
| `b_stdio_putcgetc` | 0.767823 s | 0.585818 s | 1.237040 |
| `b_stdio_putcgetc_unlocked` | 0.765147 s | 0.531555 s | 1.305291 |

## P1: malloc / 匿名 COW fault

**原来的问题**

malloc 项会触发 brk/mmap、匿名页分配和缺页。每次只 fault 当前页，开销会集中在页分配、清零、页表映射上。实验中 small fault-around 有轻微收益，但幅度不大。

当前代码引用：

```rust
// kernel/src/mm/aspace/backend/cow.rs
pub struct CowBackend {
    start: VirtAddr,
    size: PageSize,
    file: Option<(FileBackend, u64, Option<u64>)>,
    mapped_pages: AtomicUsize,
}
```

```rust
// kernel/src/mm/aspace/backend/cow.rs
fn alloc_new_at(
    &self,
    vaddr: VirtAddr,
    flags: MappingFlags,
    pt: &mut PageTableMut,
) -> AxResult {
    let frame = self.alloc_new_frame(true)?;
    ...
    pt.map(vaddr, frame, self.size, flags)?;
    self.mapped_pages.fetch_add(1, Ordering::Relaxed);
    Ok(())
}
```

**修改方向**

只在匿名、可写、同一 VMA 的写 fault 上做小窗口 fault-around，例如 4 页以内。不要扩到文件映射，不要越过 VMA 边界。

**为什么能提速**

malloc 常常连续触碰刚分配的 heap 页。小窗口预分配可以减少后续连续 fault 次数。但收益很小，窗口过大反而会增加内存占用和无用清零。

**对应实验**

| 阶段 | 总分 | 相对第一轮当前值 |
| --- | ---: | ---: |
| anon faultaround | 28.158024 | +0.095899 |
| anon faultaround2 | 28.181592 | +0.119467 |
| heap128 only | 27.936274 | -0.125851 |

结论：只保留小粒度方向，禁止扩大成 heap128 这类激进预分配。

## P2: pthread create/join 与 futex 空 wake

**原来的问题**

pthread create/join 会走 clone、线程退出、`clear_child_tid`、futex wake。当前源码在 futex wake 和线程退出 clear_child_tid 后仍无条件 `yield_now()`。如果没有实际 waiter，这个 yield 是额外调度开销。

当前代码引用：

```rust
// kernel/src/syscall/sync/futex.rs
count = futex.wq.wake(value as _, bitset);
...
axtask::yield_now();
Ok(count as _)
```

```rust
// kernel/src/task/ops.rs
if let Some(futex) = guard {
    futex.wq.wake(1, u32::MAX);
}
axtask::yield_now();
```

**修改方向**

记录实际唤醒数量，只有 `count > 0` 时才考虑 yield。

建议落地形态：

```rust
let count = futex.wq.wake(...);
if count > 0 {
    axtask::yield_now();
}
```

**为什么能提速**

pthread create/join 串行测试会频繁创建和退出线程。空 wake 也 yield 会让当前线程无意义让出 CPU，增加调度往返。只在真实唤醒 waiter 时让出，可以减少线程类 benchmark 的固定成本。

**当前状态**

这项当前源码仍未落地，不能算已保留优化。

## P3: mmap 记录和线程表快路径

**原来的问题**

libcbench 一些 malloc/thread 项会间接受 fork/clone、地址空间复制、线程表查询影响。实验里这类优化有轻微收益，但幅度小。

代码相关位置：

```rust
// kernel/src/mm/aspace/mod.rs
pub fn try_clone(&mut self) -> AxResult<Arc<Mutex<Self>>> {
    ...
    for area in self.areas.iter() {
        let new_backend = area.backend().clone_map(...)?;
        ...
    }
    Ok(new_aspace)
}
```

**为什么不是最高优先级**

这类路径对 libcbench 有影响，但一次测试总分只提升约 0.02 到 0.04，容易被运行波动淹没。应跟随通用 clone/mmap 优化做，不应单独为了 libcbench 改语义。

## P4: 不优先优化 string / utf8 / regex

**原来的问题**

这些项目主要测 libc 算法和 CPU 执行，不是内核 syscall 热路径。

| 项目组 | 代表项 | 结论 |
| --- | --- | --- |
| string | `b_string_strstr`、`b_string_strlen` | 内核侧收益低 |
| utf8 | `b_utf8_bigbuf`、`b_utf8_onebyone` | 内核侧收益低 |
| regex | `b_regex_compile`、`b_regex_search` | libc 算法为主 |

`b_string_memset` 分数有波动，但不能归因到某个内核改动。

## 评分脚本

`docs/libcbench/get_result.py` 负责复现官方 judge。所有 27 项都是 seconds，越低越好。

代码引用：

```python
# docs/libcbench/get_result.py
START_RE = re.compile(r"#### OS COMP TEST GROUP START libcbench(?:-(glibc|musl))? ####")
END_RE = re.compile(r"#### OS COMP TEST GROUP END libcbench(?:-(glibc|musl))? ####")
```

这项不提升内核速度，但能保证每轮优化后分数可对比。
