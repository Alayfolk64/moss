本文只整理 lmbench。排序按“对得分和关键子项的收益”从高到低排列。每个优化点都说明原问题、修改内容、提速原因和代码引用。

## P0: mmap / page fault 路径

**原来的问题**

`bw_mmap_rd` 会 mmap 文件后顺序扫描。旧路径对每个新页都单独 fault、单独从文件读页、单独建立映射。对顺序读来说，这会把本来连续的文件访问拆成很多小 I/O。

**修改了什么**

文件映射后端增加顺序 fault 检测。发现 page N 后紧接着 fault page N+1 时，提前把后面 4 页读入页缓存，但不提前建立页表映射。

代码引用：

```rust
// kernel/src/mm/aspace/backend/file.rs
last_fault_page: AtomicU32,
next_readahead_page: AtomicU32,
```

```rust
// kernel/src/mm/aspace/backend/file.rs
fn maybe_readahead_after_fault(&self, pn: u32) {
    let last = self.0.last_fault_page.swap(pn, Ordering::Relaxed);
    if last.checked_add(1) != Some(pn) {
        return;
    }
    let start = pn.saturating_add(1);
    let end = start.saturating_add(MMAP_FAULT_READAHEAD_PAGES);
    let _ = self.0.cache.readahead(offset, count);
}
```

触发条件被限制在单页读 fault：

```rust
// kernel/src/mm/aspace/backend/file.rs
let fault_readahead =
    range.end - range.start == PAGE_SIZE_4K && access_flags.contains(MappingFlags::READ);
...
if pages > 0 && fault_readahead {
    self.maybe_readahead_after_fault(start_page);
}
```

**为什么能提速**

后续页仍然会 page fault，但数据大概率已经在页缓存中，fault 时只需要建立映射，减少等待底层文件系统读页。这个策略只在连续页 fault 时触发，随机 fault 基本不触发，尽量不影响 `lat_pagefault`。

**对应收益**

| Pagefaults on `/var/tmp/XXX` | 978.237464 us | 4.397700 us | 1.995504 |
| `lat_mmap` | 4109.000000 us | 264.000000 us | 1.935751 |
| `bw_mmap_rd mmap_only` | 1037.403000 MB/s | 15409.82 MB/s | 1.932669 |

## P1: 文件 I/O 固定开销

**原来的问题**

lmbench 的 `Simple read/write/stat/fstat/open/close` 是小 syscall 微基准。原来的普通文件路径会额外进入 inotify/fanotify 通知准备逻辑。benchmark 场景通常没有监听者，但仍可能做 `stat()`、路径解析、mark 检查和事件准备。

**修改了什么**

inotify 加全局 watcher 快速判断；fanotify 加全局 interest mask 快速判断。没有监听者或没有感兴趣事件时，直接返回。

代码引用：

```rust
// kernel/src/syscall/fs/inotify.rs
pub(super) fn has_inotify_watchers() -> bool {
    INOTIFY_WATCHES.load(Ordering::Acquire) != 0
}

pub fn notify_inotify_file(file: &dyn FileLike, mask: u32) {
    if !has_inotify_watchers() {
        return;
    }
    ...
}
```

```rust
// kernel/src/syscall/fs/fanotify.rs
fn notify_fanotify_event(file: &Arc<dyn FileLike>, mask: u64) {
    if !has_fanotify_interest(mask) {
        return;
    }
    ...
}

fn request_fanotify_permission(file: &Arc<dyn FileLike>, mask: u64) -> AxResult {
    if !has_fanotify_interest(mask) {
        return Ok(());
    }
    ...
}
```

`read/write` 热路径仍正常触发通知入口：

```rust
// kernel/src/syscall/fs/io.rs
let read = f.read(&mut VmBytesMut::new(buf, len))?;
if read > 0 {
    notify_inotify_file(f.as_ref(), IN_ACCESS);
    notify_fanotify_access(&f);
}
```

**为什么能提速**

无监听者时，普通 I/O 少走通知子系统，减少 `stat/path/Arc clone/mark scan` 等固定开销。对 lmbench 微基准来说，固定开销占比很高，所以收益明显。

**对应收益**

| 子项 | baseline | result | score |
| --- | ---: | ---: | ---: |
| Simple stat | 425.256500 us | 14.596900 us | 1.965675 |
| Simple open/close | 501.235200 us | 55.898300 us | 1.888479 |
| Simple fstat | 29.546740 us | 3.996900 us | 1.864726 |
| Simple read | 16.819200 us | 3.803700 us | 1.773848 |
| Simple write | 16.875530 us | 5.935300 us | 1.648290 |

## P2: select 快路径

**原来的问题**

`lat_select` 对 fd set 扫描和 fd table 查询非常敏感。无论 read/write/except 哪个集合里有 fd，如果分别处理，都会重复扫描和准备数据。

**修改了什么**

先合并三个 fd set，只遍历实际出现的 fd，缓存 `(file, interested_events)` 和 fd index。poll 时只检查关心的 event。

代码引用：

```rust
// kernel/src/syscall/io_mpx/select.rs
let fd_bitmap = read_set.0 | write_set.0 | except_set.0;
let fd_count = fd_bitmap.len();
let mut fds = Vec::with_capacity(fd_count);
let mut fd_indices = Vec::with_capacity(fd_count);
for fd in fd_bitmap.into_iter() {
    let f = fd_table.get(fd).ok_or(AxError::BadFileDescriptor)?.inner.clone();
    let mut events = IoEvents::empty();
    events.set(IoEvents::IN, read_set.0.get(fd));
    events.set(IoEvents::OUT, write_set.0.get(fd));
    events.set(IoEvents::ERR, except_set.0.get(fd));
    ...
}
```

```rust
// kernel/src/syscall/io_mpx/select.rs
for ((fd, interested), index) in fds.0.iter().zip(fd_indices.iter().copied()) {
    let events = fd.poll() & *interested;
    ...
}
```

**为什么能提速**

减少重复扫描 fd set 和重复访问 fd table。`Select on 100 fd's` 这种测试主要测固定管理开销，合并扫描后收益直接。

**对应收益**

| 子项 | baseline | result | score |
| --- | ---: | ---: | ---: |
| Select on 100 fd's | 56.055610 us | 20.015500 us | 1.642935 |

## P3: dirty page 批量写回

**原来的问题**

lmbench `lmdd ... fsync=1` 会写 1MiB 后强制同步。旧写回如果按 4KiB 页逐页写，会造成大量小 `write_at()`。

**修改了什么**

把连续 dirty 页按最多 16 页合并成一批写回。

代码引用：

```rust
// vendor/axfs/src/highlevel/file.rs
const WRITEBACK_BATCH_PAGES: usize = 16;
const WRITEBACK_BATCH_BYTES: usize = WRITEBACK_BATCH_PAGES * PAGE_SIZE;
```

```rust
// vendor/axfs/src/highlevel/file.rs
dirty_pages.sort_by_key(|(pn, _)| *pn);
...
if pn != prev_pn + 1 {
    break;
}
if bytes > 0 && bytes + len > WRITEBACK_BATCH_BYTES {
    break;
}
Self::writeback_dirty_run(file, file_len, &mut dirty_pages[start..end])?;
```

**为什么能提速**

减少进入文件系统写路径的次数，降低 ext4/lwext4 锁和小块写开销。对 fsync 型写吞吐更有帮助。

## P4: 本地评分脚本

**原来的问题**

lmbench 输出格式复杂，且 36 项里既有越低越好，也有越高越好。手工对比容易误判。

**修改了什么**

`docs/benchmarks/lmbench/get_result.py` 解析 group marker，按官方 baseline 和方向计算分数。

代码引用：

```python
# docs/benchmarks/lmbench/get_result.py
START_RE = re.compile(r"#### OS COMP TEST GROUP START lmbench-(glibc|musl) ####")
END_RE = re.compile(r"#### OS COMP TEST GROUP END lmbench-(glibc|musl) ####")
```

**为什么能提速**

这不直接提升内核速度，但能缩短迭代周期。先跑高价值子项定位瓶颈，最后再跑完整 36 项，避免把时间花在短期无希望的慢项上。

## 不做的事

- 不按进程名 special-case。
- 不跳过 benchmark 的真实 I/O 工作。
- 不重复 mount `/tmp`。`kernel/src/pseudofs/mod.rs` 已经挂载 `/tmp` tmpfs。
- futex 空 wake 当前源码仍是无条件 yield，不能算 lmbench 已落地优化。
