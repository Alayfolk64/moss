# 龙芯二号板镜像部署、网络烧录与分区调整教程

更新日期：2026-08-19

本文记录龙芯 2K1000LA 星云板当前可重复使用的 MOSS 部署和 SATA rootfs 烧录方法。
没有 SATA-USB 转接器时，推荐让板上原厂 Linux 通过网络把镜像直接写入未挂载的
`/dev/sda2` 或 `/dev/sda3`；不先把大镜像保存到 `/dev/sda1`。

下面四类操作必须分开：

1. MOSS 内核由 U-Boot 通过 TFTP 装入 RAM，不写 SATA 和 SPI；
2. rootfs 镜像只覆盖 SATA 的某一个具体分区；
3. `sda1` 的缩小、扩展和分区表调整必须在 RAM-only rescue Linux 中离线进行；
4. 当前不擦除、不写入板载 SPI，保留原厂 U-Boot 作为恢复入口。

## 1. 当前磁盘布局和保护边界

当前 32 GB SATA 盘的目标合同如下。扇区大小是 512 bytes，物理顺序是
`sda1 -> sda3 -> sda2`，不是分区编号顺序。

| 物理顺序 | 板端设备 | 起始 sector | 末尾 sector | sector 数 | 容量 | 用途 |
| ---: | --- | ---: | ---: | ---: | ---: | --- |
| 1 | `/dev/sda1` | 2,048 | 24,782,847 | 24,780,800 | 12,687,769,600 bytes，约 11.8 GiB | 原厂 Linux、旧内核和 2 GiB `/swapfile-moss` |
| 2 | `/dev/sda3` | 24,782,848 | 37,365,759 | 12,582,912 | 6,442,450,944 bytes，严格 6 GiB | LoongArch64 Alpine 现场赛环境 |
| 3 | `/dev/sda2` | 37,365,760 | 62,531,583 | 25,165,824 | 12,884,901,888 bytes，严格 12 GiB | MOSS/Debian glibc 比赛环境 |

`sda2` 的起始 sector `37365760` 是已验证的 MOSS 根分区合同，分区拆分和合并都不得
改变它。表中数字只适用于当前这块总计 `62533296` 个 sector 的盘。实际操作前必须以
当次 `sfdisk --dump /dev/sda` 为准；只要总 sector、起始位置或分区类型不同，就停止操作。

> 绝对不要把分区镜像写到 `/dev/sda` 整盘。这会覆盖 MBR、原厂 Linux 和所有分区。

## 2. 构建、部署并从 TFTP 启动 MOSS

龙芯当前只构建进入 BusyBox shell 的镜像：

```bash
make site-2kla
sudo install -o tftp -g tftp -m 0644 \
  build/site-2kla/moss-2kla.bin /srv/tftp/moss-2kla.bin
sha256sum build/site-2kla/moss-2kla.bin /srv/tftp/moss-2kla.bin
```

两行 SHA-256 必须相同。部署到 `/srv/tftp` 只是准备网络加载文件，不等于写入板载
flash。

从第三分区自动启动 MOSS：

```bash
python3 scripts/run_ls2k1000_serial_tftp.py moss-2kla.bin \
  --root-device /dev/sda3 \
  --monitor-seconds 180 \
  --log tmp/moss-2kla.log
```

脚本的第一个参数是 TFTP 目录里的文件名，不是仓库中的构建路径。`--root-device` 只接受
`/dev/sda2` 或 `/dev/sda3`。

需要手工启动时，在 U-Boot 中执行：

```text
setenv ipaddr 192.168.88.2
setenv serverip 192.168.88.1
setenv netmask 255.255.255.0
setenv ethact ethernet@40040000

tftpboot 0x900000000a000000 board.dtb
fdt addr 0x900000000a000000
fdt resize 4096
fdt set /chosen bootargs root=/dev/sda3
fdt set /aliases ethernet0 /2k1000-soc/ethernet@40040000
fdt set /2k1000-soc/ahci@400e0000 ports-implemented <0x1>

tftpboot 0x9000000098000000 moss-2kla.bin
go 0x9000000098000040 0x900000000a000000
```

启动第二分区时，把 `root=/dev/sda3` 改成 `root=/dev/sda2`。这些命令只改当次 RAM 中的环境和
DT，不执行 `saveenv`。

## 3. 没有 SATA-USB 转接器时怎么烧录

这里的“没有 SATA”需要区分两种情况：

- 没有 SATA-USB 转接器，但 SATA 盘还装在板上：可以用下面的原厂 Linux + HTTP 直写方案；
- 板上根本没有 SATA 盘，`lsblk` 也看不到 `/dev/sda`：不存在 `sda2/sda3` 可供烧录，
  必须先安装存储设备，或另行设计 NFS/initramfs 根文件系统。

HTTP 直写的数据路径是：

```text
PC 上的镜像文件 -> HTTP/TCP -> 板上 wget -> /dev/sda2 或 /dev/sda3
```

`wget -O /dev/sda3 ...` 把数据直接写到块设备，不会在 `sda1`、`/root` 或 `/tmp` 生成另一份
镜像。Linux 可能用少量可回收 page cache 作为缓冲，但不会额外占用 690 MiB 或 12 GiB
的根分区空间。目标分区本来就已预留在磁盘上，烧录是覆盖其内容，不会再额外占一个分区。

> 不要先执行 `wget URL`、`wget -O /tmp/image ...` 或把 12 GiB 镜像复制到 `sda1`。
> 这些写法会真正保存一份普通文件，而当前约 11.8 GiB 的 `sda1` 根本容不下 12 GiB 镜像。

## 4. 网络直写前准备

### 4.1 PC 端验证镜像并启动 HTTP

当前已全量复核的文件是：

| 用途 | 文件 | 字节数 | SHA-256 |
| --- | --- | ---: | --- |
| `sda2` | `/srv/tftp/sdcard-la-clean-12g-20260811.img` | 12,884,901,888 | `35681b35f3fc73dbeec258a230e5781f22fd718b265c40f1ddfa668984be322d` |
| `sda3` | `/srv/tftp/alpine-linux-loongarch64.img` | 723,517,440（690 MiB） | `0ad295fc3e62dad2dd15ccf575135bc8c17fe8cddb510f3aa9ff44c4e1be2173` |

2026-08-18 已重新读取这两个实际文件，字节数和 SHA-256 与表中一致。每次烧录前仍要重新验证：

```bash
stat -c '%n %s bytes' \
  /srv/tftp/sdcard-la-clean-12g-20260811.img \
  /srv/tftp/alpine-linux-loongarch64.img
sha256sum \
  /srv/tftp/sdcard-la-clean-12g-20260811.img \
  /srv/tftp/alpine-linux-loongarch64.img
sudo e2fsck -f -n /srv/tftp/sdcard-la-clean-12g-20260811.img
sudo e2fsck -f -n /srv/tftp/alpine-linux-loongarch64.img
```

当前直连板卡的 PC 网口是 `enp3s0`：

```bash
sudo ip addr replace 192.168.88.1/24 dev enp3s0
sudo ip link set enp3s0 up
ip addr show dev enp3s0
python3 -m http.server 8000 \
  --bind 192.168.88.1 \
  --directory /srv/tftp
```

HTTP 进程保持在前台；看到板卡的 GET 请求和 `200` 响应才表明传输真正开始。

### 4.2 让 MOSS 通过 PC 持久访问公网

当前数据路径示例为：

```text
MOSS eth0(192.168.88.2) -> PC enp3s0(192.168.88.1) -> PC wlp4s0 -> 公网
```

PC 终端里的 `http_proxy`/`https_proxy` 不会自动传给 MOSS。MOSS 能 ping
`192.168.88.1` 但不能 ping 公网 IP 时，先在 PC 检查：

```bash
ip route get 223.5.5.5
sysctl net.ipv4.ip_forward
sudo iptables -S FORWARD
sudo iptables -t nat -S POSTROUTING
```

本机验证的修复是开启 IPv4 转发，按板卡网段放行转发，并对
`192.168.88.0/24` 做 NAT。规则不写入口和出口网卡名，所以 PC 在有线、Wi-Fi
或其他上游网卡之间切换时不用修改：

```bash
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -C FORWARD -s 192.168.88.0/24 -j ACCEPT || \
  sudo iptables -I FORWARD 1 -s 192.168.88.0/24 -j ACCEPT
sudo iptables -C FORWARD -d 192.168.88.0/24 \
  -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT || \
  sudo iptables -I FORWARD 1 -d 192.168.88.0/24 \
    -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
sudo iptables -t nat -C POSTROUTING -s 192.168.88.0/24 -j MASQUERADE || \
  sudo iptables -t nat -A POSTROUTING -s 192.168.88.0/24 -j MASQUERADE
```

Ubuntu 上使用标准的 `iptables-persistent` 保存该配置。不直接执行
`netfilter-persistent save`，因为它会把当前 Docker 动态链也写进启动文件。持久化文件
只保留板卡所需规则：

> `iptables-persistent` 与 Ubuntu 的 `ufw` 包冲突。当前 PC 的 `ufw` 未启用，
> 实际安装过程已移除 `ufw`。其他 PC 如果正在使用 `ufw`，不直接复制这段安装命令。

```bash
sudo apt-get install -y iptables-persistent
sudo tee /etc/sysctl.d/90-moss-board-router.conf >/dev/null <<'EOF'
net.ipv4.ip_forward=1
EOF
sudo tee /etc/iptables/rules.v4 >/dev/null <<'EOF'
*filter
:INPUT ACCEPT [0:0]
:FORWARD DROP [0:0]
:OUTPUT ACCEPT [0:0]
-A FORWARD -s 192.168.88.0/24 -j ACCEPT
-A FORWARD -d 192.168.88.0/24 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
COMMIT
*nat
:PREROUTING ACCEPT [0:0]
:INPUT ACCEPT [0:0]
:OUTPUT ACCEPT [0:0]
:POSTROUTING ACCEPT [0:0]
-A POSTROUTING -s 192.168.88.0/24 -j MASQUERADE
COMMIT
EOF
sudo iptables-restore --test /etc/iptables/rules.v4
sudo systemctl enable netfilter-persistent.service
```

不在当前已运行 Docker 的 PC 上执行 `iptables-restore /etc/iptables/rules.v4`；运行时使用
上面三条 `iptables` 命令，持久化文件留给下次开机由 `netfilter-persistent`
自动加载，之后 Docker 会补齐自己的链。

重启 PC 后验收：

```bash
sysctl net.ipv4.ip_forward
sudo systemctl is-enabled netfilter-persistent.service
sudo iptables -C FORWARD -s 192.168.88.0/24 -j ACCEPT
sudo iptables -t nat -C POSTROUTING -s 192.168.88.0/24 -j MASQUERADE
```

龙芯二号板和星光2都使用 `192.168.88.0/24` 时，上述规则可直接共用；两块板同时
连接时必须使用不同的 IP，不能都配成 `192.168.88.2`。如果星光2使用另一个网段，
将它的网段按同样方式另加三条规则；不要使用不限网段的全局 `MASQUERADE`。

2026-08-19 的抓包确认：旧内核发出的 TCP SYN 校验和为 `0x0000`，所以 ICMP
`ping` 可以成功而 HTTPS 没有响应。修复位于 `axnet` 公共发包出口，在任何物理网卡
发送前统一完成 IPv4/IPv6 TCP/UDP 校验和；这项修复同时适用于龙芯和 VF2，不依赖
具体网卡驱动。主机不需要额外添加 iptables `CHECKSUM --checksum-fill` 规则。

旧内核运行 BusyBox `ping` 时还会在回包间隔中连续打印
`ping: recvfrom: Resource temporarily unavailable`。BusyBox 使用的是阻塞 raw socket；
新内核把 raw socket 状态直接初始化在最终堆地址，避免龙芯编译器在移动较大聚合体时
污染 `O_NONBLOCK` 状态。换入新内核后，下面第一条命令应只显示正常回包和最终统计，
不再连续打印 `recvfrom` 错误：

```bash
ping -c 3 192.168.88.1
ping -c 3 223.5.5.5
ip route
cat /etc/resolv.conf
python -c 'import socket; print(socket.gethostbyname("pypi.org"))'
python -m pip install --no-cache-dir requests
```

只有 `ping`、DNS 和最后的 HTTPS 安装全部通过，才算公网链路验收完成。

### 4.3 板上原厂 Linux 核对设备

先确认当前运行的根是 `sda1`，SATA 盘和目标分区存在：

```bash
findmnt -no SOURCE,FSTYPE,OPTIONS /
cat /proc/cmdline
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS /dev/sda
fdisk -l /dev/sda
cat /sys/block/sda/size
cat /sys/class/block/sda/queue/logical_block_size
cat /sys/class/block/sda2/size
cat /sys/class/block/sda3/size
```

当前预期值必须是：

```text
/sys/block/sda/size                  = 62533296
logical_block_size                  = 512
/sys/class/block/sda2/size          = 25165824
/sys/class/block/sda3/size          = 12582912
```

如果分区尺寸不同，不要执行后面的直写命令。如果 `sda3` 尚未创建，先按第 8 节在
RAM-only rescue 中拆分分区。

配置板上网络并用小文件测试 HTTP：

```bash
ip link set eth0 up
ip address replace 192.168.88.2/24 dev eth0
ip address show dev eth0
ping -c 3 192.168.88.1
busybox wget -O /dev/null http://192.168.88.1:8000/board.dtb
```

写目标分区前停止自动挂载服务、卸载目标并同步缓存。下面以 `sda3` 为例：

```bash
systemctl stop systemd-udevd-control.socket \
  systemd-udevd-kernel.socket systemd-udevd.service \
  2>/dev/null || true
umount /dev/sda3 2>/dev/null || true
sync
findmnt -rn -S /dev/sda3
```

最后一条必须没有输出。如果有输出，绝对不要继续写盘。烧录 `sda2` 时把这两处
`sda3` 改成 `sda2`。

## 5. 通过网络直写 12 GiB `sda2`

在板上原厂 Linux 的 root shell 中再次检查尺寸和挂载状态：

```bash
test "$(cat /sys/class/block/sda2/size)" = 25165824
umount /dev/sda2 2>/dev/null || true
sync
findmnt -rn -S /dev/sda2
```

`findmnt` 必须没有输出。然后把 HTTP 响应体直接写入块设备：

```bash
busybox wget -O /dev/sda2 \
  http://192.168.88.1:8000/sdcard-la-clean-12g-20260811.img
wget_rc=$?
sync
test "$wget_rc" -eq 0
```

如果 `wget` 中断、返回非 0 或 PC 端不是 `200` 响应，此时 `sda2` 只是部分镜像，不要挂载、
不要启动；修复网络后从头重写整个镜像。

传输成功后从整个分区读回并做全量校验：

```bash
dd if=/dev/sda2 bs=16M iflag=fullblock | sha256sum
e2fsck -f -n /dev/sda2
```

读回摘要必须是：

```text
35681b35f3fc73dbeec258a230e5781f22fd718b265c40f1ddfa668984be322d
```

该镜像本身已是严格 12 GiB，不执行 `resize2fs /dev/sda2`。

## 6. 通过网络直写并扩展 6 GiB `sda3`

在板上原厂 Linux 中执行：

```bash
test "$(cat /sys/class/block/sda3/size)" = 12582912
umount /dev/sda3 2>/dev/null || true
sync
findmnt -rn -S /dev/sda3
busybox wget -O /dev/sda3 \
  http://192.168.88.1:8000/alpine-linux-loongarch64.img
wget_rc=$?
sync
test "$wget_rc" -eq 0
```

写入成功后，只读回原镜像覆盖的 690 MiB：

```bash
dd if=/dev/sda3 bs=1M count=690 iflag=fullblock | sha256sum
```

摘要必须是：

```text
0ad295fc3e62dad2dd15ccf575135bc8c17fe8cddb510f3aa9ff44c4e1be2173
```

只有摘要一致后，才修复 ext4 并扩展到整个 6 GiB 分区：

```bash
e2fsck -f -y /dev/sda3
resize2fs /dev/sda3
e2fsck -f -n /dev/sda3
```

690 MiB 镜像扩展到 6 GiB 只是让文件系统可以使用分区中的剩余空间；现有文件不会突然
占满 6 GiB。

原始下载文件 `/home/wuxun/Downloads/alpine-linux-loongarch64-ext4fs.img.xz` 解压后也是
723,517,440 bytes，但原始解压数据的 SHA-256 是
`57c64d68d12aed1e503cc54753ea27f8c38936d6dde78d7c28dfc155763e25ca`。它与 `/srv/tftp`
工作镜像不同，因为工作镜像已做过 ext4 一致性修复；不要混用两个哈希。

## 7. 网络烧录后检查和关机

只检查本次覆盖的目标分区：

```bash
fdisk -l /dev/sda
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS /dev/sda
blkid /dev/sda1 /dev/sda2 /dev/sda3
findmnt -rn -S /dev/sda2
findmnt -rn -S /dev/sda3
e2fsck -f -n /dev/sda2
e2fsck -f -n /dev/sda3
sync
```

`e2fsck -n` 只能用于未挂载分区。检查通过后可直接重启回原厂 Linux，或关机后再断电：

```bash
poweroff
```

要启动 MOSS，重新上电后按第 2 节使用 TFTP runner，并显式选择刚烧录的 `sda2` 或 `sda3`。

## 8. 如何合并和拆分分区

本节的“合并”和“拆分”只覆盖当前板卡的两种已知布局：

- 三分区布局：`sda1` 11.8 GiB + `sda3` 6 GiB + `sda2` 12 GiB；
- 两分区布局：`sda1` 17.8 GiB + `sda2` 12 GiB。

合并是删除 `sda3`、将这 6 GiB 物理空间还给前面的 `sda1`。它不会把 `sda3` 里的文件
自动移入 `sda1`；`sda3` 中需要保留的数据必须先备份。拆分则是先缩小 `sda1` 的 ext4，
再从它的尾部分出严格 6 GiB 的 `sda3`。

> 不能在以 `/dev/sda1` 为根的原厂 Linux 中执行本节命令。
> 在线 root ext4 不能这样缩小，分区表也不能在根分区正在使用时安全改写。

### 8.1 通过 TFTP 进入 RAM-only rescue Linux

`/srv/tftp` 中仍保留已实板进入过 `MOSS-RESCUE#` 的文件。2026-08-18 的重新校验值为：

| 文件 | 字节数 | SHA-256 |
| --- | ---: | --- |
| `/srv/tftp/board.dtb` | 22,612 | `62a785ee1a9ea97a47ddc7b2fed965e15de0fae62e6117be1831bdba73aa3103` |
| `/srv/tftp/moss-linux-rescue-uImage` | 10,700,515 | `f49c36145a80b4e7fdb7d0824b983a58a3118f2017c2e5618fb51973300dcf0d` |
| `/srv/tftp/moss-ls2k1000-rescue-initramfs.cpio.gz` | 5,977,865（`0x5b3709`） | `b865dadd22a7e93de7fe6d9331f38fec28444ee582ad1a4212c244ba06a16a56` |

先在 PC 端重新执行 `sha256sum` 并确认 TFTP 服务正常。在原厂 U-Boot 中使用一次性环境启动：

```text
setenv ipaddr 192.168.88.2
setenv serverip 192.168.88.1
setenv netmask 255.255.255.0
setenv ethact ethernet@40040000

tftpboot 0x900000000a000000 board.dtb
tftpboot 0x9000000006000000 moss-ls2k1000-rescue-initramfs.cpio.gz
tftpboot 0x9000000098000000 moss-linux-rescue-uImage

setenv bootargs earlycon console=ttyS0,115200 initrd=0x6000000,0x5b3709 rdinit=/init panic=10
mw.l 0x1fe27030 0
mw.l 0x1fe27038 0xdf847580
mw.l 0x1fe27030 2
mw.l 0x1fe27034 1
bootm 0x9000000098000000 - 0x900000000a000000
```

只有串口出现 `MOSS-RESCUE#` 后才继续。rescue 运行于 RAM，它会自动尝试配置
`eth0=192.168.88.2/24`，且不会自动挂载 SATA 分区。

先进行下列只读核对：

```bash
/bin/busybox grep '^/dev/sda' /proc/mounts
/bin/busybox grep '^/dev/sda' /proc/swaps
/bin/busybox cat /sys/block/sda/size
sfdisk --dump /dev/sda
sfdisk --verify /dev/sda
fdisk -l /dev/sda
```

前两条必须没有输出，磁盘必须是 `62533296` sectors。把 `sfdisk --dump` 的完整文本保存在
PC 的串口日志里，不要只留在将要改动的 SATA 盘上。

另外让 `sfdisk` 把 DOS/MBR 分区表扇区备份到 rescue 的 RAM：

```bash
sfdisk --backup-pt-sectors \
  --backup-file /run/ls2k-sda-pt-before /dev/sda
/bin/busybox ls -l /run/ls2k-sda-pt-before*
```

这些文件仍在 RAM 里，断电会消失。DOS/MBR 通常只有一个很小的备份文件，可用 Base64 打到
已开启采集的串口日志中：

```bash
for backup in /run/ls2k-sda-pt-before*; do
  echo "BEGIN $backup"
  /bin/busybox base64 "$backup"
  echo "END $backup"
done
```

串口文本备份只能恢复分区表，不能恢复分区里的文件。进行合并或拆分前，`sda1` 里的原厂
Linux 和 `sda3` 里需要保留的数据仍必须有 PC/移动存储上的独立备份。如果没有已验证的离盘备份，
停在这里，不执行后面的写分区表命令。

### 8.2 合并：删除 `sda3` 并把 6 GiB 还给 `sda1`

该操作会破坏 `sda3` 的分区入口和文件系统内容。确认 `sda3` 已备份，且当前表严格是第 1 节的
三分区布局后，在 `MOSS-RESCUE#` 中执行：

```bash
/bin/busybox swapoff -a 2>/dev/null || true
/bin/busybox grep '^/dev/sda' /proc/mounts
e2fsck -f /dev/sda1
sfdisk --lock --delete /dev/sda 3
printf 'start=2048, size=37363712\n' | \
  sfdisk --lock --wipe never --wipe-partitions never -N 1 /dev/sda
/bin/busybox sync
partprobe /dev/sda
sfdisk --dump /dev/sda
sfdisk --verify /dev/sda
```

目标表必须只剩：

```text
/dev/sda1 : start=2048,     size=37363712, type=83
/dev/sda2 : start=37365760, size=25165824, type=83
```

如果 `partprobe` 无法重读分区表，不要在旧内核视图上扩展文件系统；重新启动同一 RAM rescue，
再核对分区表。内核已看到新的 `sda1` 边界后，才执行：

```bash
e2fsck -f /dev/sda1
resize2fs /dev/sda1
e2fsck -f -n /dev/sda1
```

最终 `sda1` 为 37,363,712 sectors，即 19,130,220,544 bytes，约 17.8 GiB。`sda2` 的起始位置和容量
不变。

### 8.3 拆分：从 `sda1` 尾部新建 6 GiB `sda3`

只有当前表是上一节的两分区布局时才能执行。顺序必须是“先缩文件系统，后缩分区”；
反过来会截断 ext4。

先检查文件系统最小容量，然后把它缩到 11 GiB。`resize2fs` 如果因已用数据太多而失败，就先
清理或备份数据，不得继续改分区表。

```bash
/bin/busybox swapoff -a 2>/dev/null || true
/bin/busybox grep '^/dev/sda' /proc/mounts
e2fsck -f /dev/sda1
resize2fs -P /dev/sda1
resize2fs /dev/sda1 11G
e2fsck -f /dev/sda1
```

缩小 ext4 成功后，才缩短第一分区并新建第三分区：

```bash
printf 'start=2048, size=24780800\n' | \
  sfdisk --lock --wipe never --wipe-partitions never -N 1 /dev/sda
printf 'start=24782848, size=12582912, type=83\n' | \
  sfdisk --lock --wipe never --wipe-partitions never -N 3 /dev/sda
/bin/busybox sync
partprobe /dev/sda
sfdisk --dump /dev/sda
sfdisk --verify /dev/sda
```

结果必须精确回到第 1 节表中的三分区边界，特别是：

```text
/dev/sda1 : start=2048,     size=24780800, type=83
/dev/sda3 : start=24782848, size=12582912, type=83
/dev/sda2 : start=37365760, size=25165824, type=83
```

内核已重读新分区表后，把 11 GiB ext4 扩展到新 `sda1` 的全部 11.8 GiB：

```bash
e2fsck -f /dev/sda1
resize2fs /dev/sda1
e2fsck -f -n /dev/sda1
```

新建的 `sda3` 只有分区边界，不是可用的 Alpine 根文件系统。重启原厂 Linux 后，按第 6 节
直接向它写入 Alpine 镜像并扩展 ext4。

`resize2fs` 可能改变 `/swapfile-moss` 的物理 extent。当前 `run_ls2k1000_serial_tftp.py` 会在每次启动
MOSS 前由原厂 Linux 重新发现并校验该 swapfile extent，不依赖旧的固定 LBA。分区拆分后仍要先正常
启动原厂 Linux，检查 `sda1` 可读写、`e2fsck -n` 通过和 `/swapfile-moss` 存在，再启动 MOSS。

## 9. SATA-USB 转接器作为备用方案

网络直写是当前无转接器时的主流程。如果无法启动原厂 Linux/rescue，再关机拆盘并使用
SATA-USB 转接器。PC 上设备可能是 `/dev/sdb`、`/dev/sdc` 或其他名称，必须核对容量、型号、
序列号和分区表，不能沿用上次的设备名。

```bash
lsblk -b -o NAME,PATH,SIZE,MODEL,SERIAL,TRAN,RM,TYPE,FSTYPE,MOUNTPOINTS
sudo fdisk -l /dev/sdb
findmnt --source /dev/sdb2
findmnt --source /dev/sdb3
```

用转接器写盘时，可把第 5、6 节的网络写入命令替换为 `dd if=<镜像> of=/dev/sdbN ...`，
但后续哈希、`e2fsck` 和 `resize2fs` 验收口径不变。仍然绝对不得使用 `of=/dev/sdb` 整盘。

## 10. SPI 固件保护边界

当前生产流程不执行任何 SPI erase/write。原厂 U-Boot、environment、bdinfo 和 DTB 的只读备份仍位于
`/srv/tftp/ls2k1000la-spi-*-20260809.bin`：

```bash
sha256sum /srv/tftp/ls2k1000la-spi-*-20260809.bin
```

候选 U-Boot 未证明与本板原厂 DDR 参数和恢复流程等价，不写入 SPI，也不执行 `saveenv`。当前
TFTP + RAM 方案已能启动 MOSS，并保留原厂固件作为恢复入口。

日常构建和上板入口见 [龙芯二号板当前使用指南](龙芯二号板当前使用指南.md)，历史分区、rescue 和 SPI
验证依据见 [龙芯二号板调试状态报告](龙芯二号板调试状态报告-20260808.md)。
