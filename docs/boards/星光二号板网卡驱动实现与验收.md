# VisionFive 2 GMAC1 驱动实现与验收

本文记录 MOSS 在 StarFive VisionFive 2 v1.3B 上接入 GMAC1 实体网口的实现、设计边界和验收方法。实现基线为提交 `d803c88e`（`feat: 完善 VF2 GMAC1 以太网驱动`），记录日期为 2026-08-13。

日常构建、TFTP 和 U-Boot 操作见 [VisionFive 2 上板常用指令](星光二号板启动指令.md)，整板移植历史见 [VisionFive 2 工作总结](星光二号板工作总结.md)。
两项改动的原问题、根因和优化路径总览见 [VF2 GMAC1 与双板串口交互优化总结](星光二号板网卡与串口优化总结.md)。

## 1. 结论与验收边界

VF2 当前使用的不是 `virtio-net`，而是板载实体 Ethernet：

```text
JH7110 GMAC1 (Synopsys DWMAC 5.20 / EQoS)
        │ RGMII-ID
        ▼
Motorcomm YT8531 PHY
        │ 双绞线
        ▼
外部交换机或直连 PC
```

当前结论分为两层：

| 项目 | 结论 |
| --- | --- |
| 基础实板网络 | MOSS 与直连 PC 的双向 TCP 已在此前实板测试中通过 |
| 本轮驱动增强 | 状态机、两套 DT、交叉构建和 DMA section 检查已通过 |
| 断链恢复和三速协商 | 已实现自动化脚本，本轮未连接 VF2 实板执行 |
| 公网 `apk update` / `apk fetch` | 已实现分层测试，本轮未连接 VF2 实板执行 |

因此，不能用此前的基础 TCP 结果替代本轮新增的断链、10/100/1000 Mbps 重协商和 APK 拉取验收。

## 2. 代码分层

| 文件 | 作用 |
| --- | --- |
| `vendor/axdriver/src/jh7110.rs` | 从 DTB 发现 GMAC1，处理时钟、reset、syscon、IRQ 和 JH7110 cache 操作 |
| `vendor/axdriver_net/src/dwmac_jh7110.rs` | MAC、DMA、MDIO、PHY、TX/RX、中断和错误恢复主驱动 |
| `vendor/axdriver_net/src/dwmac_jh7110/dma.rs` | 描述符、DMA buffer、静态 DMA storage 和所有权位 |
| `vendor/axdriver_net/src/dwmac_jh7110/registers.rs` | DWMAC 5.20 寄存器偏移和 bit 定义 |
| `vendor/axdriver_net/src/dwmac_jh7110_state.rs` | 可在主机运行测试的 JH7110 寄存器策略 |
| `vendor/axdriver_net/src/dwmac_common_state.rs` | VF2 与 LS2K1000LA 共用的 Clause 22、链路和 ring 状态机 |
| `scripts/check_vf2_gmac_static.sh` | DT contract、状态机、VF2 构建和 DMA section 静态验收 |
| `scripts/run_vf2_gmac_test.py` | 串口控制 U-Boot/MOSS 并执行实板网络与 APK 测试 |

生产数据路径为：

```text
DTB ethernet1
  -> Jh7110GmacDriver::probe_global
  -> DwmacJh7110
  -> NetDriverOps
  -> axnet / smoltcp
  -> socket / BusyBox / apk
```

QEMU 的 RISC-V/LoongArch 网络仍使用 virtio 设备，与 VF2 实体 GMAC1 是不同驱动路径。

## 3. 硬件与设备树契约

### 3.1 固定硬件资源

VF2 GMAC1 的关键硬件资源如下：

| 资源 | 当前值 |
| --- | --- |
| MAC register window | `0x16040000`，最小要求 `0x1164` 字节 |
| MAC IRQ | 主线和 fixture 中为 `78`，其余两个中断为 `77`、`76` |
| AXI/AHB reset | SYSCRG ID `66` / `67` |
| RGMII syscon | 主线为 `sys_syscon + 0x90`，shift `2` |
| PHY | Motorcomm YT8531，Clause 22 地址 `0` |

主线 DT 的时钟契约为：

| `clock-names` | SYSCRG ID | 说明 |
| --- | ---: | --- |
| `stmmaceth` | 98 | GMAC1 AXI |
| `pclk` | 97 | GMAC1 AHB |
| `ptp_ref` | 102 | PTP reference |
| `tx` | 106 | GMAC1 TX inverter |
| `gtx` | 107 | GMAC1 GTXC |

ID 106 是 inverter，本身没有 gate。MOSS 直接操作 CRG 时启用其父级 GMAC1 TX gate（ID 105），同时启用 97、98、102 和 107。

### 3.2 支持的 DT 格式

驱动同时接受：

- 当前主线 Linux：`starfive,jh7110-dwmac`；
- StarFive U-Boot 2021.10：`starfive,jh7110-eqos-5.20`。

两者都必须通过 `/aliases/ethernet1` 指向 GMAC1，并明确声明 `phy-mode = "rgmii-id"`。驱动只支持 VF2 v1.3B 的 GMAC1 RGMII-ID 接线，会拒绝 v1.2A 的 RMII。

主线格式通过 `phy-handle` 找到 PHY。旧 U-Boot DT 没有 `phy-handle`，其 `ethernet-phy@1` 还缺少 `reg`；兼容路径只在当前 GMAC1 的 MDIO 子树中查找该节点，最后使用 VF2 v1.3B 实际 strap 地址 0，避免误选另一个 MAC 下的同名 PHY。

## 4. 初始化与生命周期

probe 只完成以下工作：

1. 校验 DT、启用 GMAC1 时钟并解除 AXI/AHB reset；
2. 把 syscon 切到 RGMII；
3. 读取或生成 MAC 地址；
4. 停止 MAC/DMA，清理旧状态；
5. 注册 IRQ；如果注册失败则保留 polling 模式。

probe 不启动 DMA。第一次 `receive`、`transmit` 或 TX reclaim 进入 `ensure_started()` 后，驱动才 reset DMA、初始化描述符、配置 MTL/MAC/DMA 并启动队列。这避免设备注册完成但网络栈尚未接管时，DMA 提前写入内存。

驱动的 DMA storage 是单实例资源，`DmaStorage::take()` 保证不会同时创建第二个使用同一静态 ring 的设备。当前实现因此只接入 GMAC1，没有同时支持 GMAC0。

## 5. DMA、描述符与缓存一致性

### 5.1 Ring 布局

| 项目 | 数值 |
| --- | ---: |
| TX descriptors | 64 |
| RX descriptors | 64 |
| 单个 descriptor | 64 字节，对齐到 64 字节 cache line |
| 单个 TX/RX DMA buffer | 2048 字节 |
| 网络栈 packet buffer 上限 | 1526 字节 |

DWMAC 基础 descriptor 为 16 字节。JH7110 AXI data width 为 8 字节，因此 64 字节 descriptor 的 DSL 为：

```text
(64 - 16) / 8 = 6
```

一个 descriptor 独占一条 cache line，DMA 更新描述符时不会因为 invalidate 丢失相邻描述符上的 CPU 修改。

### 5.2 非一致性 DMA

JH7110 的 GMAC DMA 不是 CPU cache coherent。所有 CPU/DMA 所有权切换都执行：

1. buffer 或 descriptor 的 clean/invalidate；
2. `fence iorw, iorw`；
3. 最后写 `OWN` 或 tail pointer。

JH7110 平台通过 L2 cache 的 flush64 MMIO 命令完成 clean-and-invalidate。ring 和 buffer 还被放入 `.dma_uncached` section，静态脚本会检查该 section 存在、可写且不可执行。

### 5.3 Tail pointer 语义

RX 与 TX tail 的语义不同：

- RX tail 是 inclusive，指向最后一个已经归还给 DMA 的 descriptor；
- TX tail 是 exclusive，指向最后一个已提交 descriptor 的下一项，即 producer boundary。

初始 RX tail 指向 ring 最后一项，使整个预置 RX ring 对 DMA 可见；初始 TX tail 指向 descriptor 0，表示尚无 TX 工作。RBU/RPS 恢复时重新发布 `rx_index` 的前一项，TBU 恢复时重新发布 TX submit boundary，不能用下一接收项或 TX clean index 代替。

### 5.4 MAC 接收过滤

驱动明确设置 Address0 High 的 `AE`，使用主 MAC 地址做 perfect unicast match，并接收广播。由于 `NetDriverOps` 目前没有 multicast-list 回调，驱动采用 all-multicast 回退以支持 IPv6 等用户，同时清除固件可能遗留的 `PR`/`RA`，不会常驻 promiscuous mode。

MAC 同时启用 `ACS` 和 `CST`，让硬件剥离 pad/FCS，避免把 RX descriptor 中包含的 4 字节 FCS 交给网络栈。

## 6. PHY 与链路状态机

驱动通过 DWMAC MDIO 控制器访问 YT8531，运行期采用 Clause 22 状态机：

1. BMSR 的 link bit 为 latch-low，所以连续读取两次；
2. 自动协商完成后读取 ANAR/ANLPAR 和 1000BASE-T control/status；
3. 解析 10/100/1000 Mbps、half/full duplex 和 pause 能力；
4. 更新 MAC speed、duplex、TX/RX flow control；
5. 根据 DT 配置更新 YT8531 对应速率的 TX clock inversion。

链路默认每秒轮询一次。暂时性 MDIO 读取失败会保留最后一次有效链路状态，不会把总线抖动直接解释为拔线；明确读到 link down 才关闭 MAC 收发。

PHY 的 RX/TX internal delay 和 drive strength 仍由 U-Boot 冷启动阶段配置。MOSS 只接管运行期链路模式和 TX clock phase，因此上板测试不能跳过 VF2 v1.3B 的正常固件启动链。

## 7. 中断与错误恢复

硬中断处理只做三件事：

1. 读取 DMA status；
2. 屏蔽已触发的 RX/TX source 并 acknowledge；
3. 通过 atomic event bitmap 把工作交给 `poll_complete()`。

deferred poll 完成 RX/TX 检查和 TX reclaim，队列排空后重新开中断；重开后再次读取 status，覆盖“检查队列”和“开中断”之间的竞争窗口。IRQ 注册失败时，polling 模式直接读取硬件 status，功能不会依赖中断一定可用。

错误处理分为：

| 事件 | 处理 |
| --- | --- |
| `RBU` / `RPS` | 重新发布最后归还的 RX descriptor |
| `TBU` | 重新发布 TX producer boundary |
| TX descriptor error summary | 记录 descriptor index 和 status，再回收 |
| `TPS` / `FBE` | 停止 MAC/DMA、reset、重建 ring、重新启动并刷新 PHY 状态 |

RX packet 非法或网络 buffer 分配失败时，descriptor 仍会重新 arm，避免一个 drop 永久缩小 RX ring。

## 8. 与 LS2K1000LA 的共用部分

VF2 EQoS 5.20 和 LS2K1000LA DWMAC 3.x 的寄存器及 descriptor 格式不同，但以下规则已提取到 `dwmac_common_state.rs`：

- Clause 22 自动协商和 pause 解析；
- PHY sample 到 link transition 的转换；
- probe、IRQ registration、DMA first-use start 生命周期；
- RX drop 必须归还 descriptor；
- TX ring submit/clean/in-flight ownership。

LA 原有状态测试继续复用这些规则。VF2 专用的 queue field、IRQ mask、AXI burst、MAC filter 和 YT8531 phase 策略保留在 `dwmac_jh7110_state.rs`。

## 10. 实板自动验收

### 10.1 PC 网络准备

PC 直连网口需要地址 `192.168.88.1/24`：

```bash
sudo ip addr replace 192.168.88.1/24 dev enp3s0
sudo ip link set enp3s0 up
```

若要测试 DNS、TLS 和 APK，PC 还必须为 `192.168.88.0/24` 提供 IPv4 forwarding 和 NAT：

```bash
sudo scripts/setup_vf2_network.sh apply
```

`apply` 读取持有 `192.168.88.1` 的板端接口和 PC 默认上联网口，启用 `ip_forward` 并安装运行期 nftables forwarding/NAT table。

### 10.2 基础、断链和双向 TCP

关闭占用 `/dev/ttyACM0` 的终端程序后执行：

```bash
sudo scripts/run_vf2_gmac_test.py \
  --serial /dev/ttyACM0 \
  --interface enp3s0 \
  --log vf2-gmac.log
```

脚本等待操作者复位开发板，然后依次执行：

1. 打断 U-Boot autoboot；
2. 临时设置 `ipaddr`、`serverip` 和 netmask；
3. TFTP 加载 `moss-vf2.bin` 并 `go 0x40200000`；
4. 板端 ping PC，验证 link、ARP 和 ICMP；
5. MOSS 到 PC、PC 到 MOSS 各传输 64 KiB，并核对长度和 SHA-256；
6. host link flap 后重复网络测试。

脚本不执行 `saveenv`。退出时会恢复 PC 网口原管理状态、测速修改过的 ethtool 参数以及原 `/srv/tftp/kernel`。

### 10.3 三速重协商

```bash
sudo scripts/run_vf2_gmac_test.py \
  --speed-suite \
  --log vf2-gmac-speed.log
```

脚本依次只广告 1000/100/10baseT Full，每次等待 carrier、ping 并重复双向 64 KiB TCP 测试，最后恢复原 advertised modes。

### 10.4 APK 拉取

板端 rootfs 必须已经具备：

- 可用的 `/etc/apk/repositories`；
- DNS 配置；
- 正确的系统时间和 CA certificate；
- `apk`、BusyBox `nslookup`、`wget` 和 `find`。

执行：

```bash
sudo scripts/run_vf2_gmac_test.py \
  --apk-package busybox \
  --log vf2-gmac-apk.log
```

脚本按以下层次验收：

```text
link/ARP/ICMP
  -> 双向 TCP
  -> DNS
  -> HTTPS/TLS
  -> apk update
  -> apk fetch
  -> /tmp/vf2-apk 中实际存在 *.apk
```

只有最后一项也通过，才能写成“APK 可以拉取”。

## 11. 故障定位

| 失败位置 | 优先检查 |
| --- | --- |
| U-Boot TFTP 失败 | PC IP、网线、TFTP service、`/srv/tftp/kernel` |
| MOSS 无 link | DT `ethernet1`、RGMII-ID、时钟/reset、syscon、YT8531 MDIO |
| ping PC 失败 | PHY link、MAC address、RX filter、ARP、板端 IP/网关 |
| TCP 仅单向失败 | 对应 TX/RX descriptor ownership、cache maintenance 和 tail pointer |
| link flap 后不恢复 | BMSR 双读、deferred poll、RBU/RPS/TBU 处理 |
| 只有 100 或 10 Mbps 失败 | YT8531 对应速率 TX clock inversion 和 MAC PS/FES |
| DNS 失败 | PC forwarding/NAT、板端 DNS 配置 |
| HTTPS 失败 | 系统时间、CA certificate、TLS 工具 |
| `apk update` 失败 | repository URL、架构、DNS/TLS 和仓库签名 key |
| `apk fetch` 返回成功但无文件 | 输出目录、包名；自动脚本会额外检查 `*.apk` |

`git clone` 或 `scp` 失败不能直接归因于网卡。它们还依赖 DNS、TLS/SSH、CA、用户态工具和服务端配置，应先按上述分层测试确定失败层。

## 12. 当前限制与下一步

当前明确限制：

- 只支持 VF2 v1.3B GMAC1 RGMII-ID，不支持 v1.2A RMII；
- 只创建一个 GMAC DMA storage，没有同时接入 GMAC0；
- 没有动态 multicast-list API，当前使用 all-multicast 回退；
- PHY delay 和 drive strength 仍依赖 U-Boot 冷启动；
- 本轮尚未在实板执行断链、三速和公网 APK 自动验收。

下一次接板后的完成标准是保存三份原始日志：基础/断链、三速、APK。日志中必须包含双向 TCP SHA-256、每个速率的 carrier 恢复，以及 APK 文件存在检查；全部通过后，才能把增强路径从“静态通过”更新为“实板通过”。
