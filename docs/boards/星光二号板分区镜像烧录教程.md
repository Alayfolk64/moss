# 星光二号板分区镜像烧录教程

本文记录 VisionFive 2 v1.3B 当前多分区 SD 卡的镜像烧录方法。核心规则是：rootfs 镜像写入具体分区，不能写入整张卡。

## 1. 当前分区布局

2026-08-13 实际整理并校验后的 128 GB SD 卡布局如下：

| Moss 中的名称 | 读卡器连接 PC 时的示例 | 用途 | 实测容量 | 文件系统 |
| --- | --- | --- | --- | --- |
| `/dev/sda1` | `/dev/sdb1` | Debian Linux | 29.8 GiB | ext4 |
| `/dev/sda2` | `/dev/sdb2` | Moss rootfs | 29.8 GiB | ext4 |
| `/dev/sda3` | `/dev/sdb3` | Alpine Linux 比赛环境 | 27.9 GiB | ext4 |
| `/dev/sda4` | `/dev/sdb4` | 第二个比赛环境 | 27.9 GiB | 当前空白 |
| `/dev/sda5` | `/dev/sdb5` | 内存交换分区 | 3.7 GiB | swap |

Moss 的 `/dev/sdaN` 是内核内部的逻辑名称。SD 卡插入 PC 后可能显示为 `/dev/sdbN`、`/dev/sdcN` 或其他名称，两者不要混用。

> `of=/dev/sdb` 会覆盖整张卡及 GPT 分区表。当前布局下必须使用 `of=/dev/sdb2`、`of=/dev/sdb3` 或 `of=/dev/sdb4` 这类具体分区。

## 2. 写卡前确认设备

插入读卡器后执行：

```bash
lsblk -b -o NAME,PATH,SIZE,MODEL,SERIAL,TRAN,RM,TYPE,FSTYPE,MOUNTPOINTS
```

根据容量、型号、`TRAN=usb` 和 `RM=1` 共同确认 SD 卡。本文的实测设备是 `/dev/sdb`，但重新插拔后设备名可能改变，不能直接照抄。

查看分区表和文件系统签名：

```bash
sudo sgdisk --print /dev/sdb
sudo blkid /dev/sdb1 /dev/sdb2 /dev/sdb3 /dev/sdb4 /dev/sdb5
```

烧录前确认目标分区没有挂载。例如目标是第三分区：

```bash
findmnt --source /dev/sdb4
```

有输出时先卸载：

```bash
sudo umount /dev/sdb3
```

可以额外备份 GPT；该文件只保存分区表，不包含分区内的数据：

```bash
sudo sgdisk --backup=sdcard-vf2-before-write.gpt /dev/sdb
```

## 3. 检查压缩镜像

本次使用的 Alpine 镜像为：

```text
/home/wuxun/Downloads/alpine-linux-riscv64-ext4fs.img.xz
```

先检查 xz 数据完整性：

```bash
xz -t '/home/wuxun/Downloads/alpine-linux-riscv64-ext4fs.img.xz'
```

命令正常退出且没有输出，表示压缩数据校验通过。再查看压缩前后的大小：

```bash
xz --robot --list '/home/wuxun/Downloads/alpine-linux-riscv64-ext4fs.img.xz'
```

该镜像解压后是 723,517,440 字节，即 690 MiB 的 ext4 文件系统镜像，必须小于目标分区容量。

## 4. 将 Alpine 镜像写入第三分区

确认本次目标确实是 `/dev/sdb3` 后，在同一个 Bash 终端执行：

```bash
set -o pipefail
xz -dc '/home/wuxun/Downloads/alpine-linux-riscv64-ext4fs.img.xz' | \
  sudo dd of=/dev/sdb3 bs=16M oflag=direct status=progress conv=fsync
```

参数含义：

- `xz -dc` 将镜像解压到标准输出，不生成额外的临时镜像文件；
- `of=/dev/sdb3` 只覆盖第三分区；
- `bs=16M` 以 16 MiB 为传输块；
- `oflag=direct` 减少页缓存对进度和写回的干扰；
- `conv=fsync` 在 `dd` 成功退出前把数据刷新到设备；
- `pipefail` 保证解压或写盘任意一端失败时整条管道返回失败。

## 5. 全量校验烧录结果

先计算压缩镜像解压后的 SHA-256：

```bash
xz -dc '/home/wuxun/Downloads/alpine-linux-riscv64-ext4fs.img.xz' | sha256sum
```

再从目标分区读回相同的 690 MiB：

```bash
sudo dd if=/dev/sdb3 bs=1M count=690 iflag=fullblock status=progress | sha256sum
```

本次实测两端摘要均为：

```text
d547220caf7b3ce4c1d67560bbed66f4ee491d10718d1ea3e55741019aef5eb4
```

只有两个摘要完全一致，才能确认写入内容无误。

## 6. 检查并扩展 ext4

原镜像只有 690 MiB，烧录后先修复文件系统，再扩展到整个第三分区：

```bash
sudo e2fsck -f -y /dev/sdb4
sudo resize2fs /dev/sdb4
sudo e2label /dev/sdb4 ''
sudo e2fsck -f -n /dev/sdb4
```

这里清空了 ext4 label，使分区继续按 `/dev/sda3`、`/dev/sda4` 选择，不依赖自定义名称。最后一条命令只读检查；必须正常结束后再继续。

查看最终布局：

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,LABEL,UUID,PARTUUID,MOUNTPOINTS /dev/sdb
sudo sgdisk --verify /dev/sdb
```

本次实测结果是第三分区为 27.9 GiB ext4，UUID 为 `dff3fc28-3a72-4c0f-92cb-b681cc185680`；第四分区没有文件系统签名；第五分区仍为 swap。

## 7. 向其他分区烧录镜像

以后把新的 ext4 rootfs 写入第四分区时，先重新确认设备名和 `/dev/sdb4` 未挂载，然后将上述命令中的目标改为 `/dev/sdb4`。例如仓库根目录的未压缩镜像：

```bash
sudo dd if=sdcard-rv.img of=/dev/sdb4 bs=16M \
  iflag=fullblock oflag=direct status=progress conv=fsync
sudo e2fsck -f -y /dev/sdb4
sudo resize2fs /dev/sdb4
sudo e2label /dev/sdb4 ''
sudo e2fsck -f -n /dev/sdb4
```

不要修改第五分区；它保留给 swap。

## 8. 安全断电

所有检查完成后执行：

```bash
sync
udisksctl power-off -b /dev/sdb
```

确认 `/dev/sdb` 从 `lsblk` 中消失后，再拔出读卡器。

## 9. 在 VisionFive 2 上选择根分区

通过 TFTP 加载 Moss 内核前，在 U-Boot 中修改本次启动的 DT bootargs。第三分区 Alpine 环境使用：

```text
fdt addr 0x42200000
fdt resize 4096
fdt set /chosen bootargs root=/dev/sda3
```

第四分区写入 rootfs 后使用：

```text
fdt set /chosen bootargs root=/dev/sda4
```

完整的 TFTP 和启动命令见 [星光二号板启动指令](星光二号板启动指令.md)。

## 10. 常见镜像压缩格式的流式解压与写入

第 4 节中的命令：

```bash
xz -dc rootfs.img.xz | sudo dd of=/dev/sdb3 ...
```

确实是边解压、边写入：`xz -dc` 把解压后的原始镜像输出到标准输出，管道再把这些字节交给 `dd`。它不需要先在磁盘上保存一份解压后的 `.img`，但 `xz -dc` 只适用于 xz 压缩格式。gzip、bzip2、zstd 和 zip 需要使用各自的解压命令。

下面的 `/dev/sdX3` 是故意不可直接执行的占位符。每次烧录前都必须重新用 `lsblk` 确认 SD 卡和目标分区，再把它替换为本次实际设备，例如 `/dev/sdb3`。rootfs 分区镜像必须写入 `/dev/sdXN` 这样的具体分区，不能写到 `/dev/sdX` 整盘，也不要使用设备通配符。

写入前统一执行：

```bash
lsblk -b -o NAME,PATH,SIZE,MODEL,SERIAL,TRAN,RM,TYPE,FSTYPE,MOUNTPOINTS
findmnt --source /dev/sdX3
sudo blockdev --getsize64 /dev/sdX3
set -o pipefail
```

如果 `findmnt` 有输出，应先卸载目标分区：

```bash
sudo umount /dev/sdX3
```

`pipefail` 很重要：没有它时，前端解压失败而 `dd` 恰好正常退出，整条管道可能错误地显示成功。所有压缩镜像都应先通过完整性检查，并确认解压后大小不超过 `blockdev --getsize64` 显示的目标分区容量。

### 10.1 未压缩的 `.img` 或 `.raw`

先确认它本身是 ext4 等文件系统镜像，而不是带 GPT/MBR 的整盘镜像：

```bash
file '/home/zjr/Data/buildstorm-rv64/rootfs.img'
blkid -p '/home/zjr/Data/buildstorm-rv64/rootfs.img'
fdisk -l '/home/zjr/Data/buildstorm-rv64/rootfs.img'
stat -c '%s bytes' '/home/zjr/Data/buildstorm-rv64/rootfs.img'
```

写入具体分区：

```bash
sudo dd if='/home/zjr/Data/buildstorm-rv64/rootfs.img' of=/dev/sdb4 bs=16M \
  iflag=fullblock oflag=direct status=progress conv=fsync
```

如果 `fdisk -l` 列出了镜像内部的 `rootfs.img1`、`rootfs.img2` 等分区，它就是整盘镜像，不能直接写入 `/dev/sdX3`。

### 10.2 xz：`.img.xz`

检查压缩数据、查看大小并计算解压后字节数：

```bash
xz -t '/path/to/rootfs.img.xz'
xz --robot --list '/path/to/rootfs.img.xz'
xz -dc '/path/to/rootfs.img.xz' | wc -c
```

流式写入：

```bash
xz -dc '/path/to/rootfs.img.xz' | \
  sudo dd of=/dev/sdX3 bs=16M iflag=fullblock \
    oflag=direct status=progress conv=fsync
```

### 10.3 gzip：`.img.gz`

检查压缩数据并计算解压后字节数：

```bash
gzip -t '/path/to/rootfs.img.gz'
gzip -dc '/path/to/rootfs.img.gz' | wc -c
```

流式写入：

```bash
gzip -dc '/path/to/rootfs.img.gz' | \
  sudo dd of=/dev/sdX3 bs=16M iflag=fullblock \
    oflag=direct status=progress conv=fsync
```

### 10.4 bzip2：`.img.bz2`

检查压缩数据并计算解压后字节数：

```bash
bzip2 -t '/path/to/rootfs.img.bz2'
bzip2 -dc '/path/to/rootfs.img.bz2' | wc -c
```

流式写入：

```bash
bzip2 -dc '/path/to/rootfs.img.bz2' | \

```

### 10.5 zstd：`.img.zst` 或 `.img.zstd`

检查压缩数据并计算解压后字节数：

```bash
zstd -t '/path/to/rootfs.img.zst'
zstd -dc '/path/to/rootfs.img.zst' | wc -c
```

流式写入：

```bash
zstd -dc '/path/to/rootfs.img.zst' | \
  sudo dd of=/dev/sdX3 bs=16M iflag=fullblock \
    oflag=direct status=progress conv=fsync
```

### 10.6 zip：`.img.zip`

zip 可以包含多个文件，因此必须先检查成员列表，并在解压时明确指定镜像成员名：

```bash
unzip -t '/path/to/rootfs.zip'
unzip -l '/path/to/rootfs.zip'
unzip -p '/path/to/rootfs.zip' 'rootfs.img' | wc -c
```

假设压缩包内的准确成员名是 `rootfs.img`，流式写入：

```bash
unzip -p '/path/to/rootfs.zip' 'rootfs.img' | \
  sudo dd of=/dev/sdX3 bs=16M iflag=fullblock \
    oflag=direct status=progress conv=fsync
```

不要省略 `rootfs.img` 成员名；否则 `unzip -p` 可能把多个成员依次连接后交给 `dd`，生成损坏的目标分区。

### 10.7 `.tar.*` 归档不能默认当作镜像

`.tar.gz`、`.tgz`、`.tar.xz`、`.tar.bz2` 和 `.tar.zst` 通常是文件树归档，而不是块设备镜像。先查看内容：

```bash
tar -tf '/path/to/rootfs.tar.xz' | head -n 50
```

如果看到 `bin/`、`etc/`、`usr/` 等大量目录，不能把整个 tar 流直接交给 `dd`；应先创建并挂载目标文件系统，再以保留属主、权限、xattr 和 ACL 的方式解包。

只有在 tar 包中明确包含一个原始 `.img` 文件时，才能指定该成员进行流式写入。例如成员名确实为 `images/rootfs.img`：

```bash
tar -xOf '/path/to/rootfs-images.tar.xz' 'images/rootfs.img' | \
  sudo dd of=/dev/sdX3 bs=16M iflag=fullblock \
    oflag=direct status=progress conv=fsync
```

### 10.8 通用的写入前后哈希校验

写入前，对“解压后的字节流”计算 SHA-256。例如 xz：

```bash
xz -dc '/path/to/rootfs.img.xz' | sha256sum
```

同时记录精确的解压后字节数：

```bash
xz -dc '/path/to/rootfs.img.xz' | wc -c
```

假设输出为 `723517440`，写入后从目标分区开头读回完全相同的字节数：

```bash
sudo head -c 723517440 /dev/sdX3 | sha256sum
```

两个 SHA-256 必须一致。gzip、bzip2、zstd 和 zip 只需把前端的 `xz -dc` 换成对应解压命令。必须先完成原始字节流校验，再执行 `e2fsck`、`resize2fs` 或 `e2label`，因为这些操作会合法地修改文件系统内容，使哈希发生变化。
