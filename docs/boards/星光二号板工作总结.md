# VisionFive 2 移植与调试工作总结

本文总结截至 2026-08-15，Moss 在 StarFive VisionFive 2（JH7110）上的移植、驱动接入、问题定位和实板验证结果。日常构建、写卡、TFTP 和 U-Boot 命令见 [VisionFive 2 上板常用指令](星光二号板启动指令.md)。

> 历史记录：本文保留 2026-08-15 验收时使用的 `192.168.88.0/24` 命令，不作为现行默认。VF2 已于
> 2026-08-19 迁移到 PC `192.168.89.1/24`、板卡 `192.168.89.2/24`；新启动请使用链接的上板指令。

## 1. 当前结论

Moss 已能在 VisionFive 2 上稳定完成以下流程：

- 由 OpenSBI 和 U-Boot 进入 S-mode，在 `0x40200000` 启动 Moss；
- 识别 4 GiB 内存和 4 个 U74 S-mode hart；
- 通过 PLIC 分发 SD/MMC、GMAC 等外部中断，并支持时钟中断和核间中断；
- 使用 UART 轮询输入进入可交互 shell，避开 JH7110 固件遗留 RX 中断导致的中断风暴；
- 解析 GPT/MBR 并按 `root=` 选择 ext4 分区，同时保留整盘 ext4 兼容；
- 从当前 SD 卡第 2 分区挂载当前测试 rootfs，进入 shell 并运行四核用户态环境；
- 使用板载 GMAC1 与 PC 双向进行 TCP/IP 通信；
- 运行 glibc 用户程序、cagent、Git 基础操作和板载 `rustc`。

目前 VF2 已具备 Moss 基础功能验证和用户态工作负载调试条件，但 SD 卡仍使用 PIO 搬运数据，eMMC、USB、显示等外设尚未接入。

## 2. 前期确认与启动介质

实板固件环境为 OpenSBI v1.2 和 StarFive U-Boot 2021.10。OpenSBI 使用物理 hart 1 作为启动 hart，hart 0 不提供普通 S-mode 运行环境。

对 StarryOS/TGOSKits 中 VF2 基线的检查和实测表明：已有实现可作为 JH7110 启动、串口和 `simple-sdmmc` 的参考，但不能直接视为 Moss 已完整支持 VF2。基线启动日志中 SD 卡可以识别，而网卡数量仍为 0；Moss 后续对平台层、中断、网络、SMP 和文件系统路径都进行了补充。

U-Boot 中两路 MMC 的对应关系是：

| U-Boot 设备 | 控制器地址 | 当前用途 |
| --- | --- | --- |
| `mmc 0` | `sdio0@16010000` | eMMC，当前 Moss 未接入 |
| `mmc 1` | `sdio1@16020000` | SD 卡，当前 rootfs 设备 |

当前使用方式为：

- Moss 内核由 U-Boot 通过 TFTP 加载到内存；
- SD 卡只保存 rootfs，不保存正在运行的 Moss 内核；
- 当前测试卡保留 GPT 分区表，Moss rootfs 位于第 2 分区；
- U-Boot 在本次 DTB 的 `/chosen/bootargs` 中设置
  `root=/dev/mmcblk1p2 rw`，Moss 根据该参数选择 rootfs。

当前 119.2 GiB SD 卡的实测布局为：

| 分区 | 大小（约） | 用途或状态 |
| --- | ---: | --- |
| `p1` | 29.8 GiB | Debian 13 rootfs，已正常启动 |
| `p2` | 29.8 GiB | Moss rootfs，本轮实机验证目标 |
| `p3` | 27.9 GiB | ext4，包含其他测试环境 |
| `p4` | 27.9 GiB | 未确认用途 |
| `p5` | 3.7 GiB | swap |

这 5 个分区不是 Moss 的启动要求，也不是建议的比赛卡布局，只是当前测试卡的
历史状态。比赛交付新的整卡 `.img.xz` 时，仍可边解压边写入整张 SD 卡，镜像
会覆盖现有分区表。

早期 Moss 块设备层无条件把整张 SD 卡交给 ext4。遇到 GPT 卡时，ext4 实际读到的是
保护 MBR/GPT 而不是超级块，因此报
`Failed to initialize filesystem: LinuxError::EOPNOTSUPP`。本轮已从驱动层解决，
不再要求为了启动 Moss 而清除分区表。

TFTP 使用的是 U-Boot 自带网卡驱动，因此“TFTP 能传内核”只能证明 U-Boot 网络正常，不能证明 Moss 网卡驱动已工作。

## 3. 平台启动支持

新增了独立的 `axplat-riscv64-visionfive2` 平台实现，并提供：

- `make kernel-vf2` 构建入口，产物为 `moss-vf2.bin`；
- VF2 的内存、MMIO、PLIC、UART、SD/MMC 和 GMAC1 配置；
- U-Boot/OpenSBI 直跳入口和早期 Sv39 页表；
- 启动阶段 DTB 保留与解析；
- SBI timer、HSM、IPI 和 system reset 接口；
- 主核和从核的独立启动入口。

启动时保留 U-Boot 提供的 DTB，并将固件、DTB、内核段和空闲内存正确排除或加入内存布局。实板启动结果能够识别 4 GiB RAM，不再把固件或 DTB 所在区域交给页分配器。

## 4. 中断体系

VF2 当前使用三类 RISC-V S-mode 中断：

| 类型 | 入口 | 用途 |
| --- | --- | --- |
| Supervisor timer interrupt | STIP | 调度时钟和定时器 |
| Supervisor software interrupt | SSIP | SMP 核间通知和 TLB shootdown |
| Supervisor external interrupt | SEIP | 进入 PLIC，分发 SD/MMC、GMAC 等设备中断 |

JH7110 的 hart 0 没有对应的 S-mode PLIC context。Moss 的逻辑 CPU 0..3 分别对应物理 hart 1..4，PLIC context 也按该映射计算，不能直接把逻辑 CPU ID 当成物理 hart ID。

PLIC 初始化会清除固件遗留的 source enable，驱动注册处理函数后再启用对应中断源。未注册的外部中断源会被屏蔽，避免形成中断风暴。

## 5. UART 串口

JH7110 UART 是 8250 兼容设备，但寄存器步长为 4 字节。Moss 沿用 U-Boot 已配置的时钟和波特率，不在接管阶段重新初始化硬件。

本轮调试中，启动最初卡在 `MOSS_MEMORY`之后。逐步缩小范围后确认：

1. 通用 S-mode trap、timer 和 IPI 正常；
2. 屏蔽 `S_EXT` 后 Moss 可继续启动，表明卡住与外部中断有关；
3. SD/MMC 的 PLIC source 75 可正常中断，表明 PLIC 全局路径没有故障；
4. 提前注册并开启 UART RX source 会出现无有效数据的持续外部中断，
   导致启动或 shell 输入卡死。

根因是 OpenSBI/U-Boot 交接后 JH7110 UART 保留了不适合 Moss 直接接管的 RX pending 状态。
当前采用可预期的降级方案：

- 在早期初始化中屏蔽 UART IER；
- VF2 console 不向 TTY 声明 UART IRQ，由现有 N_TTY 约每 10 ms 轮询硬件 FIFO；
- `read_bytes()` 每次排空当前可读 FIFO；
- SD/MMC、GMAC、timer 和 IPI 等其他中断继续正常使用。

最终镜像已实机进入 `starry:~#`，人工输入、退格和短命令正常。由于 8250 硬件 FIFO
只有 16 字节，约 10 ms 的轮询周期不能保证接收无节流的长粘贴。VF2 自动化脚本已将
Moss shell 命令改为每字符间隔 2 ms；人工粘贴长命令时也应使用类似节流。

## 6. SD 卡与 ext4

当前 Moss 只探测 `0x16020000` 的 SD 控制器，即 U-Boot 中的 `mmc 1`。驱动以已有 `simple-sdmmc` 为基础接入 Moss 块设备框架，并补充了：

- MBR 和 GPT 分区表识别，包括 GPT header、entry 范围、GUID 和分区标签解析；
- 在整盘或分区中检查 ext4 超级块魔数；
- 从 DTB `/chosen/bootargs` 解析 `/dev/mmcblkNpN`、`PARTUUID=` 和 `PARTLABEL=`；
- 用有边界检查的分区块设备包装底层 SD，将 rootfs 逻辑块号翻译为整卡 LBA；
- SD/MMC PLIC 中断注册和等待队列；
- 命令超时、数据超时和控制器恢复；
- 读写错误向块设备和文件系统返回，替代 `unwrap()` 整机 panic；
- 块号范围检查和有限次数重试；
- `flush()` 等待卡完成编程，保证 `sync/fsync` 语义；
- 从 HCON 读取 FIFO 数据宽度；
- 将 FIFO 作为固定 MMIO 数据端口访问，而不是连续地址窗口。

rootfs 选择规则是：

1. 明确提供 `root=` 时，按分区号、PARTUUID 或 PARTLABEL 选择；
2. 没有 `root=` 时，先检查整盘是否直接为 ext4；
3. 否则只有分区表中恰好一个 ext4 分区时才自动选择；
4. 多个 ext4 分区且没有 `root=` 时拒绝猜测，避免挂载并写错数据。

当前卡必须使用 `root=/dev/mmcblk1p2 rw`。这个 Linux 风格的设备名只用于表达“第 2 分区”；
Moss 实际选择的仍是 VF2 已接入的唯一 SD/MMC root 设备。

实板 HCON 表明 VF2 的 host data width 为 32 位。原驱动使用 64 位访问并随数据偏移递增 MMIO 地址，这与 DesignWare MMC FIFO 的工作方式不符，现已改为在同一 FIFO 地址进行 32 位读写。

SD 数据阶段目前仍是 PIO。为了避免任务睡眠后不能及时处理 RXDR/TXDR 而触发 host timeout，数据搬运阶段会保持当前 CPU 活跃并轮询控制器 raw status；PLIC 仍用于控制器中断接管和其他命令路径。因此 SD 卡尚未达到“全程中断且 DMA 搬运”的状态。

### GPT 第 2 分区启动实机结果

本轮已经验证这条启动链；按当前统一网络配置复现时在 U-Boot 内执行：

```text

setenv serverip 192.168.88.1
setenv netmask 255.255.255.0
tftpboot 0x40200000 kernel
fdt addr 0x42200000

```

最终清理调试探针后的镜像已通过实板验证：

- TFTP 成功加载约 5 MiB 的 `moss-vf2.bin`；
- Moss 识别 4 GiB 内存，管理约 4087 MiB；
- 挂载 p2 上的 ext4 rootfs 并进入 `starry:~#`；
- `pwd` 输出 `/root`，根目录下可见 `/glibc`、`/musl`、`/proc`、`/sys` 等；
- `/glibc` 下可见 cagent、buildstorm、busybox 和其他测试文件；
- `cat /sys/devices/system/cpu/online` 输出 `0-3`，`nproc` 输出 `4`；
- `mount` 显示 `proc on /proc type proc`。

同一张卡的 p1 也已独立启动 Debian 13，Linux 日志识别到
`mmcblk1: p1 p2 p3 p4 p5`，说明 SD 卡、GPT 和 p1 文件系统本身正常。

### ext4 追加内容变成零的问题

实测曾出现以下现象：文件首次写入正确，追加后在页缓存中也正确，但执行 `sync` 并丢弃缓存后，追加区域变成等长的零字节。

逐层探针确认：

1. 页缓存交给 ext4 的数据正确；
2. ext4 计算出的物理块和交给块驱动的数据正确；
3. 真正覆盖数据的是随后提交 inode 长度的路径。

根因是页缓存先写回完整数据，之后又调用普通 `set_len(old_len -> new_len)`。普通扩容按 POSIX 语义会把旧 EOF 到块尾清零，因此刚写入的追加内容被二次覆盖。

修复后区分两种操作：

- 用户主动执行 `truncate/ftruncate` 扩容：新增区域继续补零；
- 页缓存写回后提交新长度：只更新 inode size，不再次清零数据。

验证结果：

- 写入 `FIRST_BLOCK` 后 `sync`、丢弃缓存并实读，内容正确；
- 追加 `SECOND_BLOCK` 后重复上述操作，两段内容均正确；
- 再用 `truncate` 扩容到 32 字节，新增的 7 字节仍全部为零。

## 7. GMAC1 网络

本节记录结果概要；完整驱动结构、硬件契约、错误恢复和 APK 分层验收见 [VisionFive 2 GMAC1 驱动实现与验收](星光二号板网卡驱动实现与验收.md)。

为 JH7110 GMAC1 接入了 DesignWare MAC 驱动，完成：

- GMAC1 时钟启用和 AXI/AHB reset 解除；
- 仅接受 VF2 v1.3B 的 `rgmii-id` 接线，明确拒绝 v1.2A RMII；
- 同时解析主线 Linux `starfive,jh7110-dwmac` 和 StarFive U-Boot 2021.10 `starfive,jh7110-eqos-5.20` DT；
- 从 DTB 的 `ethernet1` 读取寄存器、IRQ、MAC、PHY、FIFO、PBL、AXI burst 和 syscon 配置；
- 描述符环、TX/RX 数据路径和缓存一致性处理；
- probe 阶段保持 DMA 停止，第一次网络队列操作才启动；
- 双读 Clause 22 BMSR，并随链路协商结果更新 10/100/1000 Mbps、双工和 pause 流控；
- 识别 YT8531 后按速率更新 TX 时钟反相位，PHY delay 和驱动强度仍沿用 U-Boot 的冷启动配置；
- 中断处理按 RX/TX 源屏蔽并在 deferred poll 后重开，注册失败时保留轮询降级路径；
- RX 丢包和内存不足路径总会归还描述符，fatal DMA bus error 会完整停止、reset 并重建队列；
- 按 DWMAC4/5 的提交顺序先写 MAC 地址高寄存器、再写低寄存器，确保 address 0
  的精确单播过滤真正生效；
- 区分空闲 TX 环报告的 `TPS` 与真正需要恢复的 stopped TX，避免无在途 TX 时连带
  reset RX；
- 与 Moss `axnet`/TCP/IP 栈对接。

实板定位时观察到一个很有迷惑性的组合：广播 ARP 可以进入 VF2，RX DMA 描述符和
cache 同步也都正常，但 PC 发往 Moss MAC 的精确单播 TCP SYN 无法进入协议栈。根因不是
PC 端口或 p3 文件系统，而是 JH7110 EQoS 的 address 0 编程顺序错误。原代码先写 LOW、
后写 HIGH；改为与 [Linux DWMAC4](https://github.com/torvalds/linux/blob/master/drivers/net/ethernet/stmicro/stmmac/dwmac4_lib.c)
和 [U-Boot EQoS](https://github.com/u-boot/u-boot/blob/master/drivers/net/dwc_eth_qos.c)
一致的 HIGH、LOW 顺序后，精确单播恢复。

64 KiB 压测还暴露出 DMA status `0x00000007`（`TI | TPS | TBU`）会在 TX 环耗尽后作为
空闲边界状态出现。原逻辑把任意 `TPS` 都当成 fatal 并重置 TX/RX；现在只有 fatal bus
error，或仍有 TX 描述符在途时的 `TPS`，才触发队列恢复。

最终镜像已完成 Moss 与直连 PC 的双向 64 KiB TCP 校验：Moss→PC 的 SHA-256 为
`ffe4bc2959a3204a0daaadab184775412016fc780f6e724428fcb37459295b4c`，PC→Moss 为
`4ecc6cf1278dedc1768a73c5ad7a9421ae183da5bb07e3194433c7bbf70288d5`；长度均为
65536 字节，且没有再出现 DMA 队列重置。当前只接入 GMAC1，即 U-Boot 日志中的
`ethernet@16040000`。

自动化脚本现在使用 Python 接收器按预期长度读取数据，不再依赖不同 `nc` 实现对 EOF/
half-close 的差异；它也改用 TCP 探测链路，因为当前 BusyBox `ping` 依赖的 raw socket
尚未实现。断链恢复、三速重协商和 `apk fetch` 仍是可选测试，本轮尚未执行。

`git clone https://github.com/...` 未成功并不等同于网卡驱动失败。当时直接原因包括 rootfs 中 DNS 解析不可用，以及缺少 `ssh-keygen`/SSH 客户端；访问公网 Git 还需要 DNS、HTTPS CA 证书和相应用户态工具共同可用。

## 8. 四核 SMP

VF2 的 4 个 U74 核已经全部启用：

- 逻辑 CPU 0..3 映射到物理 hart 1..4；
- 从核通过 SBI HSM `hart_start` 启动；
- 每核建立启动栈、陷阱入口、PLIC context 和 timer；
- IPI 目标使用物理 hart ID；
- TLB shootdown 支持跨核通知。

实板启动标志为：

```text
MOSS_DTB cpu_nodes=4 memory_regions=1 memory_bytes=0x100000000
MOSS_SMP online=4
```

用户态 `cat /sys/devices/system/cpu/online` 和 `nproc` 应分别得到 `0-3` 和 `4`。

## 9. 用户态与系统调用问题

在 cagent 和现场赛 rootfs 验证过程中，还修复或确认了以下问题：

- ELF 加载失败不再因内部 `unwrap()` 导致整机 panic；
- 修正 wait/signal/进程退出清理，使 cagent 的并发子进程能够完整回收；
- 降低正式构建日志等级，避免每次进程进入用户态、退出和 `waitpid` 都刷屏；
- 修正 tmpfs/dentry 缓存一致性问题，避免 Git 已提交后重新查找仍看到旧目录状态；
- shell 模式改用 rootfs 中标准 `/bin/sh`，并保持其他构建目标的启动方式兼容；
- 官方现场赛 ext4 rootfs 能作为 VF2 rootfs 使用，不需要把 Moss 内核写进该镜像。

当前 p2 rootfs 运行 `mount` 时会看到：

```text
sys_prctl: unsupported option 3
```

option 3 是 `PR_GET_DUMPABLE`。Moss 的 `prctl` 已实现线程名和部分 capability 选项，
但尚未实现 `PR_GET_DUMPABLE`，当前返回 `EINVAL`。调用方能够容忍该结果，所以
`mount` 继续正常运行。本轮按决定不补该选项，它与 SD 分区挂载成功与否无关。

板载 `rustc helloworld.rs` 已成功生成并运行程序，输出 `Hello, VF2!`。该次小程序编译约耗时两分多钟，主要受 SD PIO 和板端工具链冷读影响，并非编译器卡死。

## 11. 仍未完成的主要工作

1. **SD/MMC DMA**：当前 PIO 正确但性能较低，`rustc`、大型构建和大量小文件 I/O 会明显受限。
2. **UART RX 中断**：当前轮询方案可靠启动且人工交互正常，但无节流长粘贴可能溢出 16 字节 FIFO。若要恢复纯中断模式，需继续查明固件交接时的 UART pending 清理方式。
3. **eMMC**：当前只支持 SDIO1/SD 卡，尚未为 `sdio0@16010000` 完成探测、初始化和双设备选择。
4. **`prctl` 兼容性**：`PR_GET_DUMPABLE` 等选项尚未实现；当前警告不影响 shell 和 rootfs，暂不补齐。
5. **公网用户态环境**：需要补齐 DNS 配置、CA 证书、SSH 客户端和 `ssh-keygen`，才能完整验证 HTTPS/SSH Git clone。
6. **存储压力测试**：还应执行长时间随机读写、反复掉缓存、重启后 `e2fsck` 和大规模源码构建。
7. **更多外设**：USB、PCIe/NVMe、HDMI/显示、音频、GPIO 等尚未适配。
8. **电源管理**：关机通过 SBI system reset 的 shutdown 类型进入安全停止；是否真正切断板卡电源取决于 OpenSBI、U-Boot 和 PMIC，电源灯保持点亮不代表文件系统没有完成关机。

## 13. 总结

这轮工作的结果不是简单地让 VF2 打印启动日志，而是打通了从固件启动、平台中断、串口交互、SD/ext4、物理网络、四核 SMP 到 glibc 用户程序的完整路径。2026-08-15 的实板结果进一步证明，Moss 不再只能使用无分区的整盘 ext4，也可在保留 GPT 多分区卡的情况下安全指定 p2 作为 rootfs。
