# VisionFive 2 上板、启动与维护指令

本文记录 StarFive VisionFive 2（JH7110）上构建、传输、启动和维护 MOSS 的完整操作流程。文中的默认值来自 2026-08-15 实板环境；串口名、PC 网卡名和 SD 卡设备名可能随机器变化，执行前必须重新确认。

GMAC1 的驱动架构、DMA/PHY/中断实现和分层验收依据见 [VisionFive 2 GMAC1 驱动实现与验收](星光二号板网卡驱动实现与验收.md)，移植过程和问题背景见 [VisionFive 2 移植与调试工作总结](星光二号板工作总结.md)。

## 1. 当前已验证环境

| 项目 | 当前配置 |
| --- | --- |
| 板卡 | VisionFive 2 v1.3B，4 GiB RAM |
| 固件 | OpenSBI v1.2、StarFive U-Boot 2021.10 |
| 串口 | `/dev/ttyACM0`，115200 波特率 |
| PC 直连网口 | `enp3s0` |
| PC IP | `192.168.88.1/24` |
| U-Boot/MOSS IP | `192.168.88.2/24` |
| TFTP 根目录 | `/srv/tftp` |
| TFTP 内核名 | `/srv/tftp/kernel` |
| MOSS 加载/入口地址 | `0x40200000` |
| U-Boot DTB 地址 | `0x42200000` |
| U-Boot SD 卡设备 | `mmc 1`，控制器 `sdio1@16020000` |
| Linux/MOSS SD 卡设备 | `/dev/mmcblk1` |

当前 119.2 GiB SD 卡实测布局如下：

| 分区 | 容量 | 内容 | 已验证用途 |
| --- | ---: | --- | --- |
| `p1` | 29.8 GiB | Debian 13 | 原生 Linux 默认启动；p5 swap 可正常激活 |
| `p2` | 29.8 GiB | Debian 13 | MOSS shell；Git/GCC/Vim/apt/Python/curl |
| `p3` | 27.9 GiB | Alpine 3.22.1 | MOSS shell；Git/GCC/Vim/Rust/Cargo/apk/wget |
| `p4` | 27.9 GiB 分区，约 690 MiB ext4 | Alpine 3.22.1 | 新写入的 MOSS rootfs；工具与 p3 基本一致 |
| `p5` | 3.7 GiB | swap | 原生 Debian 已验证可激活；不能作为 rootfs |

这 5 个分区只是当前测试卡的布局，不是 MOSS 的固定要求。MOSS 支持 GPT/MBR 分区 rootfs，也保留整盘 ext4 rootfs 的兼容。

> **重要：** PC 上的系统盘是 NVMe，而 SD 卡在本次环境中曾显示为 `/dev/sdb`。设备名并不固定。任何 `dd`、`e2fsck -y`、`resize2fs` 或 `tune2fs` 操作前，都必须重新通过容量、型号、接口和分区表确认目标；文中的 `/dev/sdX` 是故意不可直接使用的占位符。

## 2. 最短启动流程

### 2.1 PC 端

在仓库根目录构建并部署内核：

```bash
make site-vf2

sudo ip addr replace 192.168.88.1/24 dev enp3s0
sudo ip link set dev enp3s0 up

sudo install -m 0644 build/site-vf2/moss-vf2.bin /srv/tftp/kernel
sha256sum build/site-vf2/moss-vf2.bin /srv/tftp/kernel
```

确认 TFTP UDP 69 端口正在监听：

```bash
sudo ss -lunp | grep -E '192\.168\.88\.1:69|:69[[:space:]]'
```

如果没有 TFTP 服务：

```bash
sudo /usr/sbin/in.tftpd --listen --user tftp \
  --address 192.168.88.1:69 --secure /srv/tftp
```

打开串口：

```bash
sudo minicom -D /dev/ttyACM0 -b 115200 -o
```

### 2.2 U-Boot 端

先连接 minicom，再复位或上电，并在 `Hit any key to stop autoboot` 的 2 秒倒计时内连续按空格，直到出现：

```text
StarFive #
```

逐行执行以下命令，每行都等待 `StarFive #` 再输入下一行：

```text
setenv ipaddr 192.168.88.2
setenv serverip 192.168.88.1
setenv netmask 255.255.255.0
printenv ipaddr serverip netmask

tftpboot 0x40200000 kernel
fdt addr 0x42200000
fdt set /chosen bootargs "root=/dev/mmcblk1p3 rw"
fdt print /chosen bootargs
go 0x40200000
```

把 `p3` 改成 `p2` 或 `p4` 即可切换 rootfs。不要执行 `saveenv`。

正常的 p3/p4 启动末尾应看到：

```text
MOSS_DTB cpu_nodes=4 memory_regions=1 memory_bytes=0x100000000
MOSS_MEMORY managed_mib=4087 free_mib=4087
starry:~#
```

当前修复后的内核不会再卡在 NTP，也不应再出现以下旧版故障：

```text
register handler for VF2 PLIC source 78 failed
Alarm clock
Alarm clock
```

## 3. 接线和上电顺序

1. 将 USB 串口连接到 PC，确认出现 `/dev/ttyACM0`。
2. 用网线直连 PC 与 VF2 的 GMAC1 网口。
3. 插入准备好的 SD 卡。
4. 在 PC 上先启动 minicom，避免错过 U-Boot 的短倒计时。
5. 给 VF2 上电或按 Reset。

检查串口和网口：

```bash
ls -l /dev/ttyACM0
ip -brief address show enp3s0
ip -brief link show enp3s0
```

当前驱动只支持 VF2 v1.3B 的 GMAC1 `rgmii-id`。v1.2A 的 GMAC1 是 RMII 接线，不能直接套用本文的网络驱动配置。

## 4. 构建、检查和部署 MOSS

构建 VF2 交互镜像：

```bash
make site-vf2
```

产物位于固定构建目录：

```text
build/site-vf2/moss-vf2.bin
```

该目标固定使用 4 GiB、4 核、VF2 平台和 `site-init`。`site-init` 进入 `/root`，设置 `starry:~#` 提示符后启动 `/bin/sh`；板卡地址 `192.168.88.2/24` 和网关 `192.168.88.1` 已固化，不接受额外构建参数。

提交或上板前可运行 VF2 静态检查；它会验证主线 Linux DT、StarFive U-Boot 2021.10 DT、GMAC 状态机和最终构建：

```bash
scripts/check_vf2_gmac_static.sh
```

部署前同时计算两份文件的摘要，必须一致：

```bash
sudo install -m 0644 build/site-vf2/moss-vf2.bin /srv/tftp/kernel
sha256sum build/site-vf2/moss-vf2.bin /srv/tftp/kernel
```

2026-08-15 本次 p2/p3/p4 实板验证使用的文件为 5,227,776 字节，SHA-256 为：

```text
c4c4b3f25e2231e2b2eae53218cc8af3f448089fe91c89e3006de7049cad7779
```

重新构建后摘要可能变化，应以“本地构建产物与 `/srv/tftp/kernel` 一致”为准。

## 5. PC 网口、TFTP 和外网转发

### 5.1 配置直连地址

```bash
sudo ip addr replace 192.168.88.1/24 dev enp3s0
sudo ip link set dev enp3s0 up
ip addr show dev enp3s0
```

如果 `ip -brief link` 显示 `NO-CARRIER`，通常表示开发板未上电、MOSS 已停机或网线未连接。

### 5.2 检查 TFTP

```bash
test -s /srv/tftp/kernel
ls -lh /srv/tftp/kernel
sudo ss -lunp | grep -E ':69[[:space:]]'
```

手工启动仅绑定直连地址的 TFTP 服务：

```bash
sudo /usr/sbin/in.tftpd --listen --user tftp \
  --address 192.168.88.1:69 --secure /srv/tftp
```

如果端口已经被其他 `in.tftpd` 占用，不要重复启动；先用 `ss` 和 `ps -ef | grep '[i]n\.tftpd'` 确认实际监听进程。

### 5.3 可选：让 MOSS 访问公网

仓库提供了持久化配置脚本，会安装 IP 转发、nftables NAT 和可选的 chrony 放行规则：

```bash
sudo scripts/setup_vf2_network.sh install
sudo scripts/setup_vf2_network.sh status
```

配置已安装但运行期状态丢失时：

```bash
sudo scripts/setup_vf2_network.sh apply
```

移除这些 PC 端持久化配置：

```bash
sudo scripts/setup_vf2_network.sh uninstall
```

该脚本会修改 `/etc/sysctl.d`、nftables 和 systemd 配置；只需要直连 TFTP/HTTP 测试时不必安装。

### 5.4 切换分区不需要切换 PC 网口

启动 p2、p3 或 p4 时，PC 端都使用同一套网络配置，不需要为不同分区配置不同网口：

| 位置 | 统一配置 |
| --- | --- |
| PC 直连 VF2 的网口 | `enp3s0`，`192.168.88.1/24` |
| U-Boot/MOSS | `192.168.88.2/24` |
| MOSS 默认网关 | `192.168.88.1` |
| PC 当前公网出口 | 由默认路由决定，本次为 `wlo1` |

分区只决定加载哪个 rootfs。各 rootfs 内的 `/etc/resolv.conf`、软件仓库和工具不同，但 PC 直连地址、VF2 地址和网关不应随分区改变。

U-Boot 的 `ipaddr`、`serverip` 和 `netmask` 只负责 TFTP 阶段；进入 MOSS 后使用 MOSS 的运行时网络。若 PC 的公网出口从 Wi-Fi 切换到有线网、VPN 或热点，已有 nftables 规则中记录的出口接口可能过期，应重新执行：

```bash
sudo scripts/setup_vf2_network.sh apply
```

## 6. 串口和进入 U-Boot

打开 minicom：

```bash
sudo minicom -D /dev/ttyACM0 -b 115200 -o
```

常用按键：

- `Ctrl-A` 后按 `Z`：显示 minicom 帮助。
- `Ctrl-A` 后按 `X`：退出 minicom 并释放串口。
- `Ctrl-A` 后按 `F`：发送 BREAK；在原生 Linux 串口控制台中可用于 Magic SysRq。
- U-Boot 倒计时中按任意键：中断自动启动。
- U-Boot 命令输错或输入粘连时按 `Ctrl-C`：清空当前命令并回到 `StarFive #`。

VF2 UART 当前使用约 10 ms 周期轮询接收，硬件 FIFO 只有 16 字节。人工逐行输入正常；自动化或大段粘贴应设置至少 2 ms/字符的节流。若一次粘贴多行后出现类似错误：

```text
flags type check failure for "netmask"
```

应按 `Ctrl-C`，逐行重新输入，并用下面的命令回读：

```text
printenv ipaddr serverip netmask
```

### 6.1 错过 U-Boot 后怎么办

如果已经进入 p1 的 Debian，并且有登录权限，优先正常执行：

```bash
sudo reboot
```

如果没有登录权限，只在调试环境中可使用串口 Magic SysRq：

1. `Ctrl-A`、`F`，随后按 `s`，等待 `Emergency Sync complete`。
2. 再次 `Ctrl-A`、`F`，随后按 `b` 强制复位。
3. 立刻连续按空格截停 U-Boot。

`b` 是强制复位，下一次 Debian 启动可能执行 journal recovery；生产数据环境应使用正常关机或重启。

## 7. U-Boot 中检查 SD 卡和分区

选择 SD 卡并重新扫描：

```text
mmc dev 1
mmc rescan
mmc info
part list mmc 1
```

查看各分区文件系统和目录：

```text
fstype mmc 1:1
fstype mmc 1:2
fstype mmc 1:3
fstype mmc 1:4

ls mmc 1:2 /
ls mmc 1:3 /
ls mmc 1:4 /
```

`mmc 0` 对应 eMMC 控制器。启动日志中的：

```text
Card did not respond to voltage select! : -110
```

通常来自当前未就绪的 `mmc 0`，不代表 `mmc 1` 上的 SD 卡不可用。看到 `part list mmc 1` 或 Linux 日志中的 `mmcblk1: p1 p2 p3 p4 p5` 才能确认 SD 卡分区已识别。

## 8. 分别启动 p2、p3 和 p4

每次复位后都先重新设置 U-Boot 网络并下载内核：

```text
setenv ipaddr 192.168.88.2
setenv serverip 192.168.88.1
setenv netmask 255.255.255.0
printenv ipaddr serverip netmask

tftpboot 0x40200000 kernel
```

TFTP 成功标志：

```text
Using ethernet@16040000 device
TFTP from server 192.168.88.1; our IP address is 192.168.88.2
Filename 'kernel'.
Load address: 0x40200000
done
Bytes transferred = 5227776 (4fc500 hex)
```

TFTP 使用 U-Boot 自带网卡驱动，只能证明 U-Boot 网络正常；MOSS GMAC 必须进入 shell 后再用 TCP 测试。

### 8.1 p2：Debian 13 rootfs

```text
fdt addr 0x42200000
fdt set /chosen bootargs "root=/dev/mmcblk1p2 rw"
fdt print /chosen bootargs
go 0x40200000
```

p2 实板工具：Git、GCC、Vim、apt、Python 3、curl。它没有 Alpine 的 apk，也没有当前 p3/p4 中的 rustc、cargo 和 wget。

### 8.2 p3：Alpine 3.22.1 rootfs

```text
fdt addr 0x42200000
fdt set /chosen bootargs "root=/dev/mmcblk1p3 rw"
fdt print /chosen bootargs
go 0x40200000
```

p3 是本次“卡在 NTP、无法进入 shell”问题的原始复现分区。使用当前内核后已经实板确认能立即进入 shell，Git、GCC、Vim、Rust、Cargo、apk、wget 和 TCP 网络正常。

### 8.3 p4：新写入的 Alpine rootfs

```text
fdt addr 0x42200000
fdt set /chosen bootargs "root=/dev/mmcblk1p4 rw"
fdt print /chosen bootargs
go 0x40200000
```

p4 已通过 PC 端直接写入 rootfs 并实板启动。当前未扩容，ext4 仍只有 176640 个 4 KiB 块，约 690 MiB，只剩约 16 MiB 空闲空间。现有工具可以启动，但安装 Python 等较大软件前必须先扩容。

### 8.4 p1 和 p5

p1 默认由 U-Boot 的 extlinux 配置启动原生 Debian Linux。需要回到 p1 时，不截停 U-Boot，让它自动启动即可。p5 是 swap，不要设置为 `root=`。

### 8.5 其他 rootfs 表达方式

MOSS 也支持：

```text
fdt set /chosen bootargs "root=PARTUUID=<GPT-PARTUUID> rw"
fdt set /chosen bootargs "root=PARTLABEL=<分区标签> rw"
```

当前 p3 与 p4 是从同一 ext4 镜像复制出来的，文件系统 UUID 相同。使用明确的 `/dev/mmcblk1p3` 和 `/dev/mmcblk1p4` 已验证可以正常启动；在 UUID 去重前不要使用该重复 UUID 选择 p3/p4。

`fdt set` 只修改内存中的本次 DTB，不要执行 `saveenv`。如果没有提供 `root=`，MOSS 只会在整盘直接为 ext4，或分区表中恰好只有一个 ext4 分区时自动选择；当前多 ext4 分区卡必须显式指定。

## 9. MOSS shell 中确认启动结果

### 9.1 基础检查

```sh
pwd
cat /etc/os-release
stat -f /
cat /proc/cpuinfo
cat /proc/meminfo
cat /sys/devices/system/cpu/online
nproc
mount
```

当前 VF2 应有 4 个逻辑 CPU：

```text
0-3
4
```

MOSS 当前没有提供 `/proc/cmdline`，根文件系统也不一定作为 `/` 条目出现在 `/proc/mounts` 中，因此：

- `cat /proc/cmdline` 可能显示文件不存在；
- `df -h /` 可能显示 `can't find mount point`；
- 应使用 `stat -f /`、`/etc/os-release` 和 U-Boot 中回读的 bootargs 确认分区。

当前三个分区可由 `stat -f /` 的块数区分：

| 分区 | 发行版 | 4 KiB 块总数 |
| --- | --- | ---: |
| p2 | Debian 13 | 7,812,608 |
| p3 | Alpine 3.22.1 | 7,324,160 |
| p4 | Alpine 3.22.1，未扩容 | 176,640 |

### 9.2 工具检查

p2 Debian：

```sh
git --version
gcc --version | head -n 1
vim --version | head -n 1
apt --version
python3 --version
python3 -c 'print(6 * 7)'
curl --version | head -n 1
```

p3/p4 Alpine：

```sh
git --version
gcc --version | head -n 1
vim --version | head -n 1
rustc --version
cargo --version
apk --version
wget --help
```

包管理器按发行版选择：Debian 使用 `apt`，Alpine 使用 `apk`。不要把某一发行版缺少另一套包管理器当成内核故障。

可选的 GCC 小程序验证会临时写入 rootfs，结束后立即删除：

```sh
printf '#include <stdio.h>\nint main(void){puts("VF2_OK");return 0;}\n' > /tmp/vf2.c
gcc /tmp/vf2.c -o /tmp/vf2
/tmp/vf2
rm -f /tmp/vf2 /tmp/vf2.c
sync
```

板端 `rustc` 首次编译可能需要两分钟以上，主要是 SD PIO 和工具链冷读，不等同于编译器卡死。

### 9.3 比赛脚本

p2 或包含 `/glibc` 测试内容的 rootfs 中：

```sh
cd /glibc
./cagent_testcode.sh
```

```sh
cd /glibc
./buildstorm_testcode.sh
```

如果脚本需要 Bash 而当前 `/bin/sh` 不兼容，应显式执行 `bash ./脚本名`，前提是 rootfs 已安装 Bash。

## 10. 网络验证

### 10.1 不要用 ping 作为当前基准

BusyBox `ping` 需要 raw socket，而当前 MOSS 会打印：

```text
Unsupported socket type: domain: 2, ty: 3
ping: can't create raw socket: Socket type not supported
```

这不代表 GMAC 或 TCP 失效。应使用 TCP 验证。

### 10.2 PC 临时 HTTP 服务

PC 端执行：

```bash
python3 -m http.server 8000 \
  --bind 192.168.88.1 \
  --directory /srv/tftp
```

p3/p4 Alpine 执行：

```sh
wget -O /dev/null http://192.168.88.1:8000/kernel
```

p2 Debian 执行：

```sh
curl -w '%{http_code} %{size_download}\n' \
  -o /dev/null http://192.168.88.1:8000/kernel
```

本次三个分区均完整接收 5,227,776 字节；p2 返回 HTTP 200。

传输过程中偶尔可能看到：

```text
JH7110 GMAC1 dropped RX descriptor ...
```

如果最终显示 100% 且字节数正确，本次传输已成功；如果频繁出现、连接中断或摘要不一致，应保留完整日志继续检查 RX 描述符状态。

### 10.3 netcat 双向测试

MOSS 向 PC 发送，PC 先执行：

```bash
nc -l 192.168.88.1 19000
```

MOSS 再执行：

```sh
echo MOSS_VF2_TX_OK | busybox nc -w 3 192.168.88.1 19000
```

PC 向 MOSS 发送，MOSS 先执行：

```sh
busybox nc -l -p 19001
```

PC 再执行：

```bash
printf 'MOSS_VF2_RX_OK\n' | nc -w 3 192.168.88.2 19001
```

不同 `nc` 实现对 `-l`、`-p` 和 EOF 的语义可能不同，严格验收建议使用仓库自动化脚本。

### 10.4 自动化 GMAC1 验收（可选）

先关闭 minicom，确保 `/dev/ttyACM0` 未被占用：

```bash
sudo scripts/run_vf2_gmac_test.py \
  --serial /dev/ttyACM0 \
  --interface enp3s0 \
  --root-device /dev/mmcblk1p3 \
  --log vf2-gmac-p3.log
```

脚本启动后复位 VF2。切换 p2/p4 时修改 `--root-device`。查看完整参数：

```bash
python3 scripts/run_vf2_gmac_test.py --help
```

可选三速链路测试：

```bash
sudo scripts/run_vf2_gmac_test.py \
  --root-device /dev/mmcblk1p3 \
  --speed-suite \
  --log vf2-gmac-speed.log
```

仅在 Alpine rootfs 已配置仓库、DNS、CA 证书且空间足够时测试 apk：

```bash
sudo scripts/run_vf2_gmac_test.py \
  --root-device /dev/mmcblk1p3 \
  --apk-package busybox \
  --log vf2-gmac-apk.log
```

## 11. 将 SD 卡插入 PC 后写 rootfs

### 11.1 安全原则

- 先关闭 VF2，断开板端电源，再拔 SD 卡。
- PC 端只操作经过容量、USB 接口、GPT UUID 和分区数量共同确认的设备。
- 分区 rootfs 镜像写入 `/dev/sdX4`；整盘镜像才写 `/dev/sdX`。
- 当前 p4 原先没有文件系统签名，因此本次没有保留约 30 GiB 的整分区备份，只保留了很小的 GPT 元数据备份。
- 写入 p4 不应修改 p1、p2、p3、p5；必要时可在前后对这些分区的前 4 MiB 做摘要比较。

### 11.2 识别 SD 卡

插卡前后分别执行：

```bash
lsblk -e 7 -o NAME,PATH,TYPE,SIZE,MODEL,SERIAL,TRAN,RM,FSTYPE,UUID,PARTUUID,MOUNTPOINTS
```

当前卡应表现为：

- USB、可移除设备；
- 容量约 119.2 GiB；
- GPT UUID `ccc75430-6c08-4549-8ead-d78c699cd303`；
- 5 个分区，大小约为 29.8、29.8、27.9、27.9、3.7 GiB。

进一步只读确认：

```bash
sudo sfdisk --dump /dev/sdX
sudo blkid /dev/sdX1 /dev/sdX2 /dev/sdX3 /dev/sdX4 /dev/sdX5
```

确认没有自动挂载：

```bash
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS /dev/sdX
swapon --show
```

如果识别结果与预期不一致，立即停止。绝不能把 PC 的 `/dev/nvme0n1` 当成 SD 卡。

### 11.3 区分“分区 rootfs 镜像”和“整盘镜像”

检查镜像：

```bash
file rootfs.img
fdisk -l rootfs.img
```

- `file` 直接显示 `Linux ... ext4 filesystem data`，且 `fdisk` 没有分区表：这是分区 rootfs 镜像，应写入 `/dev/sdXN`。
- 镜像内部带 GPT/MBR 和多个分区：这是整盘镜像，写入 `/dev/sdX` 会覆盖现有全部分区。
- `*.img.xz` 只是上述原始镜像的压缩形式，解压后仍按内部布局决定写整盘还是分区。

不要因为文件名中带 `sdcard` 或 `rootfs` 就猜测写入层级。

### 11.4 当前已验证的 p4 写入流程

本次使用的源镜像：

```text
images/on-site-final-2025/alpine-linux-riscv64-ext4fs.img
```

镜像属性：

```text
size    = 723517440 bytes
sha256  = ec18eedee8eded3b524a01e7d2bef84d7c703a15eb2af55dff2f6edd6b2117bd
type    = ext4 partition image
```

先只读检查源镜像：

```bash
sha256sum images/on-site-final-2025/alpine-linux-riscv64-ext4fs.img
e2fsck -fn images/on-site-final-2025/alpine-linux-riscv64-ext4fs.img
```

保存很小的 GPT 元数据备份：

```bash
sudo sgdisk --backup=vf2-gpt-before.bin /dev/sdX
```

确保各分区未挂载，然后只写 p4：

```bash
sudo umount /dev/sdX1 /dev/sdX2 /dev/sdX3 /dev/sdX4 /dev/sdX5 \
  2>/dev/null || true

sudo dd \
  if=images/on-site-final-2025/alpine-linux-riscv64-ext4fs.img \
  of=/dev/sdX4 \
  bs=16M iflag=fullblock oflag=direct \
  status=progress conv=fsync,notrunc

sync
sudo blockdev --flushbufs /dev/sdX
```

再次强调：`of=` 必须是确认后的第四分区 `/dev/sdX4`，不能是整盘 `/dev/sdX`，也不能是 PC 的 NVMe。

对当前固定镜像可校验写入区域：

```bash
sudo cmp -n 723517440 \
  images/on-site-final-2025/alpine-linux-riscv64-ext4fs.img \
  /dev/sdX4
```

`cmp` 无输出并返回 0 表示写入内容一致。也可以读取 176640 个 4 KiB 块计算摘要：

```bash
sudo dd if=/dev/sdX4 bs=4096 count=176640 status=none | sha256sum
```

结果应为源镜像的 SHA-256。

### 11.5 UUID 是否必须修改

当前 p3 和 p4 的 ext4 UUID 都是：

```text
dff3fc28-3a72-4c0f-92cb-b681cc185680
```

这不会阻止以下显式设备路径启动：

```text
root=/dev/mmcblk1p3 rw
root=/dev/mmcblk1p4 rw
```

本次 p4 已在不修改 UUID 的情况下实板启动。只有准备在原生 Linux 中按文件系统 UUID 挂载、使用 `/dev/disk/by-uuid`，或由其他用户态工具按 UUID 识别分区时，才建议去重。MOSS 启动请选择设备路径、PARTUUID 或 PARTLABEL，不要写成 `root=UUID=...`：

```bash
sudo e2fsck -fy /dev/sdX4
sudo tune2fs -U random -L MOSS_P4 /dev/sdX4
sudo blkid /dev/sdX3 /dev/sdX4
```

这些命令会写 p4 的 ext4 元数据，应在确认目标后执行。

### 11.6 是否需要扩容

把 690 MiB ext4 镜像写入 27.9 GiB p4 后，文件系统不会自动变大。仅启动和运行现有工具时可以暂不扩容；需要安装 Python、依赖包或保存大量数据时执行：

```bash
sudo e2fsck -fy /dev/sdX4
sudo resize2fs /dev/sdX4
sudo e2fsck -fn /dev/sdX4
```

扩容不会改变 GPT 分区边界，只把 p4 内部 ext4 使用范围扩展到整个分区。

### 11.7 只读挂载检查和安全拔卡

```bash
sudo mkdir -p /mnt/vf2-rootfs
sudo mount -o ro /dev/sdX4 /mnt/vf2-rootfs
cat /mnt/vf2-rootfs/etc/os-release
ls -l /mnt/vf2-rootfs/bin/sh
sudo umount /mnt/vf2-rootfs

sync
sudo blockdev --flushbufs /dev/sdX
```

确认没有挂载点后，再从 PC 拔卡并装回 VF2。

### 11.8 整盘镜像写入（会清除当前五分区布局）

只有已经确认镜像内部带完整磁盘布局，并且明确要覆盖整张卡时才执行：

```bash
sudo dd if=full-disk.img of=/dev/sdX bs=16M \
  iflag=fullblock oflag=direct status=progress conv=fsync
sync
```

xz 压缩的整盘镜像：

```bash
xz -dc full-disk.img.xz | sudo dd of=/dev/sdX bs=16M \
  oflag=direct status=progress conv=fsync
sync
```

以上操作会覆盖 GPT、p1–p5 以及所有数据，不能用于本次“只替换 p4 rootfs”的需求。

## 12. 切换分区、同步和复位

在 MOSS shell 中切换 rootfs 前先执行：

```sh
sync
```

当前 VF2 上的 MOSS `reboot -f` 会让系统停机、网口变为 `NO-CARRIER`，但不会自动重新进入固件。推荐流程：

1. 在 MOSS 中执行 `sync`。
2. 执行 `reboot -f` 后等待串口停止，或直接在 `sync` 完成后按硬件 Reset。
3. 按 Reset 或重新上电。
4. 连续按空格进入 `StarFive #`。
5. 重新 TFTP 内核并修改 `root=/dev/mmcblk1pN`。

不截停 U-Boot 时会返回 p1 原生 Debian。

## 13. 常见问题和判断方法

### 13.1 TFTP 失败

依次检查：

```bash
ip -brief address show enp3s0
ip -brief link show enp3s0
test -s /srv/tftp/kernel
sudo ss -lunp | grep -E ':69[[:space:]]'
sha256sum build/site-vf2/moss-vf2.bin /srv/tftp/kernel
```

U-Boot 中重新检查：

```text
printenv ipaddr serverip netmask ethact
```

成功时通常使用 `ethernet@16040000`。某一路 PHY 协商失败不等于另一网口一定失败。

### 13.2 卡在 NTP、IRQ 78 或反复 Alarm clock

这说明 TFTP 中很可能仍是旧内核。当前修复包括：

- NTP 在后台运行，shell 不再等待它结束；
- GMAC 驱动拥有 IRQ 78 时，不再重复注册通用 IRQ waker。

重新构建、覆盖 `/srv/tftp/kernel`，并确认摘要一致。

### 13.3 找不到或挂错 rootfs

多分区卡必须显式设置：

```text
fdt addr 0x42200000
fdt set /chosen bootargs "root=/dev/mmcblk1p3 rw"
fdt print /chosen bootargs
```

出现 `Failed to initialize filesystem: LinuxError::EOPNOTSUPP` 时，优先检查 `root=` 是否遗漏、分区号是否正确，以及目标是否确实为 ext4。

### 13.4 p4 出现 No space left on device

p4 当前未扩容，只剩约 16 MiB。把卡插回 PC 后按第 11.6 节运行 `e2fsck` 和 `resize2fs`。

### 13.5 ping 不通但 wget/curl 正常

当前是 raw socket 未实现，不是 TCP 网卡故障。使用 HTTP、netcat 或自动化脚本测试。

### 13.6 TFTP 正常但 MOSS 网络不通

U-Boot TFTP 与 MOSS GMAC 是两套驱动路径。进入 MOSS 后检查：

- 是否看到 GMAC1 初始化日志；
- PC 网口是否仍为 `192.168.88.1/24`；
- 是否能用 wget/curl 访问 PC 临时 HTTP 服务；
- `/srv/tftp/kernel` 是否是当前内核。

日志：

```text
JH7110 GMAC1 had no firmware MAC; using 02:4d:4f:53:53:01
```

表示固件 DTB 没提供可用 MAC，驱动使用本地管理地址，不是启动失败。

### 13.7 Git clone、apk 或 apt 访问公网失败

先分层判断：

1. 直连 PC TCP 是否正常；
2. PC 是否启用了转发/NAT；
3. DNS 是否可用；
4. 系统时间是否正确；
5. CA 证书和 TLS 是否齐全；
6. rootfs 是否有足够空间。

`git clone https://...` 失败不能单独证明 GMAC 故障。

#### 13.7.1 `apk` 报 `temporary error`，但仍显示软件包数量

现场曾在 p3 遇到以下现象：

```text
WARNING: updating https://dl-cdn.alpinelinux.org/...: temporary error (try again later)
0 unavailable, 2 stale; 24691 distinct packages available
ERROR: openssh-...: temporary error (try again later)
```

显示 `24691 distinct packages available` 不代表本次联网成功。`apk` 更新索引失败后仍可使用本地旧索引，因此能够解析 `openssh` 及其依赖；真正下载每个 `.apk` 文件时没有公网连接，才会全部失败。不要先换 Alpine 镜像源，也不要重写 p3 rootfs。

本次实测根因是 PC 上的 `moss-vf2-network.service` 开机时启动过早。当时 VF2 直连地址或默认公网出口尚未就绪，服务报错后没有自动重试：

```text
cannot find VF2 or default uplink interface
```

结果是 `net.ipv4.ip_forward=1` 虽然仍然存在，但 `table ip moss_vf2` NAT 表没有建立。此故障与当前启动 p2、p3 还是 p4 无关。

先在 PC 端检查：

```bash
ip -brief address show
ip -4 route show default
systemctl status --no-pager -l moss-vf2-network.service
sudo nft list table ip moss_vf2
```

本次环境应至少能看到：

```text
enp3s0  UP  192.168.88.1/24
default via ... dev wlo1
```

若服务为 `failed`，或者 nft 命令提示 `No such file or directory`，等待 PC 的直连网口和公网出口都就绪，然后恢复转发：

```bash
cd ~/Data/moss
sudo systemctl restart moss-vf2-network.service
sudo systemctl status --no-pager moss-vf2-network.service
sudo nft list table ip moss_vf2
```

正常状态应为 `active (exited)`，并能列出包含 `forward`、`postrouting` 和 `masquerade` 的 `table ip moss_vf2`。也可以直接重新应用当前接口配置：

```bash
cd ~/Data/moss
sudo scripts/setup_vf2_network.sh apply
sudo scripts/setup_vf2_network.sh status
```

然后回到 p3/p4 验证 HTTPS 和 apk：

```sh
date -u
cat /etc/resolv.conf
wget -O /dev/null https://dl-cdn.alpinelinux.org/alpine/v3.22/main/riscv64/APKINDEX.tar.gz
apk update
apk add openssh
```

如果 VF2 能访问 PC 上的临时 HTTP 服务，但以上公网 HTTPS 失败，GMAC 和直连链路通常已经正常，应继续检查 PC NAT、DNS、系统时间和 CA 证书。如果连 PC 的 HTTP 服务也失败，才回到第 13.6 节检查直连网口和 MOSS GMAC。

### 13.8 minicom 输入丢字或命令粘连

不要一次粘贴整段 U-Boot 命令。逐行输入、等待提示符，并在关键步骤使用 `printenv`、`fdt print` 回读。自动化输入设置至少 2 ms/字符。

### 13.9 原生 Debian 启动时恢复 journal

如果此前使用硬件 Reset 或 Magic SysRq `b`，Debian 可能打印 `recovering journal`。等待 fsck 完成；后续尽量先正常关机，至少先执行 `sync`。

### 13.10 `sys_prctl: unsupported option 3`

这是用户程序查询 `PR_GET_DUMPABLE` 时返回 `EINVAL` 的兼容性警告，不代表 ext4 挂载失败，普通 shell 命令可以继续运行。
